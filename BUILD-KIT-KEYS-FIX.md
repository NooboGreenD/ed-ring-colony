# Комплект первой сборки: ключи встраиваются в многострочный bundle.py

Дата: 2026-10-09. Жалоба: при подготовке пакета для скачивания — «Не удалось
встроить ключи: в bundle.py не найден TRUSTED_KEYS».

## Причина

`GET /api/admin/uploader/build-kit` (кнопка скачивания комплекта в «Обновления
Helper») вставляет публичные ключи канала в `uploader/bundle.py`. Маршрут искал
словарь регуляркой `/^TRUSTED_KEYS:…\{.*\}\s*$/m`. Точка в JavaScript не
совпадает с переводом строки, поэтому регулярка находила только словарь,
целиком умещающийся в одну строку. Актуальный `bundle.py` держит словарь
многострочным, с комментариями (строки 85–90), и проверка падала: маршрут
отвечал 500 с этим текстом.

Клиентский разбор ключей (`clientTrustedKeys`) и публикация релиза
(`stampTrustedKeysSource`) многострочный словарь уже понимали. Расходился только
маршрут сборки.

## Исправление

* Вставка вынесена в `embedTrustedKeys()` (`src/lib/uploaderStore.ts`). Регулярка
  находит весь словарь, однострочный или многострочный, и заменяет его целиком.
  Текст вне словаря не меняется.
* `build-kit/route.ts` вызывает эту функцию. Текст ошибки для файла без
  словаря прежний.
* `stampTrustedKeysSource` (публикация релиза) не менялась.

## Проверка

`scripts/tests/uploader-build-kit.test.mjs`:

* настоящий маршрут на настоящем `uploader/bundle.py` возвращает ZIP; в
  `bundle.py` комплекта ровно ключи сервера, а остальной файл совпадает с
  исходным;
* комплект даёт те же ключи при разборе, которым сервер читает клиентские
  ключи, и исполняется Python (если `python3` установлен) с теми же
  `TRUSTED_KEYS`;
* однострочный словарь заменяется; упоминание `TRUSTED_KEYS` в тексте не
  принимается за объявление; файл без объявления даёт понятную ошибку.

До исправления первый тест падал ровно с той ошибкой, которую видел
администратор (500).
