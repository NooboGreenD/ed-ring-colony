# Личный кабинет: аватары (503), объединённая вкладка и создание эскадрилий

Разбор и правки: **27 сентября 2026**. Три обращения из одного письма:

1. «Картинки профиля не загружаются».
2. «При смене аватарки ошибка 503».
3. «Не создаются эскадрильи».
4. Плюс просьба: объединить «Сообщения» и «Друзья» в одну вкладку профиля.

Проверить чужую инфраструктуру из среды разработки нельзя (нет ни живого
Supabase Storage, ни production-базы), поэтому поведение закреплено тестами на
настоящих route handlers с подменённым хранилищем и базой — см. раздел 5.

---

## 1. Аватары: почему 503 и почему картинки пропали

| # | Причина | Где было | Следствие |
|---|---|---|---|
| 1 | Браузер грузил файл **напрямую** в `supabase.<домен>/storage/v1/...` | `src/app/account/page.tsx` → `client.storage.from('avatars').upload(...)` | Когда контейнер `storage` не поднят или Kong не видит живой upstream, шлюз отвечает **503 Service Unavailable**. Сайт об этом ничего не знал: `alert(error.message)` — и всё |
| 2 | Ссылки в `profiles.avatar_url` остались с прежнего хоста (`https://<ref>.supabase.co/...`) после переезда на свой сервер | база | Файлов по этим адресам больше нет → «битая» картинка у каждого пилота, зарегистрированного до переезда |
| 3 | `<img src={avatar_url}>` без обработки ошибки | ~10 мест в интерфейсе | Вместо аватара — системный значок сломанного изображения |
| 4 | Лента форума ссылалась на `/default-avatar.png`, которого нет в `public/` | `src/app/forum/page.tsx` | Гарантированный 404 у каждого автора без аватара |
| 5 | Бакет `avatars` создаётся в `DO`-блоке, который молча пропускается, если схема `storage` ещё не развёрнута | `000_base_schema.sql` | На части установок бакета просто нет → «Bucket not found» уже после починки 503 |

### Что сделано

**Загрузка идёт через сайт**: `POST /api/account/avatar` (multipart) и
`DELETE /api/account/avatar`.

```
файл → проверка (тип, размер ≤ 1 МБ, непустое тело)
     → Supabase Storage (бакет создаётся, если его нет)
     → если Storage недоступен: картинка в таблицу profile_avatars
     → profiles.avatar_url = публичный адрес ИЛИ /api/avatars/<id>?v=<хэш>
```

Ответ сообщает, куда легла картинка: `{"avatarUrl": …, "storage": "storage" |
"database", "warning": …}`. Пилот видит понятный текст вместо кода 503, а
администратор — предупреждение «Storage недоступен, аватар сохранён в базе».

**Отдача запасных копий** — `GET /api/avatars/<user_id>`: правильный
`Content-Type`, `ETag`, `Cache-Control: immutable` (версия картинки уже есть в
адресе), 304 на повторный запрос.

**Адреса чинятся при отображении** — `src/lib/avatarUrl.ts`:
`resolveAvatarUrl()` переписывает объект Storage с любого чужого хоста на
текущий `NEXT_PUBLIC_SUPABASE_URL`. Внешние аватары (Discord, Яндекс),
относительные пути и `data:` не трогаются. Строки в базе при этом не
перезаписываются: меняется только источник картинки.

**Битых картинок больше нет** — новый компонент `src/components/Avatar.tsx`
рисует инициалы на устойчивом по имени фоне, если файл не открылся.
Подключён в `CosmeticAvatar` (а значит, в досье, комментариях, ЛС,
поддержке), в меню пользователя, списках друзей, составах эскадрилий и
проектов, ленте форума.

**Миграция** `20261004000000_profile_avatars_fallback.sql`: таблица
`profile_avatars` (bytea + SHA-256 + RLS «только свою строку») и идемпотентное
создание бакета `avatars` с политиками.

### Если 503 всё-таки виден в логах

Аватар теперь сохраняется и без Storage, но саму причину стоит устранить:

```bash
docker ps --filter name=storage          # контейнер supabase-storage поднят?
docker logs --tail 50 supabase-storage   # чаще всего: нет доступа к БД или к тому /var/lib/storage
curl -s -o /dev/null -w '%{http_code}\n' https://supabase.<домен>/storage/v1/bucket \
  -H "apikey: $SERVICE_ROLE_KEY" -H "Authorization: Bearer $SERVICE_ROLE_KEY"
# 200 — жив; 503 — Kong не видит upstream (контейнер лежит/перезапускается)
```

## 2. Одна вкладка «Сообщения и друзья»

Вкладка «Сообщения» была заглушкой: «личные сообщения доступны только друзьям,
перейдите в раздел Друзья». Теперь в личном кабинете две вкладки — «Профиль» и
«Сообщения и друзья», а переписка, список друзей и заявки живут на одной
странице (`/account/friends`, компонент `FriendsPanel` с встроенным чатом).

- `/account/messages` **перенаправляет** на объединённую страницу: ссылки из
  писем, уведомлений и закладок продолжают работать.
- В меню пользователя вместо двух пунктов один, со счётчиками рядом:
  оранжевый — заявки в друзья, красный — непрочитанные сообщения.
- Значок «Сообщения: N» в шапке и уведомление о новом сообщении ведут туда же.
- Ключ перевода `account.messagesAndFriends` добавлен во все 7 языков.

## 3. Эскадрильи: почему не создавались

| # | Причина | Следствие |
|---|---|---|
| 1 | Форма `/squadrons` отправляла **пустые строки** (`tag: ""`, `power: ""`, `home_system: ""`), а схема требовала у тега 2–10 символов | Запрос отклонялся ещё до базы: **400 «Некорректные данные эскадрильи»** без указания поля. Самый частый сценарий: пилот не заполнил тег |
| 2 | Плейсхолдер подсказывал формат «Тег [TAG]», а проверка принимала только `^[A-Za-z0-9]+$` | Ввод `[RCV]` → та же ошибка 400 |
| 3 | Когда тег не приходил, в базу уходил `NULL`, а колонка объявлена `tag TEXT NOT NULL` (`000_base_schema.sql`) | Insert падал: `null value in column "tag"` → 500 |
| 4 | `created_by` ссылается на `profiles`; у аккаунта без строки профиля — нарушение внешнего ключа | 500 с текстом PostgreSQL |
| 5 | Любой отказ базы превращался в «Could not create squadron» | Ни пилот, ни поддержка не понимали причину |
| 6 | Состав создаёт триггер `on_squadron_created`; если база не обновлена, эскадрилья оставалась без командира | Созданная эскадрилья «ничья» |

### Что сделано

- `src/lib/squadronForm.ts` — чистый разбор формы: пустые строки считаются
  незаполненными полями, тег принимается в привычной записи (`[rcv]`, `r-c-v`),
  приводится к `RCV`, а если тега нет — собирается из названия
  (`Ring Colony Vanguard` → `RCV`, `Заря Колонии` → `ZK`, иначе `SQDN`).
- Ошибки возвращаются **списком по полям**: `{"error": "…", "errors": […]}` —
  интерфейс показывает все сразу, вместо одной общей фразы.
- Отказ базы переводится в подсказку: занятый тег, отсутствующая колонка
  («примените миграции»), RLS («проверьте `SUPABASE_SERVICE_ROLE_KEY`»),
  отсутствующий профиль.
- Маршрут сам создаёт строку `profiles`, если её нет, дозаписывает создателя в
  `squadron_members` (если триггера в базе нет), повторяет вставку без
  колонки, которой нет в отставшей схеме, и подставляет производный тег при
  `NOT NULL`.
- Форма: тег нормализуется прямо при вводе, кнопка блокируется на время
  запроса, показывается подсказка «если тег не указать — соберём из названия».
- Миграция `20261005000000_squadron_tag_optional.sql` снимает `NOT NULL` с
  `squadrons.tag` и добавляет индекс по `lower(tag)`.

## 4. Миграции

```bash
docker exec -i supabase-db psql -U postgres -d postgres -v ON_ERROR_STOP=1 \
  < supabase/migrations/20261004000000_profile_avatars_fallback.sql
docker exec -i supabase-db psql -U postgres -d postgres -v ON_ERROR_STOP=1 \
  < supabase/migrations/20261005000000_squadron_tag_optional.sql
```

или `UPDATE_APPLY_MIGRATIONS=1 deploy/update-project.sh`. Обе идемпотентны и
добавлены в снимок `supabase/full_schema.sql`.

Без них сайт работает: без первой не будет запасного хранилища аватаров (при
живом Storage оно и не нужно), без второй тег всё равно подставляется
приложением.

## 5. Тесты

```bash
node --test scripts/tests/avatar-url.test.mjs             # адреса аватаров, инициалы
node --test scripts/tests/squadron-form.test.mjs          # разбор формы, тексты ошибок базы
node --test scripts/tests/avatar-squadron-routes.test.mjs # настоящие маршруты со stub-Supabase
npm test                                                  # всё вместе: 683 проверки
```

Сквозной тест закрепляет: загрузку в Storage, **503 → сохранение в базе и
рабочую отдачу `/api/avatars/<id>` с 304 по ETag**, создание отсутствующего
бакета, отказы по размеру/типу, удаление аватара; а для эскадрилий —
создание при пустых полях формы, тег `[cr7]` → `CR7`, список ошибок по полям,
старую схему (`tag NOT NULL` + отсутствующая колонка), автосоздание профиля и
запрет второй эскадрильи.

Чего тесты не заменяют: настоящий Supabase Storage, поведение Kong под
нагрузкой и проверку на production-базе.
