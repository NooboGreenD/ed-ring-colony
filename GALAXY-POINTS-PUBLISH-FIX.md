# «Облако точек собрать не удалось: Service Unavailable»

Симптом из прод-инцидента: в Админка → «Каталог систем» сборка облака точек для
слоя «Все системы ⚗» падала с текстом `Service Unavailable`, и карта оставалась
без точек. Журнал сборки при этом говорил, что само облако собралось:

```
сборка облака точек: предел 1200000, бэкенд pg
облако прочитано по прямому подключению к Postgres
точек 969,102 из 201,369,102 строк (шаг 3.499601159652819e+100), файл 26.8 МБ
WARNING: загрузка файла точек не удалась: Service Unavailable
```

Заметны обе половины бага: облако есть (969k точек, 26.8 МБ — в бакет влезает),
а «сборка не удалась»; и странный «шаг» `3.5e+100` при 201 млн строк.

## Причина 1: одна ошибка хранилища перечёркивала минуты чтения каталога

`uploadPoints` вызывал `storage.upload()` ровно один раз и бросал исключение на
любой ошибке. `503 Service Unavailable` от Supabase Storage — обычное
дело на перезапуске контейнера storage, на сбросе соединения от Kong и на
таймауте промежуточного прокси; к содержимому файла он отношения не имеет.
Вызов был в конце долгой сборки, сразу после `writeCatalogStats`, и его ошибка:

- помечала сборку неудачной (`pointsBuild.ok = false`), хотя файл уже был
  собран и лежал в памяти процесса;
- не давала поставить `points_uploaded` → каждый холодный старт
  `/api/galaxy/all-systems` перечитывал каталог заново, и карта «дохла» на
  минуты;
- не оставляла никакого файла: `public/data/galaxy-systems-points.bin` пишется
  только сборкой из CLI, а в контейнере его нет.

Файл при этом было куда положить: у веб-контейнера уже смонтирован диск данных
`GALAXY_ARCHIVE_DIR` (в docker-compose — bind mount на отдельный volume).

## Причина 2: 969 102 — это не лимит, а переполнение буфера

Лимит облака (`GALAXY_POINTS_MAX`, по умолчанию 1 200 000) никем не
ограничивался сверху по размеру файла и применялся внутри `PointsBuilder` так:
буфер фиксирован, при переполнении `compact()` выбрасывает каждую вторую точку и
удваивает внутренний счётчик `stride`. Строки читались **все 201 млн**, а
буфер сжимался столько раз, сколько было нужно; «шаг» в логе печатался этим
счётчиком удвоений — отсюда `3.5e+100`. Финальные 969 102 точек — это не
«выбрано 969k», а «столько осталось после последнего сжатия».

## Что сделано

1. **Облако пишется на диск данных до любого сетевого вызова.** Новый модуль
   `src/lib/galaxyPointsPublish.ts`: `writePointsCache` (временный файл +
   `rename`, поэтому «половина облака» не читается никогда) + sidecar
   `.meta.json`; `pointsCacheInfo` читает только 12-байтный заголовок, так что
   статус админки не вычитывает 58 МБ каждые 4 секунды. Каталог —
   `GALAXY_POINTS_DIR` (по умолчанию `<GALAXY_ARCHIVE_DIR>/points`).
2. **Загрузка повторяется, но только когда повтор имеет смысл.**
   `uploadPointsToStorage`: 3 попытки, паузы 2 с / 4 с на 408/425/429/5xx и на
   сетевые ошибки (`fetch failed`, `ECONNRESET`, `socket hang up`, таймауты).
   Отказ по размеру (`413`, «size exceeds») не повторяется никогда — это
   лечится лимитом, а не сетью.
3. **Сборка больше не считается неудачной, если файл лег хотя бы куда-то.**
   `points_build.published`: `storage` | `disk` | `none`; `ok = target !== none`,
   текст ошибки storage остаётся в логе и в поле `error` как предупреждение.
   В админке появилась кнопка «Повторить загрузку в storage»
   (`POST /api/admin/galaxy` с `action: "publish-points"`) — она берёт файл из
   кэша и **не трогает таблицу**.
4. **Количество точек считается из доступного, а не из константы.**
   `POINTS_FILE_BUDGET = 60 МиБ` → `POINTS_MAX_LIMIT = 2 169 467`; потолок
   сборки = `min(GALAXY_POINTS_MAX, точки влезающие в min(file_size_limit
   бакета galaxy-data, POINTS_FILE_BUDGET))`. Лимит бакета читается из
   `storage.buckets` (`readPointsBucketLimit`) и может быть задан вручную через
   `GALAXY_POINTS_BUCKET_BYTES`. По умолчанию облако теперь **2 000 000 точек =
   58 МБ** — на каталоге 201 369 102 строки это шаг 101.
5. **Выборка делается базой, а не памятью процесса.** При прямом подключении
   читается `… WHERE mod(id, stride) = 0 ORDER BY id`, через PostgREST —
   функция `galaxy_points_sample(after_id, stride, lim)` (миграция
   `20261009000000_galaxy_points_scale.sql`). Лишние 200 млн строк не
   материализуются в Node, поэтому большой потолок — это не большая память.
6. **Статистика честная.** `points_stride` = `прочитано_строк / сохранено_точек`
   (целое, а не счётчик удвоений), рядом `points_rows`, `points_sampled`,
   `points_bytes`, `points_published`. Они пишутся даже когда storage отказал:
   раньше отсутствие записи и заставляло карту пересобирать облако каждый раз.
7. **Сетку поиска по клику переписали, иначе рост числа точек невозможен.**
   Прежняя `buildPointGrid` на 1.2 млн точек строилась 1.9 с и жрала 836 МБ, а
   на 5 млн — 9.7 с / 2.3 ГБ (таблица вед + открытая адресация). Теперь это
   CSR поверх поразрядной сортировки ключей ячеек: 1 млн точек ~0.6 с, памяти —
   сами массивы (см. `scripts/tests/galaxy-points-pick.test.mjs`).

## Как проверить

```bash
# сборка + публикация (админка или API)
curl -s -X POST https://…/api/admin/galaxy -H "authorization: Bearer $ADMIN" \
  -H 'content-type: application/json' -d '{"action":"build-points"}'
curl -s https://…/api/admin/galaxy -H "authorization: Bearer $ADMIN" | jq '.points_build | {ok, published, count, rows, stride, attempts, error}'
# {ok: true, published: "storage", count: 2000000-ish, rows: 201369102, stride: 101, attempts: 1, error: null}

# облако доступно и отдаётся
curl -sI https://…/api/galaxy/all-systems | head -3
docker exec ed-ring-colony-web-1 ls -l /app/data/spansh/points
```

Если `published: "disk"`, а в `error` что-то про `size exceeds` — файл больше
лимита бакета: накатите `20261009000000_galaxy_points_scale.sql` (поднимает
`file_size_limit` до 64 МиБ через `GREATEST`, то есть откат миграции лимит не
уменьшает) и уменьшать `GALAXY_POINTS_MAX` не нужно.

## Границы исправления

- **Self-hosted Supabase имеет ещё и глобальный `FILE_SIZE_LIMIT`** (у
  storage-сервиса по умолчанию 50 МиБ), и применяется `min(глобальный, лимит
  бакета)`. `deploy/selfhost/install.sh` ставит `FILE_SIZE_LIMIT=73400320` и
  поднимает `client_max_body_size` прокси Kong с 50m до 80m; на уже
  развёрнутых инсталляциях это нужно поправить в `.env` стека вручную, иначе
  облако останется только на диске данных.
- Дельты (`1day`/`1week`/…) облако не пересобирают — в нём равномерная выборка
  всего каталога, а не «свежие системы»; пересборка остаётся ручной кнопкой и
  полным импортом.
- `points_uploaded` по-прежнему означает «файл есть в storage» (на этот флаг
  завязан выбор «качать или собирать»), а «лежит на диске» — отдельный
  `points_published.target`.
