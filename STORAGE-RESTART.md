# Supabase Storage «отвалился»: проверка и перезапуск из админки

Storage — **отдельный стек** (`/opt/supabase`), а не сервис сайта. Обновление
проекта, миграции и пересборка `web` его не касаются: `docker compose up` идёт
в каталоге сайта, а Storage живёт в своём. Поэтому его падение сайт не роняет —
он молча перестаёт принимать файлы:

- аватары, логотипы и фоны эскадрилий уходят в резервную таблицу
  `squadron_images` (ответ API `storage: "database"`) — это резервный путь, а не
  ремонт Storage, см. [STORAGE-UPLOAD-FIX.md](STORAGE-UPLOAD-FIX.md);
- файлы, загруженные раньше **только** в Storage, перестают открываться;
- документы и вложения, для которых резервного пути нет, просто не сохраняются.

Снаружи это выглядит как «картинки не загружаются» и находится обычно по
сообщению игрока. Раньше лечение было одно: SSH на сервер и
`docker compose up -d storage`.

## Что теперь есть

### 1. Кнопка в админке

**Админка → Мониторинг → «Хранилище файлов (Supabase Storage)»**

- **«Проверить»** — только чтение: состояние контейнера `storage`, healthcheck,
  число перезапусков, признак OOM, код выхода и ответ API `GET /bucket`;
- **«Перезапустить Storage»** — запускает ту же проверку и перезапускает
  **только сервис `storage`**, и только если он действительно не работает.
  Прогресс и журнал — в блоке «Обновление проекта» (job `kind=storage`).

Проверка и перезапуск идут через приватного update-агента: у контейнера `web`
нет ни Docker-сокета, ни доступа к каталогу стека. Если агент не запущен, панель
честно пишет, что проверить Storage нельзя.

### 2. Проверка после обновления

- `deploy/update-project.sh` в конце прогона проверяет Storage и пишет в журнал
  обновления один из двух выводов: «✓ Storage работает» или «⚠ Storage не
  работает» с кнопкой, куда нажать. **Упавшая проверка не роняет удачное
  обновление** — она только читает.
- `deploy/diag-after-update.sh` (раздел 6) относит лежащий Storage к известным
  поломкам «сайт жив, а половина функций нет».
- `deploy/selfhost/upgrade.py` (обновление самого стека Supabase) останавливает
  Storage на время копии файлов и поднимает обратно. Раньше код возврата
  `docker compose up` считался доказательством успеха; теперь после подъёма
  идёт проверка состояния, и если контейнер не встал — обновление
  останавливается **до** замены контейнеров, с готовым следующим шагом.

### 3. Сторож (по умолчанию включён)

Агент раз в `STORAGE_WATCH_SECONDS` (по умолчанию 300 с) читает состояние
Storage. Если сервис **доказанно** лежит, запускается тот же job `kind=storage`:
перезапуск виден в панели и не пересекается с обновлением или бэкапом.

Что сторож не делает:

- не трогает работающий Storage (проверка read-only);
- не лечит отказ ключа (`401/403`): контейнер жив, рестарт только оборвёт
  загрузки — панель скажет проверить `SERVICE_ROLE_KEY`;
- не перезапускает, когда ответ API проверить нечем (нет `node` в образе или
  общих сетей): «не знаю» — не повод для рестарта;
- не уходит в цикл: не больше `STORAGE_WATCH_MAX_PER_HOUR` (3) попыток в час,
  затем час тишины и запись в журнал с причиной.

Выключить: `STORAGE_WATCH_SECONDS=0` в `.env.production`.

## Как проверяется, что Storage работает

`deploy/storage-repair.sh` даёт вердикт по двум независимым фактам:

1. **состояние контейнера** — `docker inspect`: `running/exited/restarting`,
   healthcheck, `RestartCount`, `OOMKilled`, код выхода;
2. **ответ API** — `GET /bucket` (нужен ключ, поэтому ключ читается из `.env`
   стека в память и никогда не печатается). Проверка идёт **изнутри контейнера
   Storage** через `docker exec … node`:
   - не зависит от того, подключён ли агент к docker-сети Supabase;
   - не требует публичного адреса, TLS, nginx и Kong;
   - если `node` в образе нет или он старше 18 (`fetch` отсутствует) — честный
     `unknown`, а не ложное «сломано».

Переменная `STORAGE_INTERNAL_URL` (например `http://storage:5000`) включает
дополнительную проверку из контейнера агента — только если агента сознательно
подключили к сети Supabase (`deploy/compose.supabase-net.yml`).

Коды ответа: `2xx` — работает; `401/403` — работает, но ключ не принят;
`000`/`5xx` — не отвечает.

## Ручной запуск на хосте

```bash
# только проверка (ничего не меняет), код 0 — работает, 1 — поломка, 2 — нет docker
sudo bash deploy/storage-repair.sh

# проверка и, если надо, перезапуск только сервиса storage
sudo bash deploy/storage-repair.sh --restart
```

Скрипт не удаляет тома и бакеты, не делает `docker compose down`, не меняет
`.env`, не трогает `chmod` на `/var/lib/storage`, не перезапускает `db`, `auth`,
`kong` и `imgproxy`. Существующий контейнер перезапускается через
`docker restart` (дубль создать нельзя); `compose up -d --no-deps storage`
используется только если контейнера нет вовсе — с тем же проектом и теми же
compose-файлами, которыми стек запускали.

## Настройки агента

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `STORAGE_CONTAINER` | `supabase-storage` | имя контейнера Storage |
| `STORAGE_SERVICE` | `storage` | имя сервиса в compose стека |
| `STORAGE_INTERNAL_URL` | пусто | адрес API из контейнера агента (нужна общая сеть) |
| `STORAGE_WAIT_SECONDS` | `90` | сколько ждать готовности после рестарта |
| `STORAGE_TIMEOUT_MINUTES` | `10` | предел времени задачи |
| `STORAGE_WATCH_SECONDS` | `300` | период сторожа, `0` — выключить |
| `STORAGE_WATCH_MAX_PER_HOUR` | `3` | предел перезапусков в час |
| `STORAGE_REPAIR_SCRIPT` | `<клон>/deploy/storage-repair.sh` | путь к скрипту |

## Если Storage не поднимается

Причина почти всегда одна из четырёх, и скрипт говорит, какая:

| Признак в панели | Что смотреть |
|---|---|
| `убит OOM` | мало памяти: `docker stats`, лимит контейнера, соседние сервисы |
| `остановлен (код N)` и сразу падает снова | `docker logs supabase-storage` — обычно нет места (`df -h`, `df -i`) или права на том `/var/lib/storage` |
| `healthcheck не проходит`, API не отвечает | база: доступность `supabase-db`, пароль роли `supabase_storage_admin`, внутренние миграции Storage |
| `ключ не принят (401/403)` | `SERVICE_ROLE_KEY` в `.env` стека разошёлся с ключом сайта — сверьте ключи, перезапуск не поможет |

Порядок ручного разбора — в [STORAGE-UPLOAD-FIX.md](STORAGE-UPLOAD-FIX.md),
раздел «Failed to retrieve buckets». Полная диагностика без перезапуска —
`sudo python3 deploy/selfhost/storage-check.py` (читает контейнеры, Kong и ключ
Studio, ничего не меняет).

## Проверки

```bash
node --test scripts/tests/storage-repair.test.mjs
node --test scripts/tests/update-agent.test.mjs scripts/tests/env-route.test.mjs
npm run test:quick
npm run typecheck
```

Тесты гоняют настоящий `deploy/storage-repair.sh` на подставном `docker`:
здоровый сервис не перезапускается, упавший — перезапускается, отказ ключа
рестартом не лечится, журнал не печатает пароль из `DATABASE_URL`, а этапы
скрипта совпадают со `STORAGE_STAGES` панели. Отдельно проверяются агент
(`GET /storage`, `POST /storage/restart`, 409 при занятом слоте) и сторож
(живой сервис, отказ ключа, лимит попыток).

Это не заменяет проверку живого сервера: реальный Storage в песочнице не
запускается.
