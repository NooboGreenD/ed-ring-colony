# Аудит SQL-миграций — 2026-09-25

Проверены все SQL-файлы репозитория (55 миграций `supabase/migrations/*.sql`,
`supabase/maintenance/*.sql`, `supabase/full_schema.sql`, `migrations/*.sql`).

Чем проверяли:

1. **Настоящий парсер PostgreSQL** (libpg_query 18 — то же ядро, что разбирает
   запросы на сервере): файл целиком, тела `DO` как plpgsql, тела функций в
   `$fn$`.
2. **Настоящий сервер PostgreSQL 16**: база поднималась с нуля и миграции
   накатывались по одной в том же порядке, что и `deploy/update-project.sh`
   (`supabase/migrations/*.sql` по алфавиту, `psql -v ON_ERROR_STOP=1`), в
   окружении, похожем на Supabase (роли `anon/authenticated/service_role`,
   схемы `auth`/`storage`, `auth.uid()`, публикация `supabase_realtime`,
   пользователь-администратор).
3. **Тесты репозитория**: `node --test scripts/tests/migrations-sql.test.mjs`
   (усилены, см. последний раздел).

## 1. Главное: `20260903000000_wiki_fill_empty_categories.sql` — файл убивал обновление

Файл был сохранён **одной строкой без единого перевода строки** (12 598 байт,
0 символов `\n`). Из-за этого:

* первый же комментарий (`-- ====…`, 12-й байт после начала) превращал в
  комментарий **весь остаток файла вместе с блоком `DO $seed$ … $seed$;`**;
* при попытке выполнить `DO` сервер отвечал
  `ERROR: 42601: syntax error at end of input` — блок `BEGIN` никогда не
  закрывался, потому что `END $seed$;` тоже был «съеден» комментарием;
* `deploy/update-project.sh` накатывает миграции с `ON_ERROR_STOP=1` и на первой
  же ошибке делает `die "миграция … завершилась с ошибкой — код сайта ещё не
  переключался"`, то есть **кнопка «Обновить сейчас» падала бы на этом файле**
  (он не отмечен в `migrations.mark`, значит попадает в список неприменённых);
* вдобавок в текстах статей вместо переводов строк стояли маркеры `$nl$`
  (159 штук) — их никто не разворачивал, поэтому даже успешный накат положил бы
  в базу одну строку с литералами `$nl$` вместо Markdown.

### Что исправлено

| Было | Стало |
|---|---|
| одна строка, комментарий съедает весь файл | нормальная структура: комментарии на своих строках, `DO/INSERT/END` целы |
| `$nl$` внутри `$c$…$c$` | реальные переводы строк (текст статей побайтово совпадает с исходным после разворота маркеров) |
| `INSERT … RETURNING id INTO v_article_id` | `ON CONFLICT (slug) DO NOTHING` + ревизия только если строка вставилась — повторный накат больше не падает на `duplicate key value` |
| `category_id` хардкодом `448d06b4-…` | категория ищется по этому id, затем по slug `guides`, и лишь при отсутствии создаётся (в базе, поднятой `20260901000000_wiki.sql`, id категорий другие — они генерируются `gen_random_uuid()`) |
| автор хардкодом `d0680fc1-…` | тот же пользователь, но если его нет — берётся первый `admin/moderator` из `profiles`; если автора нет вообще (установка с нуля), сид пропускается с `NOTICE` вместо падения FK |

Содержимое статей не менялось: 3 статьи категории «Гайды»
(`pervye-shagi-novichka`, `bystryj-zarabotok-kreditov`,
`gayd-po-otkrytiyu-inzhenerov`), `is_featured` первой статьи сохранён (`true`),
ревизии — по одной на статью с `change_summary = 'Initial seed'`.

### Проверка на живом PostgreSQL

| Сценарий | Результат |
|---|---|
| Свежая база, миграции по порядку | 3 статьи в категории `guides`, 3 ревизии, контент многострочный, `$nl$` нет |
| База, где категория «Гайды» имеет «историчный» id `448d06b4-…` | статьи легли в неё (замысел автора сохранён) |
| Повторный накат того же файла | дублей и ошибок нет (3 статьи, 3 ревизии) |
| База без пользователя-автора | `NOTICE … нет пользователя-автора — сид пропущен`, ошибок нет |
| Сверка текстов с исходным файлом | контент совпадает побайтово (2 147 / 2 024 / 2 296 байт) |

`supabase/full_schema.sql` — автосборка из миграций (`supabase/DATABASE.md`),
поэтому исправленный блок продублирован и туда: на чистой базе через psql
(`-v ON_ERROR_STOP=0`, как в `deploy/selfhost/install.sh`) файл выполняется без
ошибок, сид пропускается с `NOTICE` (админа ещё нет) — и наполняет вики, как
только администратор зарегистрирован и файл запущен повторно (он идемпотентен).

## 4. Настоящие ошибки, не связанные с форматом

Найдены прогоном на живом PostgreSQL (окружение Supabase-подобное, свежая база).
В списке — только то, что падает **само**, без каскада от предыдущих файлов:

| Файл | Ошибка | Причина |
|---|---|---|
| `001_rls_policies.sql` | `42703 column "requester_id" does not exist` | политики для `public.friends` написаны под колонки `requester_id`/`addressee_id`, а таблица в `000_base_schema.sql` (и в политиках `20260830102924_rls_policies.sql`) объявлена как `user_id`/`friend_id`; там же индекс `idx_friends_requester ON public.friends(requester_id)` |
| `20260830110258_rls_policies_v2.sql` | то же самое | почти копия предыдущего файла (10 и 2 совпадения) |
| `20260915000000_galnet_translations.sql` | `42P01 relation "public.galnet_news" does not exist` | каскад от пустого `20260830152500_galnet_news.sql` |
| `20260924010000_reconcile_galnet_news_structure.sql` | то же | каскад от того же файла |

Что важно понимать про `friends`: правка «в лоб» на `user_id`/`friend_id`
соответствует схеме **этого** репозитория, но если в вашей рабочей базе таблица
всё-таки с `requester_id`, поменять надо наоборот — сначала стоит посмотреть
фактическую схему:

```sql
select column_name from information_schema.columns
 where table_schema='public' and table_name='friends';
```

Ещё мелочи:

* **Дубль версии миграции**: `20260925000000_galaxy_systems_scale.sql` и
  `20260925000000_yandex_identities.sql`. Скрипт обновления раскладывает файлы
  по алфавиту и переживёт это, а вот `supabase` CLI и любые трекеры миграций по
  версии — нет.
* `migrations/add_site_content_translations.sql` (каталог в корне) и
  `supabase/add_site_content_translations.sql` — исторические копии, их
  содержимое уже покрыто `20260920000000_site_content_translations.sql`.
  Скрипт обновления каталог `migrations/` не читает, так что это просто хлам.
* `scripts/tests/migrations-sql.test.mjs` **не ловил** этот класс поломок:
  тела `DO` с внутренними `$…$`-кавычками (а это ровно все wiki-сиды) из
  проверки исключались. Доказательство: на исходном сломанном файле тест
  проходил `9/9 pass`.

## 5. Что усилено в тестах

`scripts/tests/migrations-sql.test.mjs`:

1. **Тела `DO` проверяются целиком**, включая сиды wiki: внутренние
   `$c$…$c$` маскируются коротким строковым литералом (содержимое статей для
   plpgsql-разбора не важно), поэтому обёртка в отдельный тег больше не
   «спотыкается». На исходном сломанном файле тест падает с
   `DO 1: syntax error at end of input` — то есть регрессия теперь ловится.
2. **`ни один комментарий не съедает код`**: сканер находит токены
   `SQL_COMMENT` длиннее 400 символов (самый длинный честный комментарий в
   дереве — 228 символов). Так ловятся файлы, сохранённые одной строкой.
3. **`каждая миграция содержит хотя бы одну команду`**: пустой файл больше не
   пройдёт молча. Файлы, которые и должны ничего не делать, перечислены в
   `KNOWN_DEAD` с причиной; починенные файлы надо из этого списка убрать (тест
   напомнит).

Ни один файл из `KNOWN_DEAD` самим тестом не «лечится» — это осознанный
список долга, чтобы новые поломки ловились сразу.
