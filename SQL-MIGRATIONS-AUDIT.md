`supabase/maintenance/*.sql`, `supabase/full_schema.sql`, `migrations/*.sql`.

Чем проверяли:

   `auth.uid()`, публикация `supabase_realtime`).
3. **Тесты репозитория**: `node --test scripts/tests/migrations-sql.test.mjs`

## 3. Что усилено в тестах

`scripts/tests/migrations-sql.test.mjs`:

1. **Тела `DO` проверяются целиком**, включая сиды wiki: внутренние
   `$c$…$c$` маскируются коротким строковым литералом. Раньше такие тела из
   проверки исключались, поэтому на сломанном файле тест давал `9/9 pass`.
2. **`ни один комментарий не съедает код`** — сканер ищет токены `SQL_COMMENT`
   длиннее 400 символов (самый длинный честный комментарий в дереве — 228).
3. **`каждая миграция содержит хотя бы одну команду`** — пустой файл больше не
   проходит молча; исключений нет, шаблон для SQL Editor переехал в
   `supabase/templates/`.
4. **`в текстах статей не осталось маркеров $nl$`** — проверяются токены вне
   комментариев, чтобы прежний способ хранения переводов строк не вернулся.

## 4. Что стоит знать про базы, где эти миграции уже «применены»

* Скрипт обновления отмечает миграцию применённой в
  `update-state/migrations.mark` **по имени файла**. Переименованный
  `20260925010000_yandex_identities.sql` в старых базах не отмечен и будет
  применён повторно — это безопасно, файл идемпотентен
  (`CREATE TABLE IF NOT EXISTS`, `DROP POLICY IF EXISTS`, `CREATE INDEX
  IF NOT EXISTS`).
* Файлы `20260903000000`, `20260903010000`, `20260903020000`,
  `20260830152500`, `20260904100000` перезаписываются новыми версиями, но
  остаются под теми же именами: если они уже отмечены применёнными, повторный
  накат не произойдёт. Если нужно добрать контент/таблицы на рабочей базе —
  примените их вручную (или удалите строки из `migrations.mark`):
  ```bash
  docker exec -i supabase-db psql -U postgres -d postgres -v ON_ERROR_STOP=1 \
    < supabase/migrations/20260903010000_wiki_update_colonization.sql
  ```
  Все восстановленные файлы идемпотентны, повторный запуск ничего не сломает.
* Миграции серии `20260904*` (capi/eddn/fleet carriers) и `20260921*`
  **не** идемпотентны (`CREATE TABLE` без `IF NOT EXISTS`): повторный накат
  всего набора на уже развёрнутой базе даст «already exists». Это ожидаемое
  поведение — обновление применяет только неотмеченные файлы.

## 5. Осталось на будущее (не блокирует обновление)

1. **`GRANT INSERT` + политика `WITH CHECK (true)` на `galnet_sync_log` для
   `anon`** — писать в лог может любой посетитель сайта. Логику синка это не

   `route_systems.sql`) и `supabase/add_site_content_translations.sql`: их
   содержимое уже в `20260920000000_site_content_translations.sql`, каталог
   `migrations/` скриптом обновления не читается. Оставлены «для справки»
   (см. `supabase/DATABASE.md`) — можно удалить.
3. **`supabase/full_schema.sql` нужно пересобирать после новых миграций**
   (команда в `supabase/DATABASE.md`). Проверка «сколько блоков в снимке против
   `migrations/`» была бы полезным тестом — сейчас это ловится только глазами.
4. **`friends`**: RLS теперь работает, но у приложения нет ни одной страницы
   или API, использующих эту таблицу (`grep from('friends')` пусто) — если
   функциональность не планируется, таблицу и политики можно удалить.

## 6. Воспроизведение проверок

```bash
# 1. Разбор парсером PostgreSQL (нужен devDependency libpg-query)
npm test -- --test-name-pattern='SQL'

# 2. Накат на живую базу: поднять PostgreSQL 16, создать роли/auth/storage,
#    затем по каждому файлу (как deploy/selfhost/install.sh)
for f in supabase/migrations/*.sql; do
  psql "$DB_URL" -q -v ON_ERROR_STOP=0 -f "$f"
done

# 3. Снимок целиком
psql "$DB_URL" -q -v ON_ERROR_STOP=0 -f supabase/full_schema.sql

# 4. Что должно получиться
psql "$DB_URL" -c "select c.slug, count(*) from public.wiki_articles a
                   join public.wiki_categories c on c.id = a.category_id group by 1 order by 1"
# colonization | 3   (гайд v2.0 + 2 статьи)
# guides       | 3
# lore         | 5
# exobiology   | 13
```
