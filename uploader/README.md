# Colonial Helper

Standalone desktop uploader for **ED Ring Colony** — https://edringcolony.ru.

## Версия 2.10.25 — собственный сервер

API по умолчанию — `https://edringcolony.ru/api`, **не** адрес Supabase.
На вкладке подключения можно открыть страницу API-токенов или сменить сервер
(с перезапуском; старый токен на новый сервер не передаётся). При переезде
сохранённый токен работает, если перенесены `api_tokens` и UUID пользователей;
иначе создайте новый на `https://edringcolony.ru/account?tab=tokens`.

Кэш импортов/offsets теперь связан с сервером и аккаунтом. После обновления
возможна однократная повторная сверка истории. GitHub Releases остаётся каналом
обновлений. Подробности для администратора — [POST-MIGRATION.md](../POST-MIGRATION.md).


## Что делает

- Загружает журналы Elite Dangerous на сайт
- Отслеживает маршрут полёта (NavRoute.json / CSV)
- **Live-watcher**: автоматически читает новые строки из Journal.*.log
- **Инфографика пилота**: отдельная вкладка с крупными показателями (тонны, доставки, груз, системы) и плитками — динамика сессии со спарклайном, состояние корабля, маршрут, топ систем по тоннам, статус и подключения, журналы и экономика
  - адаптивная сетка (1–3 колонки, в компактном режиме до 4) и компактный режим
  - графики на чистом `tk.Canvas`, обновление раз в секунду, без сетевых запросов
- **Колонизатор**: проекты Raven Colonial прямо из приложения — список своих
  проектов, назначение основного, завершение стройки и создание нового проекта
  с автозаполнением из журнала (после создания открывается страница проекта)
  - **«Сверить стройплощадку с Raven»**: сколько осталось завезти по данным
    Raven Colonial (там учтён и груз других командиров) против того, что завезли
    вы по журналу и что это приложение реально отправило; недосланное
    предлагается дослать
  - **«Привязать площадку к проекту»**: если сопоставить площадку с проектом
    автоматически нельзя (в системе несколько строек или `marketId` проекта
    отличается от журнального), тонны зачисляются выбранному проекту
  - доставки на стройплощадку уходят в Raven Colonial отдельной очередью и не
    теряются при сбое сайта или перезапуске: отправленное запоминается, повтор
    тоннаж проекту не завышает
- **Карта системы**: вкладка со схемой системы, в которой находится пилот —
  звезда, планеты и луны, станции, поселения, авианосцы и стройплощадки
  - у строящихся объектов **прогресс-бар с процентом завезённого груза**
    (журнал + Raven Colonial, поэтому виден и груз других командиров) и остаток
    в тоннах
  - планы площадок из Raven Colonial: чего в системе ещё нет, но задумано
  - отметка «Вы здесь», список объектов с синхронным выбором, зум, открытие
    проекта в Raven Colonial по Ctrl+двойному клику, Esc сбрасывает центр
  - режим **«Карточки системы»**: карточки тел с фактами и постройками внутри;
    клик наводит камеру, колесо приближает, Esc/«Все тела» снимают фокус
  - наземные постройки рисуются на поверхности своего тела (не в пустоте),
    иконки строек и станций маленькие, подписи гасятся в плотных системах
  - раскладка общая с сайтом: `orrery.py` ↔ `src/lib/systemOrrery.ts`
- **HUD Overlay**: плавающие окна поверх Elite Dangerous
  - Блоки: ROUTE, STATUS, SHIP, CARGO, SESSION, EVENTS, EXOBIO, CARRIER
  - EXOBIO — компактная таблица (образцы, предсказания родов с процентами и
    видами, тела, планеты); при моноширинном шрифте колонки ровные, иначе
    автоматический откат к списку
  - Настройки каждого блока: показ, блокировка позиции, клик-сквозь, своя прозрачность, свой размер шрифта, пресет размера (XS…XL), правило автопоказа, горячая клавиша, сброс
  - Поведение: клик-сквозь (мышь работает в игре), показ блоков по ситуации (станция, полёт, SRV, пешком, груз, биосигналы, маршрут), автоскрытие при простое
  - Раскладка: якоря, отступы, профили (хранят и вид, и поведение блоков)
  - Системные горячие клавиши (F1…F12, Windows) — работают, когда в фокусе игра
  - Всё применяется к живым окнам, без перезапуска оверлея

## Использование

1. Введите API токен (из профиля на сайте)
2. Укажите папку журналов Elite Dangerous
3. Загрузите логи вручную или включите Watcher
4. На вкладке **Колонизатор** задайте ключ RCC — там же список проектов и
   создание нового (форма заполнится из журнала при посадке на стройплощадку).
   Кнопка **«Сверить стройплощадку с Raven»** показывает остаток потребности и
   досылает то, что не ушло в Raven Colonial
5. На вкладке **Карта системы** смотрите систему, в которой находитесь: тела,
   станции, авианосцы и стройплощадки с процентом завезённого груза. Двойной
   клик по объекту центрирует карту, Ctrl+двойной открывает проект стройки
   в Raven Colonial, Esc возвращает звезду в центр
6. Во вкладке **Оверлей** настройте HUD и включите его
7. На вкладке **Оверлей** настройте раскладку (якоря, отступы, профили)
8. Играйте в Borderless Windowed — оверлей будет поверх игры

## Версия 2.10.23 — SHIP-оверлей: живые статусы вместо правдоподобных чисел

* **Прочность модулей и корпуса в live-режиме.** `ship_tracker` разбирает события
  по документированным полям: `ModuleInfo` из `Slots` (а не только из `Modules`),
  `Repair.Item` (не `Module`), `AfmuRepairs` по локализационному id, список слотов
  в `RebootRepair`, `HullDamage` только своего корабля (не истребителя и не NPC),
  `RepairDrone`, `Synthesis` «Repair», `JetConeDamage`, `CockpitBreached`,
  `SystemsShutdown`, `AmmoUsed`/`BuyAmmo`, `RefuelAll` (кредиты больше не тонны).
* **Чего журнал не отдаёт — в HUD нет.** Процента щитов в `Status.json` не
  существует → строка «ЩИТЫ упали / вверху / нет генератора» без шкалы; величина
  урона из `JetConeDamage` неизвестна → жёлтый `?` вместо выдуманных −20 %;
  прочность целых модулей известна только по снимку → `*` и сноска об этом.
  Рядом с корпусом — возраст и источник значения: `67 % (2м · попадание)`.
* **Модель отдельно от Tk:** `uploader/ship_hud.py` (`build_ship_hud` →
  `hud_rows` → `render_hud_text`). Оверлей печатает ровно то, что посчитала
  модель, поэтому тесты проверяют настоящий экран, а не его пересказ.
* **Компактность:** 360×420 с плашками → 360×330, 14 строк, самая длинная —
  39 символов. `line_budget()` считает бюджет строки по ширине блока и кеглю:
  составные строки режутся по границам показателей, шкала укорачивается,
  подпись уходит следом — переноса, съедающего высоту, больше нет.
* **Новая настройка «Список модулей в SHIP»** — «только важные» (повреждённые,
  выключенные, ключевые системы, остальное в «ещё N»), «все», «только итог».
  Применяется без пересоздания окна; снятая галочка «Модули» как и раньше прячет всё.
* **Мерцание:** при неизменной подписи HUD виджеты не трогаются вовсе, лишние
  строки скрываются, а не удаляются; шрифт и режим списка перекрашивают строки
  на месте.
* **Файлы состояния больше не разбираются второй раз:** `Status.json` и
  `ModulesInfo.json` идут через тот же парсер, что и события журнала, с флагом
  «снимок может быть устарел» (он умеет только ухудшать прочность, но не чинить).
* Миграция настроек `3 → 4`: у тех, кто не менял размер блока, высота 420 → 330.

## Версия 2.10.22 — тело в 3D выглядит сферой, а не блином

* **Причина блина — не геометрия, а box сцены.** `layout.scene.aspectmode = "data"`
  подбирал рамку по габаритам данных: у почти плоской системы z-ось сжималась, и вместе
  с орбитами сплющивались сферы тел. Карта (приложение и сайт) перешла на
  `aspectmode: "manual"` + `aspectratio {1,1,1}` (`orrery.scene_aspect()`,
  `sceneAspect()` в движке сайта) — при равных кубических размахах осей и
  ортографической камере силуэт тела остаётся кругом с любого ракурса.
* **Материал тела** (`orrery.SPHERE_MATERIAL`, он же на сайте): `opacity 1` вместо
  0.92 (полупрозрачный пузырь показывал задние грани) и свет `ambient 0.3 /
  diffuse 0.85 / specular 0.4 / roughness 0.6 / fresnel 0.55` с косым
  `lightposition` — появилась объёмная терминатор-граница вместо плоского пятна.
* **Сетка одна на все зумы**: `SPHERE_MESH = 40×24` (`orrery.sphere_mesh()`), она же
  приходит в JS экспорта (`const SPHERE_MESH`), потому что `mesh3d.i/j/k` статичны —
  перекладывать вершины другим числом нельзя. Дымка атмосферы — отдельная оболочка
  мельче (×0.8) на `radius × SPHERE_HAZE_SCALE (1.06)` с `opacity 0.35`.
* **Постройки на поверхности** подняты на `radius × SPHERE_SURFACE_LIFT (1.03)` —
  один коэффициент вместо трёх литералов в Python, TypeScript и JS экспорта.

## Версия 2.10.21 — 3D-карта: камера, в которой всё видно

* **Фокус больше не уводит камеру в чёрный экран.** `camera.center` Plotly
  считает в нормализованных единицах сцены (1 = половина разреза окна), а в
  карту попадала координата цели в unit'ах системы (вроде 110.6) — вид улетал
  в пустоту. Теперь центр окна задают размахи осей, а камера всегда смотрит в 0
  (`orrery.scene_camera` на стороне приложения, `sceneCamera` в движке сайта).
* **Вся система влезает в поле.** Рамки обзора = куб по габариту реально
  нарисованных точек (`orrery.trace_extent`, `traceExtent` на сайте), а не по
  бюджету раскладки: раньше внешние орбиты, кольца и зоны обитаемости
  обрезались краем поля.
* **Проекция ортографическая** и |eye| = 1.35 — перспектива с коротким «глазом»
  срезала края сцены, а на уровне «поверхность» камера оказывалась внутри сферы
  тела (тот же чёрный экран). Кнопка «🎥 Перспектива» возвращает глубину по
  желанию; «🧭 Сверху (2D)» и «📐 Сбоку» — те же направления камеры.
* **Маркер лежит на своей орбите.** Эллипс с реальным эксцентриситетом теперь
  строится с полуосью, подобранной так, чтобы он проходил через точку
  раскладки (`_orbit_scale`): раньше тело съезжало с нарисованной орбиты на
  ~e·a, и окно фокуса центрировалось не на нём.
* **На сайте** те же исправления: `sceneCamera(viewMode)`, `focusWindow` /
  `overviewWindow` и кнопки вида «🔭 3D / 🧭 сверху / 📐 сбоку» в панели карты.
* **CI-совместимость:** layout фигуры использует только валидные ключи Plotly
  (`scene.camera.projection`, а не несуществующий `scene.projection`) —
  `go.Figure` валидирует layout строго и ронял сборку EXE; за это отвечает
  тест `test_scene_layout_uses_only_valid_plotly_keys`.

## Версия 2.10.20 — Plotly-карта приложения = 3D-карта сайта

* **Карта, открываемая кнопкой «Plotly 3D 🌐», больше не бывает плоской.**
  Фигура всегда собирается как 3D-сцена (`scatter3d` + `layout.scene`) — ровно
  так же, как `SystemPlotlyMap` на сайте. Раньше режим `2d` строил обычные
  `scatter`-трассы без `scene`, а все кнопки вида пишут в `scene.camera`,
  поэтому в открытой карте переключать было нечего: «работает только 2D».
* **Вид — это камера, а не другой рендер.** «🧭 Сверху (2D)» = ортографическая
  проекция сверху, «🔭 3D Orrery» = перспектива, «📐 Сбоку» = профиль. Кнопки
  Plotly работают и в сохранённом HTML, плюс в шапке карты появилась своя
  кнопка «🔭 3D / 🧭 2D сверху» — она перекладывает камеру и проекцию.
* **Настройка `map_plotly_view`** в `config.json`: `"3d"` (по умолчанию) или
  `"2d"` — с какой камеры открывать. Переключатель «Вид (канвас)» 2D/3D на
  вкладке карты на Plotly больше не влияет: он про холст Tk.
* **Сфера тела в фокусе.** На уровнях «окрестности» и «поверхность» цель
  получает `mesh3d`-сферу (сетка 24×14, как на сайте) и полупрозрачную дымку
  атмосферы; наземные постройки ставятся на видимую поверхность сферы — в
  статичной фигуре через `place_stations(..., sphere_radii=...)`, при зуме в
  браузере через `refreshSphere()` и `structurePositions()`. Стартовая камера
  3D совпадает со сайт-формулой `eye = (e·0.62, −e·0.62, e·0.4)` при `e = 1.65`,
  а рамка сцены (сетка, деления, фон `#07090e`) выглядит так же, как на сайте.
* **Паритет закреп тестами:** `uploader/tests/test_plotly_map.py` и
  `test_plotly_map_cards.py` проверяют, что `view_mode` меняет только камеру,
  что 2D-трасс в карте нет ни в одном режиме, что сетка сферы совпадает с
  сайтом и что Tk-переключатель канваса не укладывает карту в плоскость.

## Версия 2.10.19 — карта как на сайте, EXOBIO таблицей, поставки с признаком стройки

* **Общий движок раскладки `orrery.py`.** Расположение звёзд, планет, лун,
  колец, зон обитаемости и привязка построек к телам считаются одной чистой
  функцией (`plan_system`, `place_stations`, `focus_view`, `neighbours_of`), у
  которой есть зеркало на сайте — `src/lib/systemOrrery.ts`. Поэтому карта
  приложения и 3D-карта системы на сайте показывают одну и ту же геометрию,
  а не «похожую».
* **Наземные постройки стоят на поверхности тела, а не висят в космосе.** В
  2D и 3D станции и поселения (planetaryInstallation) поднимаются на радиус
  тела + подъём в пикселях, пересчитываемый из текущего масштаба
  (`_station_lift_px`): при зуме постройка остаётся на теле, а не улетает от
  него. В экспортированном HTML то же самое делает JS
  (`structurePositions()`), потому что зум там меняет пользователь.
* **Карта системы: режим «Карточки системы».** На панели появляется боковой
  список карточек тел (класс, дистанция, радиус, g, температура, атмосфера,
  вулканизм, биосигналы, кольца, «первооткрыватель») и внутри каждой карточки
  — постройки этого тела с прогрессом завезённого. Клик по карточке наводит
  камеру (`focus_view`), колесо мыши над списком приближает, кнопка «Все тела»
  снимает фокус. Тот же ряд карточек попадает в экспортированный Plotly-HTML
  и в 3D-карту сайта, так что данные в карточке и на холсте всегда одинаковые.
* **Иконки стройплощадок и станций уменьшены** (5.5/5.0 px вместо крупных
  маркеров, 9 px подпись) и подписи гасятся в плотных системах: в системе с
  десятками звёзд и сотнями тел карта остаётся читаемой. Подпись включается
  для выбранного объекта, на максимальном зуме и по «все подписи».
* **Оверлей EXOBIO умеет табличную раскладку** (по умолчанию): образцы,
  предсказания родов, тела и планеты выводятся колонками в
  равноширинном шрифте вместо «текстовых простыней»; при недоступном
  моноширинном шрифте происходит откат к прежнему списку, а ширина колонок
  считается по реальной ширине окна. Туда же переехала и оценка стоимости
  образца.
* **Предсказание родов органики пересобрано по игровым данным.** Правила
  `GENUS_RULES` учитывают категорию атмосферы, конкретные газы, класс тела,
  вулканизм и окна температуры/гравитации: жёстко тело отсекается по атмосфере,
  газам, классу и («вулканизм обязателен» при известном его отсутствии),
  остальное снижает процент. В списке только кандидаты с
  вероятностью ≥ 25 %, рядом — подходящие виды рода и цена. Исправлены
  имена родов из журнала (`Shards` → `Crystalline Shards`, `Tubers` →
  `Sinuous Tubers`, `Concha` → `Conchas`): раньше из-за этого имена в
  предсказании и цены в справочнике не совпадали.
* **Парсер журнала помечает, куда именно ушёл груз.** Каждая доставка едет на
  сайт с `source` и `is_construction`: `ColonisationContribution` и
  `CargoDepot` — стройка; дифференциальная потеря `Cargo` — стройка только у
  рынка, про который журнал показывал `ColonisationConstructionDepot`;
  `MarketSell` на авианосце — перевозка. Из этого поля на сайте растут два
  разных блока досье: «весь перевозимый груз» и «тоннаж на стройплощадки».
  `PARSER_VERSION` поднят до 3, поэтому старые журналы пере-импортируются и
  получают признак, а не остаются без него.
* Тесты: **990** (`uploader/tests/`, включая `test_orrery_layout.py` — 19,
  `test_plotly_map_cards.py` — 15, `test_journal_transport_scope.py` — 11,
  `test_exobio_overlay.py`, `test_map_tab.py`, `test_plotly_map.py`).

временный сбой повторяется до 3 раз — события не теряются, а лог не забивается
одинаковыми строками (в лог идёт первая неудача, затем каждая 25-я, и одна строка
о восстановлении).

## Версия 2.5.1 — устранено зависание при включении оверлея

Программа намертво висла сразу после включения оверлея: клик ни по главному
окну, ни по оверлею не помогал. Причина — дедлок между главным потоком Tk и
фоновым потоком оверлея. `GameMonitor` опрашивал Windows (перебор всех окон +
чтение заголовков) **под своей блокировкой**, а среди перебираемых окон были
наши собственные: `GetWindowTextW` для окна своего процесса ждёт ответа
потока Tk, а поток Tk в это время ждал ту же блокировку. Оба потока вставали
навсегда.

Теперь опрос идёт вне блокировки (второй поток не ждёт его, а берёт последний
снимок), свои окна пропускаются по PID до чтения заголовка, а дублирующий
перебор окон в `overlay._get_ed_hwnd()` удалён.

## Версия 2.4.1 — оверлей больше не зависает по клику

Клик по кнопке `*` в шапке блока оверлея открывал меню, после чего программа
переставала отвечать на клики: меню создавалось локальной переменной и
показывалось через `Menu.post()`, который (в отличие от `tk_popup()`) не
снимает граббер мыши. К моменту возврата из метода виджет уничтожался, граббер
оставался на несуществующем окне, и мышь переставала доходить до любого окна.

Теперь меню живёт в атрибутах блока, повторный клик снимает предыдущее, показ
идёт через `tk_popup()`, а `destroy()` окна отпускает меню до закрытия.

## Версия 2.1.0 — быстрая первичная загрузка

Первичная загрузка всей истории журналов с подключёнными API (EDSM / Inara /
Raven Colonial) раньше могла идти часы: каждое событие журнала уходило во
внешние сервисы синхронным HTTP-запросом из потока загрузки. За 800 файлов
истории это больше 100 тысяч запросов.

Что изменилось:

- внешние сервисы получают только **live**-события watcher'а; история по
  умолчанию не отправляется в EDSM/Inara/Raven (включается галочкой на
  вкладке «Загрузка логов»);
- все отправки идут через фоновый диспетчер с ограниченной очередью — разбор
  журнала никогда не ждёт сеть (`uploader/event_dispatch.py`);
- каждый файл разбирается **один раз** (доставки, snapshots стройки, трекинг
  корабля и внешние API идут одним проходом);
- одинаковые подряд идущие `ColonisationConstructionDepot` отбрасываются —
  в реальном журнале их тысячи, а меняется состояние в разы реже;
- доставки уходят на сайт параллельными пачками по 100 (было: по 25
  последовательно), snapshots — по 100 параллельно;
- первичная сверка копит данные и отправляет их **одним пакетом** в конце, а
  не отдельным запросом на каждый файл;
- кэш уже загруженных файлов (`.colonial_helper_imported_files.json`):
  повторный импорт тех же файлов занимает секунды. Сбросить его можно кнопкой
  «Сбросить кэш импорта».

Замер на 800 файлах / 21 МБ: **~6,8 часа → около минуты**, повторный импорт —
около нуля. Подробности — в `CHANGES.md` (раунд 10).

## Версия 2.0.0 и загрузка Journal

Uploader 2.0 использует идемпотентную обработку Journal-файлов с сохранением
byte-offset рядом с пользовательским конфигом:

```text
.colonial_helper_journal_offsets.json
```

При первом запуске watcher выполняет reconciliation всей доступной истории,
а затем продолжает с сохранённых позиций. При ротации Journal позиция
сбрасывается. В progress bar отображаются процент по байтам, число файлов,
прочитанный объём и имя текущего файла.

На ED Ring Colony отправляются два независимых типа данных:

- доставки игрока (`ColonisationContribution`, `CargoDepot`, FC `MarketSell` и
  безопасные cargo-delta) — в leaderboard deliveries;
- `ColonisationConstructionDepot` — публичные snapshots общего прогресса
  стройплощадки, ресурсы, construction ID и timestamp — в историю прогресса
  проекта. Эти snapshots не увеличивают личный тоннаж командира.

Повторная отправка безопасна: доставки используют `source_hash`, а события
строительства дедуплицируются по пользователю, времени, системе и construction
ID на сервере. Данные EDSM и Inara отправляются отдельно и не смешиваются с
API ED Ring Colony.

Ключи Raven Colonial, EDSM и Inara хранятся только локально. В версии 2.0
они дополнительно сохраняются в отдельном файле:

```text
~/.colonial_helper_credentials.json
```

Это предотвращает потерю credentials при закрытии приложения, обновлении EXE
или сохранении настроек HUD.
