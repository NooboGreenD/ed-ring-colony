# После переезда: edringcolony.ru, Uploader, OAuth и фоновые задачи

Анализ и изменения: **21 сентября 2026**. Основная схема — Docker Compose на
своём сервере; оба домена работают по HTTPS по подтверждению владельца.

- Сайт: **https://edringcolony.ru**
- Supabase API / Auth: **https://supabase.edringcolony.ru**
- Uploader: **Colonial Helper 2.10.25**
- Сайт: **Next.js 16.3.5 / React 19.2.8**, Fiber 9.7.0 / Drei 10.7.8
- **Готовая команда для Ubuntu 20.04: [UBUNTU20-UPGRADE.md](UBUNTU20-UPGRADE.md)**

Это инструкция **обновления уже работающей установки**, не первоначальной
установки. Не запускайте повторно `deploy/selfhost/install.sh`,
`supabase/full_schema.sql` или `docker compose down -v` ради этого обновления.
Новых SQL-миграций для этих изменений нет. Рабочий сервер из среды разработки
не администрировался; OAuth с настоящими аккаунтами и Docker-развёртывание
не проверялись на production. Docker daemon в среде разработки отсутствует:
проверены YAML-конфигурации, runner и сборка Next.js, но не запуск контейнеров.

## 1. Что обнаружено и что изменено

| Область | Было | Стало |
|---|---|---|
| Uploader → сайт | Жёсткий адрес Vercel | Новый HTTPS-домен, отдельная настройка сервера |
| Uploader → Supabase | Прямого подключения нет | Так и остаётся: только API сайта и личный `rc_…` токен |
| Сохранённые токены | Отдельный credentials-файл не восстанавливал `api.token` после чтения | Восстановление исправлено; токен связан с адресом сервера |
| Кэш импортов / offsets | Не учитывал сервер и пользователя | Учитывает origin + проверенный UUID; старые offsets требуют однократной сверки |
| HTTP перенаправления Uploader | `requests` мог переслать JSON с токеном при 307/308 | Перенаправления запрещены; проверка TLS остаётся включённой |
| Discord | Несколько реализаций OAuth, ошибки Server Actions терялись в production | Один PKCE-поток, понятные ошибки и статус привязки |
| OAuth callback | Origin мог оказаться внутренним адресом Docker; self-fetch с JWT | Канонический origin, прямое создание профиля через RLS, без self-fetch |
| Привязка | Не проверялось, что до и после callback тот же аккаунт | Подписанная HttpOnly-cookie с UUID/провайдером/TTL + проверка пользователя |
| Фоновые задачи | 6 Actions, только 5 задач в примере cron | Один контейнер `jobs`, все 6 задач, включая Raven progress |
| Защита служебных API | Поддельный `vercel-cron/…` обходил авторизацию в 2 API | Только секрет в заголовке; query-параметр `secret` больше не принимается |
| CI сайта | Проверки зависели от Actions | `npm test` при сборке Docker-образа на сервере |
| GitHub | Фоновые задачи + сборка EXE | В этой ветке оставлен только Windows EXE pipeline; удалённые расписания отключаются при передаче на сервер |
| Регистрация email | Admin API с принудительным подтверждением чужого адреса | Обычный `signUp`, проверка настроек GoTrue, обязательное письмо |
| Восстановление | Не было законченного UI | Resend/recovery, явное подтверждение ссылки, подписанный user/session-bound допуск на 10 минут |
| Next/React | Уязвимая Next 14 + React 18 | Next 16 / React 19, async request APIs, `proxy.ts`, no-store при refresh cookie |
| Карта/гидратация | Пробел под `<html>`, внешний fallback-шрифт | Исправлена гидратация; локальный шрифт для обычных 3D-подписей |

Во время обновления существующие UUID, пароли, досье, эскадрильи, доставки и
API-токены не меняются. Только явное восстановление пароля пользователем затем
отзывает refresh-сеансы и токены Uploader.
Профиль при OAuth создаётся только через `INSERT`; конфликт существующего
профиля не заменяет никнейм или аватар данными Discord. Старый `/auth/callback`
перенаправляет на проверяемый callback на сервере, без запуска браузерного SDK
и преждевременного обмена OAuth-кода.

## 2. Обновление сайта и задач на сервере

**Рекомендуемый автоматизированный путь — [UBUNTU20-UPGRADE.md](UBUNTU20-UPGRADE.md).**
Ниже — альтернативный ручной путь для нестандартных стеков. Не смешивайте их:
после управляющего скрипта используйте сохранённый им Compose-контекст, а не
старые команды `docker compose` из первоначального каталога.

### 2.1. Подготовка

1. Сделайте обычный backup Postgres **вместе со схемой `auth`**, Storage и
   закрытых конфигураций обоих стеков. Проверьте возможность восстановления.
2. Сохраните прежний образ сайта / версию исходников для отката.
3. Разверните новые исходники в существующем каталоге сайта, например
   `/opt/ed-ring-colony/src`. Не заменяйте `.env.production` пустым шаблоном.
4. Проверьте в `.env.production`:

```dotenv
NEXT_PUBLIC_SITE_URL=https://edringcolony.ru
NEXT_PUBLIC_SUPABASE_URL=https://supabase.edringcolony.ru
FRONTIER_REDIRECT_URI=https://edringcolony.ru/api/capi/callback
AUTH_OAUTH_PROVIDERS=discord
AUTH_EMAIL_ENABLED=false # включить после настройки и проверки SMTP
JOBS_ENABLED=capi-sync,update-progress,cg-check,eddn-cleanup,galnet-sync,translate
GALNET_FEED_LIMIT=30
GALNET_TRANSLATE_LIMIT=10
JOBS_TRANSLATE_PASSES=4
```

`NEXT_PUBLIC_SUPABASE_ANON_KEY` и `SUPABASE_SERVICE_ROLE_KEY` должны быть
**от локального Supabase**, не от старого облачного проекта. Существующие
рабочие ключи не регенерируйте. `CRON_SECRET` — непустой случайный секрет
рекомендуемой длиной не менее 32 символов. Он должен совпадать у `web` и `jobs`.
Если раньше его записывали в общедоступный `/etc/cron.d/…`, замените именно
`CRON_SECRET`, не JWT-ключи Supabase.

`YANDEX_TRANSLATE_API_KEY` / IAM token, `INARA_API_KEY` и при необходимости
`RAVEN_API_BASE` находятся в `.env.production` сайта. Планировщику **не передаются**
service_role, пароль БД и ключи внешних API. Файл окружения держите вне Git с
правами `0600` и подходящим владельцем.

### 2.2. Сборка и устранение двойного расписания

```bash
cd /opt/ed-ring-colony/src
# --env-file нужен и для build args, и для подстановок compose;
# service.env_file сам по себе не участвует в этих подстановках.
docker compose --env-file .env.production config --quiet
docker compose --env-file .env.production build web jobs
```

Сборка `web` запускает тесты сайта и production build. Старые контейнеры в это
время продолжают работать. Если сборка не прошла, не останавливайте старый сайт.

Перед включением `jobs` отключите старые источники расписания:

- GitHub → Actions: отключить **только** шесть старых workflows. Изменение файлов
  в рабочей ветке ещё не останавливает расписания на default branch!
- При использовании `gh` команды ниже выполняются владельцем при переключении:

```bash
for workflow in auto-translate.yml cron-capi-sync.yml cron-cg-check.yml \
  cron-eddn-cleanup.yml galnet-sync.yml update-progress.yml; do
  gh workflow disable "$workflow" --repo NooboGreenD/ed-ring-colony
done
```

- Не отключайте `build-exe.yml` / **Build Colonial Helper EXE**.
- Проверьте `crontab -e`, root crontab и `/etc/cron.d/ed-ring-colony`.
  Удалите только вызовы фоновых API сайта. **Оставьте `pg_dump`, Storage backup
  и ротацию бэкапов.** Не удаляйте cron-файл целиком.
- Дайте уже запущенным задачам завершиться. Старые задания, работающие с БД
  напрямую, не используют новый HTTP-lock.

```bash
docker compose --env-file .env.production up -d web jobs
docker compose --env-file .env.production ps
docker compose --env-file .env.production logs --tail=100 jobs
```

В первый запуск без state-файла каждая включённая задача выполняется один раз
сразу. Это реальная работа с БД, а не dry-run. Затем применяется расписание.

### 2.3. Расписание и эксплуатация

Время всегда **UTC**, независимо от часового пояса хоста/контейнера.

| Задача | Период / время | Endpoint |
|---|---|---|
| `capi-sync` | каждые 5 минут | `/api/cron/capi-sync` |
| `update-progress` | каждые 30 минут | `/api/cron/update-progress` |
| `cg-check` | 00:00, 06:00, 12:00, 18:00 | `/api/cron/cg-check` |
| `eddn-cleanup` | 00:30, 06:30, 12:30, 18:30 | `/api/cron/eddn-cleanup` |
| `galnet-sync` | 06:20 ежедневно (09:20 МСК) | `/api/galnet` + очередь переводов |
| `translate` | 00:40, 06:40, 12:40, 18:40 | `/api/cron/translate` |

- Контейнер обращается к `http://web:3000` **внутри Docker-сети**. Это не адрес
  для браузера и не публичная передача токенов по HTTP. Опубликованных портов у
  `jobs` нет. Публичные клиенты используют только HTTPS.
- Успешные интервалы записываются атомарно в именованный volume `jobs-state`.
  Не удаляйте volume при обычном обновлении. После простоя — один догон,
  а не очередь всех пропущенных запусков.
- Работы выполняются последовательно, без самоперекрытия и пиков нагрузки.
  Длительная задача может сдвинуть фактическое время следующей.
- Ошибки HTTP, не-JSON, `ok:false`, `success:false`, ненулевой `failed` дают
  повтор через 1, 2, 4, затем максимум 5 минут. Ошибки видны в `jobs` и `web` logs.
- На стороне сайта повтор уже работающего задания получает `409`.
  Galnet и перевод используют общий lock. Схема рассчитана на **один `web`
  и один `jobs`**; для нескольких реплик нужен распределённый lock в БД.
- Без Inara/Yandex ключей соответствующая задача получает `skipped` с причиной,
  а не бесконечную очередь ошибок. Необязательные задачи можно удалить из
  `JOBS_ENABLED`. Пустое значение отключает всё расписание.
- Galnet сохраняется независимо от наличия переводчика. При включённом переводе
  синхронизация переводит до `GALNET_TRANSLATE_LIMIT` свежих статей, затем
  выполняется до `JOBS_TRANSLATE_PASSES` дополнительных порций такого же размера.
  Обычный запуск `translate` раз в 6 часов обрабатывает **одну** порцию — сохранён
  прежний объём одного планового запуска. Повторы после ошибок и начальный догон
  могут тратить дополнительную квоту: настройте контроль расходов у провайдера.
  Удаление `translate` из `JOBS_ENABLED` отключает перевод и внутри Galnet,
  оставляя синхронизацию оригиналов.
- EDDN **очистка** входит в расписание; ZeroMQ-приёмник рыночных данных —
  отдельный необязательный worker, сам по себе здесь не включается.

Диагностика без раскрытия секретов:

```bash
# Список задач, без обращения к БД
docker compose --env-file .env.production exec jobs node scripts/server-jobs.mjs --list
# Последние успешные интервалы (секретов в файле нет)
docker compose --env-file .env.production exec jobs cat /data/jobs-state.json
# Ручной реальный запуск одной задачи; возвращает ненулевой exit code при ошибке
docker compose --env-file .env.production exec jobs node scripts/server-jobs.mjs --once galnet-sync
```

`--once` намеренно не изменяет расписание. Не запускайте его одновременно с той
же задачей планировщика: получите `409`. Не используйте `--scale jobs=2`.
Повреждённый state-файл останавливает scheduler; исправьте права или восстановите
его, а не удаляйте автоматически с повторным расходованием квоты перевода.

Для установки **без Docker** остался `deploy/crontab.example`: тот же runner,
Node 22, отдельный закрытый env-файл и `flock`. Это альтернатива, не второй
планировщик поверх Docker.

## 3. Discord: две разные callback-ссылки

### В Discord Developer Portal → OAuth2 → Redirects

```text
https://supabase.edringcolony.ru/auth/v1/callback
```

Discord возвращает код в **GoTrue**, а не напрямую в Next.js.

### В self-hosted Supabase

В `/opt/supabase/.env` проверьте/добавьте:

```dotenv
SITE_URL=https://edringcolony.ru
API_EXTERNAL_URL=https://supabase.edringcolony.ru
SUPABASE_PUBLIC_URL=https://supabase.edringcolony.ru
ADDITIONAL_REDIRECT_URLS=https://edringcolony.ru/api/auth/callback,https://edringcolony.ru/auth/email
GOTRUE_EXTERNAL_DISCORD_ENABLED=true
GOTRUE_EXTERNAL_DISCORD_CLIENT_ID=ID_ВАШЕГО_DISCORD_ПРИЛОЖЕНИЯ
GOTRUE_EXTERNAL_DISCORD_SECRET=СЕКРЕТ_ТОГО_ЖЕ_ПРИЛОЖЕНИЯ
```

Значения здесь — примеры-заполнители. Не копируйте их вместо действующих секретов.
`API_EXTERNAL_URL` задаётся без завершающего `/`.

**Важно:** наличие переменных в `.env` не гарантирует, что они попали в контейнер
`auth`. В официальном compose провайдер может не быть перечислен в `environment`.
Подготовлен `deploy/selfhost/supabase-auth.override.yml`:

1. Если `/opt/supabase/docker-compose.override.yml` отсутствует, скопируйте
   туда этот файл. Если уже есть — **объедините `services.auth.environment`**,
   не перезаписывайте существующую конфигурацию. При использовании явных `-f`
   включите override в каждый вызов compose.
2. Override передаёт GoTrue настройки провайдеров и
   **`GOTRUE_SECURITY_MANUAL_LINKING_ENABLED=true`**. Не включайте в нём
   Google/GitHub, пока они не настроены.
3. Примените именно к работающему Supabase-стеку:

```bash
cd /opt/supabase
docker compose config --quiet
docker compose up -d --no-deps --force-recreate auth
docker compose logs --tail=50 auth
```

Если запускаете compose не из стандартных файлов, сохраните существующее
сочетание `-f`/`--env-file` и добавьте override к нему. Версия GoTrue должна
поддерживать manual identity linking. Флаг сайта `AUTH_OAUTH_PROVIDERS`
**не включает** провайдера в GoTrue и не заменяет его секреты.

### Проверка без потери аккаунта

1. Войти в существующий аккаунт привычным способом, записать свой UUID.
2. `/account` → «Способы входа» → «Привязать Discord» → дать разрешение.
3. Проверить: UUID тот же, профиль/CMDR/доставки/эскадрилья не изменились;
   среди `auth.identities` есть Discord, на сайте показано «привязан».
4. Выйти и войти через Discord: открывается **то же** досье.
5. Проверить отказ в Discord, повтор старой ссылки, отсутствие manual linking,
   Discord уже у другого пользователя. Должна появиться понятная ошибка,
   без незаметного переключения аккаунта.
6. Отвязка требует другого доступного способа входа и подтверждения пользователя.
   Не удаляйте последний способ; сначала настройте пароль и проверьте вход.

Поток использует PKCE и подписанную HttpOnly-cookie на 10 минут. Начинайте и
заканчивайте вход в одной вкладке/браузере, на одном каноническом домене.
В процессе привязки не переключайте аккаунт в другой вкладке.

Автоматического SQL-объединения двух готовых профилей нет. Если Discord уже
привязан к другому UUID, требуется отдельная процедура с доказательством владения
обоими аккаунтами и переносом зависимых записей; совпадения email недостаточно.

## 4. Uploader 2.10.25

- Обновить EXE через прежний канал GitHub Releases или собрать `build-exe.yml`.
  Этот workflow сохранён. Стабильная публикация требует выпуска из `main`;
  сборки рабочей ветки остаются prerelease и доступны в канале «Все сборки».
  Изменение исходников само по себе **ещё не публикует EXE**.
- На вкладке подключения виден `https://edringcolony.ru`; кнопка открывает
  `/account?tab=tokens`. Вставляется личный API-токен, **не anon/service_role/JWT**.
- Если таблица `api_tokens` перенесена с теми же user UUID/hash, старый токен
  продолжит работать. Если нет — сгенерировать новый в существующем аккаунте.
  При `401` программа объяснит это, а не останется «подключённой» к старому UUID.
- Старый Vercel-адрес в настройках нормализуется в новый адрес **до запроса**.
  Публичный HTTP не используется. TLS-проверка не отключается при ошибке сертификата.
- «Другой сервер…» проверяет HTTPS-origin, сохраняет адрес и закрывает приложение.
  После перезапуска потребуется токен именно того сервера; ключи RCC/EDSM/Inara
  остаются прежними. Такое поведение не меняет адрес под выполняющимися загрузками.
- Кэш старой версии без server/account scope перепроверяется один раз. Это может
  увеличить первую загрузку: используйте актуальную БД с уже имеющимися
  миграциями идемпотентности доставок. Новое обновление схему БД не меняет.
- При смене базы **на том же домене с сохранением UUID**, если нужно повторить
  историю, используйте сброс кэша на вкладке загрузки и ручной импорт журналов.
  Программа не может определить восстановление/замену БД по одному адресу.

## 5. Дополнительные способы авторизации

| Вариант | Подход | Решение |
|---|---|---|
| Email + пароль | Уже работает; резерв для OAuth | Сохранить, но закрыть проблему подтверждения email ниже |
| Discord | Native Supabase identity | Основной игровой способ; доработан в этом обновлении |
| Google | Native Supabase identity | Код входа/привязки готов, выключен по умолчанию |
| GitHub | Native Supabase identity | Код готов, удобен части аудитории, выключен по умолчанию |
| Яндекс / VK ID | Отдельный OAuth/OIDC-адаптер либо брокер, например Keycloak | Разумный следующий этап для аудитории; не включаются одним флагом текущего кода |
| Telegram | Проверка подписи login payload, срока и защиты от replay; уникальный Telegram ID | Отдельный проект интеграции, не подставлять фиктивный email вместо identity |
| Passkeys | Проверить возможности установленной версии GoTrue / внешнего IdP | Рассматривать после базовой защиты и восстановления доступа |
| TOTP MFA | Второй фактор, не самостоятельный способ входа | Приоритетно для администраторов |
| Frontier CAPI | Доступ к игровому досье | **Не** авторизация на сайте; не смешивать с Supabase identities |

**Рекомендация:** сначала завершить проверку Discord и email-политики, затем
включить Google и/или GitHub без новых пользовательских таблиц. Яндекс/VK/Telegram
выбирать по реальному спросу: поддержка дополнительного IdP увеличивает объём
секретов, обновлений, восстановления доступа и тестов.

Для Google/GitHub после настройки приложений и проверки email-политики:

1. У провайдера callback — `https://supabase.edringcolony.ru/auth/v1/callback`.
2. В Supabase `.env` заполнить соответствующие
   `GOTRUE_EXTERNAL_GOOGLE_*` / `GOTRUE_EXTERNAL_GITHUB_*` и `ENABLED=true`;
   override уже содержит их передачу в `auth`. Пересоздать `auth`.
3. В окружении **сайта** установить `AUTH_OAUTH_PROVIDERS=discord,google,github`
   (или нужное подмножество) и пересоздать `web`.
4. Проверить `/api/auth/providers`: только имена включённых провайдеров,
   никаких секретов. Это runtime-настройка, пересборка клиентского JS для списка
   кнопок не нужна. Привязка использует тот же UUID и те же ограничения, что Discord.

### Email: исправление регистрации и восстановление

`/api/auth/register` больше не использует admin auto-confirm. Для отправки
нужен `AUTH_EMAIL_ENABLED=true` и публичная настройка GoTrue
`mailer_autoconfirm=false`; неизвестная/небезопасная конфигурация блокирует signup.
До подтверждения почты вход после регистрации не выполняется. Минимум нового
пароля — 12 символов, максимум 72 байта UTF-8; действующие короткие пароли
не меняются и продолжают приниматься при обычном входе.

Ручная настройка в **Supabase env** (без замены действующих ключей):

```dotenv
ENABLE_EMAIL_AUTOCONFIRM=false
DISABLE_SIGNUP=true
SMTP_HOST=РЕАЛЬНЫЙ_SMTP_HOST
SMTP_PORT=587
SMTP_ADMIN_EMAIL=РЕАЛЬНЫЙ_АДРЕС_ОТПРАВИТЕЛЯ
SMTP_USER=РЕАЛЬНЫЙ_SMTP_LOGIN
SMTP_PASS=СЕКРЕТ_ВВОДИТСЯ_ТОЛЬКО_НА_СЕРВЕРЕ
SMTP_SENDER_NAME=ED Ring Colony
```

Merge `deploy/selfhost/supabase-auth.override.yml` передаёт SMTP, шаблоны
`/auth/templates/signup` и `/auth/templates/recovery`, OTP expiry 1 час,
минимальную длину и требование недавнего подтверждения при смене пароля в GoTrue.
Сначала запустите новый web (шаблоны должны отдаваться по HTTPS), затем `auth`.
Проверьте реальную почту и только после этого установите `DISABLE_SIGNUP=false`
в Supabase и `AUTH_EMAIL_ENABLED=true` в web. Само добавление ключей в `.env`
без передачи в контейнер не работает. На автообновлённом стеке вместо ручного
редактирования используйте `upgrade.py configure-auth --edit-smtp`.

- `/resend-confirmation` и `/forgot-password` возвращают одинаковый ответ вне
  зависимости от наличия адреса. HTTP 202 означает принятие запроса, **не**
  гарантию доставки; детали проверяйте в закрытых GoTrue/SMTP logs.
- Шаблоны передают `.TokenHash` в URL **после `#`**. Он не отправляется в HTTP GET,
  очищается из истории и обменивается только по явному POST. Обычный GET-сканер
  письма не расходует ссылку и не выполняет автоматический вход.
- Сброс требует проверенного recovery OTP и подписанной HttpOnly-cookie,
  привязанной к UUID и `session_id`, с TTL 10 минут. Произвольной активной сессии
  или одного параметра `type=recovery` недостаточно.
- После смены пароля отзываются refresh-сеансы и API-токены Uploader. Частичный
  отказ отзыва честно показывается пользователю. Access JWT живёт до своего `exp`;
  OAuth-привязки сохраняются и при подозрении на взлом требуют отдельной проверки.

### Что исправлено и что нельзя завершить без эксплуатации

1. **Зависимости в этой ветке:** Next 16.3.5, React 19.2.8, Supabase SSR 0.12.7;
   `npm audit` для всего lockfile — **0 уязвимостей** на момент проверки. Async
   cookies/params мигрированы, SSR refresh-cookie запрещают кэширование; проверен
   настоящий Chromium/WebGL2. Это не обещание отсутствия будущих advisory.
2. **Исторические email:** прежние `email_confirm:true` нельзя задним числом
   считать доказательством владения. Существующие UUID и пароли намеренно не
   сбрасываются массово; спорные аккаунты и чужие OAuth identities проверяются
   адресно перед расширением способов входа.
3. **На сервере:** backup перед обновлением автоматизирован, но внешнюю копию,
   полный restore-тест, оповещения по `lastSuccess`, TLS/диску и бюджеты внешних API
   должен обеспечить оператор. SMTP/DNS и OAuth-приложения требуют настоящих
   настроек владельца. Ubuntu 20.04 нуждается в ESM либо плановом обновлении ОС.
