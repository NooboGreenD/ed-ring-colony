# Helper: повторная обработка журналов при запуске

## Статус и границы вывода

Симптом: у части пользователей Helper при некоторых запусках повторно обрабатывает
10–30 исторических журналов, хотя раньше отправка завершалась без ошибок;
наблюдаются длительная загрузка CPU и впечатление зависания.

Ниже — дефекты, воспроизведённые на синтетических данных, и локальные исправления.
Реального проблемного запуска пользователя нет: единственная причина симптома
**не установлена**. Проверка журналов, локальная индексация экзобиологии и HTTP-
отправка — разные операции; успешный upload не отменяет необходимость локального
индекса и сам по себе не подтверждает сохранение курсора чтения.

## Воспроизведённые механизмы

1. **Дорогая запись экзобиологии.** Сохранение 300 систем делало 301 полную
   сериализацию кэша. Кроме того, ручной полный скан выполнял сохранение в GUI-
   callback. Теперь снимок трекера группируется за один проход, данные и метки
   файлов сохраняются одной заменой JSON, подготовка/сохранение идут в worker.
   Автоматический и ручной полные сканы используют общий запрет перекрытия.
2. **EOF без перевода строки.** Законченный последний JSON-event оставался за
   курсором. Теперь он обрабатывается один раз без требования LF. Настоящий
   неполный JSON/UTF-8 остаётся непрочитанным; неизменившийся хвост повторно не
   открывается и не вызывает запись смещений. Изменение размера/mtime разрешает
   новую попытку, ошибка чтения не кэшируется.
3. **Гонка stop/start.** Новый запуск мог очистить общий stop Event, пока старый
   worker ещё работал. Это позволяло двум потокам менять курсоры. Повторный старт
   теперь запрещён до окончания старого потока; отложенный callback старого
   worker не завершает новый. Остановка во время подготовки учитывается.
4. **Каталог временных файлов.** Если внешний очиститель удалил Temp, атомарная
   запись смещений не создавала его заново. Теперь создаются оба каталога.
   Проверены сохранение, повторная загрузка и восстановление после удаления Temp.

Дополнительно: перечисление журналов выдерживает исчезновение отдельного файла;
ошибочные/выходящие за размер смещения нормализуются; пустые тики не переписывают
checkpoint. У кэша экзобиологии сериализованы операции записи, временные имена
уникальны, остатки временного файла удаляются после неудачной замены. Отмена
сканирования не отмечает недочитанный файл завершённым. При неудаче записи старый
дисковый JSON остаётся целым; подготовленные данные и метки остаются в памяти
для следующего сохранения, а не считаются отдельным подтверждением на диске.

## Диагностика проблемного запуска

Не удалять offsets, кэш ручного импорта или outbox «для лечения»; не включать
повторную отправку всей истории во внешние сервисы. Не запрашивать API-токен или
полные личные журналы.

Нужны версия Helper, ОС, примерное количество/общий объём журналов, момент начала
зависания, состояние Watcher и небольшой обезличенный фрагмент его сообщений:

- `Journal reconciliation: ...` объясняет отсутствие применимого checkpoint:
  нет файла, повреждён/старый формат либо другой аккаунт/сайт. Содержимое файла
  и идентификаторы аккаунтов в этом сообщении не печатаются.
- `Startup journal reconciliation: ...` даёт число файлов, прочитанные байты,
  wall time и CPU time процесса. Может включать обработку и ожидание отправки.
- `Local exobio index (not upload): ...` относится **только к локальному индексу**.
  Содержит число файлов/событий и длительность, не число загруженных доставок.

CPU time — всего процесса, включая одновременно работающие потоки, не профиль
конкретного worker. Число файлов в прогрессе само по себе не показывает, сколько
полных файлов было заново отправлено: файл может иметь лишь короткий хвост.
Для передачи диагностического фрагмента вручную убрать имена пилота, пути и
любые личные данные из соседних сообщений.

## Проверки и оставшиеся ограничения

- 21 новый регрессионный тест: реальные методы Helper извлекаются через AST без
  импорта Qt; алгоритмы трекера/кэша проверяются обычным импортом.
- Расширенный целевой прогон: **288 тестов успешно**, включая существующие
  тесты экзобиологии, отправки, carrier/station/BGS/squadron/CG, PowerPlay,
  self-host API и упаковки. Это не полный GUI-прогон проекта.
- Нет проверки Windows, Qt event loop, антивируса/реального очистителя и
  воспроизведения проблемного пользовательского запуска. PySide6 недоступен.
- Формат меток файлов экзобиологии пока прежний: имя + mtime с допуском 0.01 s.
  Быстрое дописывание с тем же mtime может быть пропущено. Тест дописывания
  явно меняет mtime; он не доказывает устранение этого ограничения.
- Блокировки защищают изменения и экспорт трекера, но не все существующие
  прямые чтения его публичных словарей интерфейсом. Синхронная запись текущей
  системы может ждать занятую блокировку кэша.
- Смещения журналов — **позиции чтения, не подтверждения HTTP**. Существующий
  разрыв между сохранением позиции и подтверждённой отправкой deferred batches
  не устранён: отключение/аварийное завершение может оставить неподтверждённые
  доставки/снимки без надёжного восстановления. Это требует отдельного durable
  outbox/ACK решения; ускорение индексации не является исправлением этого пути.

Исправления не сбрасывают историю и не запускают production replay. Эта работа
сама по себе не означает выпуск, развёртывание или публикацию новой версии.
