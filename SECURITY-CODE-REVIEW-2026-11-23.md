# ED Ring Colony / Colonial Helper — аудит ошибок и безопасности

**Дата:** 23 ноября 2026. **Проверенный код:** commit `77d7459`, ветка `arena/24476c57-ed-ring-colony`.
**Результат:** обнаружены подтверждённые локально дефекты разграничения доступа, финансовой целостности и бизнес-логики. Есть две критические находки, требующие первоочередного разбора. Исправления приложения и миграций в рамках этого отчёта **не вносились**.

> Это аудит исходников и изолированных воспроизведений, а не подтверждение взлома production. Реальные политики БД, секреты окружения, сетевые ACL и установленные версии production не запрашивались. Секретные значения намеренно не приводятся. Прежний `SECURITY-AUDIT.md` описывает другой срез проекта и этим отчётом не перезаписывается.

## 1. Краткий итог

Наиболее опасны:

1. **Приватный ключ подписи обновлений Helper находится в исходниках** и соответствует доверенному клиентом публичному ключу. Это компрометация ключа доверия, но не доказательство возможности подменить официальный HTTPS-канал.
2. **RLS эскадрилий допускает межэскадрильный доступ и изменение членства в обход API.** Ошибка разрешения имён в SQL подтверждена PostgreSQL.
3. **Баланс и покупки не атомарны:** на 100 кредитов одновременно приобретены два предмета по 80; при параллельных начислениях потеряна часть денег.
4. **Повторная регистрация строительства меняет владельца существующей записи** на другого вошедшего пользователя.
5. Дополнительно найдены SSRF-поверхность в push, условный дефект привязки платежа ЮKassa к заказу, ненадёжный fallback биллинга, ошибки галереи и перевода между эскадрильями.

## 3. Подробные находки

### S01. Приватный seed ключа подписи обновлений включён в исходники

**Места:** `src/lib/uploaderStore.ts:81–83, 883–910, 1063–1069, 1154`; доверие клиента — `uploader/bundle.py:90` и проверка manifest signature далее в этом модуле.

В модуле есть `CANONICAL_SIGN_SEED_B64`. Это не только тестовый пример: seed используется при выборе ключа и сохраняется через `ensureCanonicalSigningKey()`. Клиент доверяет соответствующему публичному ключу.

**Проверка:** локально из seed получен Ed25519 public key; он совпал с серверной константой и ключом в `TRUSTED_KEYS` клиента. Подпись безопасной тестовой строки успешно прошла проверку. Значение seed, приватный ключ и подпись в отчёт не включены.

**Последствие:** любой имеющий исходники может создавать подписи от имени этого доверенного ключа. Если атакующий также получает возможность доставить клиенту свой manifest/bundle, нарушается доверие к обновлениям. Сам seed **не даёт** доступа к домену, publish API или серверу.

**Исправление:** считать ключ скомпрометированным; создать новый вне Git; хранить в secret storage/закрытом томе; убрать автоматическое восстановление старого seed. Скоординировать сервер, bootstrap и trust store установленных клиентов, отозвать старый ключ. Удаление строки новым коммитом не отменяет компрометацию в истории. **Не публиковать подробности ключа в публичном issue.**

**Регрессия:** secret scanning; сборка сервера без встроенного private seed; обновлённый клиент отклоняет manifest, подписанный отозванным ключом, и принимает новый доверенный ключ.

### S02. RLS эскадрилий: некоррелированные проверки и отсутствие проверки полномочий

**Места:** `supabase/migrations/20260830110258_rls_policies_v2.sql:359–407, 1000–1013, 1020–1049`; аналогичные определения есть в `001_rls_policies.sql`.

Пример условия:

```sql
EXISTS (
  SELECT 1 FROM public.squadron_members sm
  WHERE sm.squadron_id = squadron_id AND sm.user_id = auth.uid()
)
```

Неполностью квалифицированный `squadron_id` внутри подзапроса разрешается в его локальную таблицу. Вместо сравнения с защищаемой строкой получается сравнение `sm.squadron_id` с самим собой. Для пользователя, состоящего **в любой** эскадрилье, условие истинно независимо от эскадрильи внешней строки.

Кроме того, политики изменения `squadron_members`/`squadron_ranks` проверяют лишь наличие членства, но не `can_manage_members`/`can_manage_ranks`. Простая квалификация имён не закрывает повышение собственных полномочий внутри своей эскадрильи.

**Локальное доказательство:** пользователь A — участник эскадрильи 10, пользователь B — эскадрильи 20. Под ролью `authenticated` и UID A, с точными CREATE POLICY из миграции:

- SELECT `squadron_chat_messages` вернул сообщения **обеих** эскадрилий;
- A изменил собственный `rank_id` с обычного ранга на управленческий;
- A изменил строку членства B в другой эскадрилье.

GRANT на запись членства и рангов указан непосредственно в этой миграции. В просмотренных последующих миграциях замены этих политик не найдено. Полная production-схема не выгружалась.

**Последствие:** прямое обращение к Supabase REST обходит хорошие проверки прав Next.js API. Нарушены конфиденциальность чатов и целостность членства/рангов эскадрилий; это не равнозначно выдаче глобальной роли администратора сайта.

**Исправление:** новая forward-only миграция, полная квалификация внешних колонок, права на операцию и целевую эскадрилью; при необходимости проверяющие SECURITY DEFINER-функции с фиксированным search_path и ограниченным EXECUTE, без рекурсивного чтения той же RLS-таблицы. Проверить также chat/voice INSERT/SELECT. На время ремонта ограничить прямую запись в чувствительные таблицы, сохранив необходимые серверные операции.

**Регрессия:** реальный `SET ROLE authenticated` для outsider/member/officer/admin; чтение чужого чата, самоповышение, изменение чужого членства и ранга должны отклоняться независимо от API.

### S03. Баланс и выдача покупок не объединены транзакцией

**Места:** `src/lib/billingData.ts:388–405` (`subscribeWithCredits`), `658–669` (`adjustBalance`), `742–795` (`purchaseItem`), `1033` и далее (`fulfilIntent`); Supabase upsert — `src/lib/billing/storage.ts`.

`adjustBalance` выполняет read → вычисление нового баланса → upsert. Проверка достаточности средств находится отдельно от списания, выдачи предмета и ledger-записи. `Math.max(0, ...)` скрывает отрицательный результат, а не запрещает перерасход. Per-intent CAS в `fulfilIntent` не сериализует разные заказы одного пользователя.

**Локальная проверка настоящего repository:**

```text
Начальный баланс 100; параллельно +10 и +20:
  ожидалось 130, получено 120.
Начальный баланс 100; два разных предмета по 80:
  обе покупки success=true, остаток 20.
```

Проверялся file adapter с отдельным файлом, не `data/billing_store.json`. В Supabase не проводился concurrent live-тест, однако read/overwrite-последовательность адаптера также не содержит атомарного SQL debit/increment.

**Последствие:** недополученные начисления, покупки сверх баланса, расхождение inventory/ledger/balance; при сбое между операциями возможно частичное исполнение.

**Исправление:** SQL-транзакция/RPC: блокировка строки пользователя или условное `UPDATE ... SET credits=credits-price WHERE credits>=price RETURNING ...`, выдача и ledger в одной транзакции. Начисления — атомарный increment с idempotency key. Для file preview — сериализация и запрет реальных денежных операций; process-local mutex не решит несколько серверных процессов.

**Регрессия:** параллельные разные покупки, два пополнения, пополнение одновременно с покупкой и сбой после debit; финальная сумма и выдачи должны соответствовать ledger.

### S04. Регистрация строительства перезаписывает владельца существующего проекта

**Места:** `src/app/api/projects/register/route.ts`; `src/app/api/architect/raven-project/route.ts:79–101`; `supabase/migrations/20261106090000_construction_projects.sql:175–202`.

Сервер передаёт в service RPC текущий `userId`, но RPC делает upsert по общему `project_key` и присваивает `user_id = COALESCE(EXCLUDED.user_id, cp.user_id)` без проверки прежнего владельца. Подлинность commander/права на площадку перед записью не подтверждаются.

**Локальная проверка:** A зарегистрировал площадку; B передал тот же ключ, другую метку времени и статус. ID строки остался тем же, `user_id` стал B, статус изменился на `complete`.

**Последствие:** изменение атрибуции и содержимого чужого проекта. Сам RPC закрыт для anon/authenticated, но доступен через аутентифицированный серверный маршрут — один REVOKE проблему не решает. Строительная телеметрия может быть намеренно общей; это не оправдывает неявную передачу владельца.

**Исправление:** разделить owner metadata и общие наблюдения; не менять владельца обычным ingest; подтверждать право на owner-only поля; смену владельца оформить отдельной операцией. Для общей телеметрии хранить источник, доверие и допустимую свежесть.

**Регрессия:** B может добавить разрешённое наблюдение, но не заменить owner/commander и не выполнить чужую owner-only операцию.

### S05. ЮKassa: проверен платёж, но intent может браться из непроверенного тела

**Места:** `src/lib/billing/providers.ts:141–165`; `src/app/api/billing/webhooks/[provider]/route.ts:49–75`.

Драйвер правильно запрашивает платёж у API ЮKassa, однако выбирает intent так:

```ts
json?.metadata?.intent_id || obj.metadata?.intent_id
```

Если проверенный ответ API не содержит `intent_id`, принимается значение из присланного webhook. Общий handler затем не сверяет provider/external ID/amount/currency с выбранным заказом: такие проверки есть только для Т-Банка.

**Локальная проверка:** mock API вернул `succeeded`, сумму 1 RUB и пустые metadata. Во входном теле указан другой локальный intent. Драйвер вернул `ok=true`, `paid` и intent из входного тела. Реального запроса к ЮKassa не было.

**Условия злоупотребления:** нужен известный идентификатор успешного платежа **в том же магазине**, у которого нет проверенных metadata intent; webhook secret должен отсутствовать либо быть известен; целевой intent должен быть действительным и ещё исполнимым. Обычные платежи, создаваемые приложением с корректными metadata, этим доказательством не скомпрометированы. Наличие подходящего платежа в production не установлено.

**Исправление:** использовать только поля проверенного API-ответа; при отсутствии verified intent искать по provider+external ID или отклонять; всегда сверять поставщика, внешний ID, сумму, валюту и live/test mode. Не полагаться только на секрет в metadata.

**Регрессия:** отсутствующие verified metadata, правильный платёж с чужим intent, неверная сумма/валюта/поставщик должны давать отказ без выдачи товара.

### S06. Push endpoint пользователя становится адресом серверного HTTPS-запроса

**Места:** `src/app/api/push/subscribe/route.ts:9–23`; `src/lib/pushNotifications.ts:43–72, 112–136`; `web-push` в установленной версии, `src/web-push-lib.js:348–369`.

Подписка принимает любой непустой endpoint и ключи. Отправитель передаёт их `webpush.sendNotification` без allowlist хостов/портов, проверки DNS/IP и явного timeout. Библиотека использует hostname/port/path endpoint для `https.request`.

**Локальная проверка:** со сгенерированными валидными push-ключами endpoint `https://127.0.0.1:9443/local-proof` дошёл до вызова `https.request` с localhost и портом 9443. Вызов перехвачен **до сети**, запрос не отправлялся.

**Условия/границы:** нужна учётная запись и событие, вызывающее push этому пользователю; настроенные VAPID keys; доступный из контейнера адрес. HTTPS-проверка сертификата остаётся включена: это **не** произвольное чтение HTTP cloud metadata. До ошибки TLS возможны DNS/соединения, а доверенные внутренние HTTPS-сервисы могут получить POST. Ответ отправки пользователю не возвращается.

**Исправление:** разрешённые push-службы с точной нормализацией host/port, отклонение credentials и локальных/reserved IP после DNS resolution, защита от rebinding, egress policy, timeout и ограничение числа подписок/параллельных отправок. Нельзя проверять только строковый префикс домена.

### S07. Биллинг может молча перейти на локальный JSON и сообщать об успехе при ошибке диска

**Места:** `src/lib/billing/storage.ts:83–104, 136–153, 299–327`; fail-closed только для Т-Банка — `src/app/api/billing/webhooks/[provider]/route.ts:21–22`.

Ошибка стартового probe Supabase приводит к fallback на FileAdapter, который кэшируется на процесс. Временная ошибка БД становится длительной работой с другим источником денег/подписок. В `FileAdapter.save()` ошибка записи только логируется; вызывающий insert/upsert продолжает возвращать успех. Запись JSON не атомарна и не координируется между процессами.

**Условия:** сбой БД/схемы при выборе адаптера либо явно включённый file backend; для потери persistence — ошибка диска. Production-событие не воспроизводилось. Live Т-Банк отдельно блокирует такой backend; остальные провайдеры не получают равноценной общей гарантии в webhook handler.

**Исправление:** file backend — только явный preview/test mode; production money flow fail-closed при недоступной БД. Ошибки persistence должны прерывать операцию, readiness — отражать состояние. Не восстанавливать денежный баланс из случайного локального файла после рестарта.

### S08. Rate limit обмена кода Helper обходится подстановкой X-Forwarded-For

**Места:** `src/app/api/uploader/link/claim/route.ts:13–17, 29–32`; `src/lib/rateLimit.ts:3–15`; `deploy/nginx.conf:35–37`.

API доверяет **первому** адресу `X-Forwarded-For`. В приложенной конфигурации nginx применяется `$proxy_add_x_forwarded_for`: клиентский заголовок сохраняется перед реальным адресом. Меняя первый элемент, клиент получает новый ключ limiter. В дополнение cache process-local и ограничен 500 ключами.

**Проверка:** 13-я попытка с одним ключом блокируется, попытка с новым ключом проходит; цепочка формирования ключа установлена по исходникам nginx/API. Реальный proxy chain production не проверен. Коды криптографически случайны и имеют TTL — обход лимита **не доказывает** успешный перебор токена.

**Исправление:** доверенный proxy должен перезаписывать идентифицирующий заголовок, приложение — доверять только известному proxy chain; распределённый limiter и общий предел неудачных обменов, мониторинг. Не просто заменять один недоверенный заголовок другим.

### S09. Галерея кораблей: противоречие Storage RLS, неверный delete path, обход правил metadata

**Места:** `src/app/api/user/ships/photos/route.ts:55–64, 82–100, 117–130, 143–174`; `supabase/migrations/20261120000000_ship_images_bucket.sql:26–44`; `20261120010000_user_ship_photos.sql:20–31, 55–77`.

Три связанных дефекта:

1. POST использует пользовательский Supabase client, но миграции разрешают запись в `ship-images` только `service_role`. В чистой схеме с этими политиками premium-пользователь получает отказ Storage; local SQL под `authenticated` подтвердил RLS rejection. Вручную добавленные production policies могли изменить поведение.
2. DELETE извлекает из public URL хвост **вместе с `ship-images/`**, после чего передаёт его в `from('ship-images').remove(...)`. Объект фактически ищется с лишним bucket prefix. Ошибка удаления игнорируется, запись metadata удаляется. Дополнительно пользовательскому client не дана политика удаления Storage. Результат — оставшийся публично доступным файл при ответе success.
3. RLS таблицы `user_ship_photos` проверяет только `user_id`, но не premium perk, лимит 5 и допустимый image_url. При стандартных Supabase grants прямой REST INSERT обходит ограничения API. В локальной схеме с явно смоделированными стандартными grants вставлены 6 строк без подписки; это обход metadata-правил, **не доказательство возможности загрузить 6 настоящих файлов**, поскольку Storage upload отдельно запрещён.

**Исправление:** выбрать единый безопасный поток: серверная проверка владельца/perk/quota и service upload/delete либо эквивалентные строгие storage policies. Не разрешать authenticated запись всего bucket, содержащего также официальные картинки. Хранить bucket-relative object_key, обрабатывать ошибки удаления и предусмотреть cleanup/retry. Ограничить прямой metadata DML или перенести инварианты в БД; quota должна быть атомарной.

### S10. Transfer-миграция удаляет старое членство, но не вставляет новое

**Место:** `supabase/migrations/20261118010000_squadron_transfer_fix.sql:223–269`.

В ветке `IF EXISTS (старое членство)` выполняются DELETE и `reason='transferred'`. INSERT новой строки расположен в `ELSE` той же цепочки IF/ELSIF и при переводе **не выполняется**. После одного вызова пользователь не состоит ни в старой, ни в новой эскадрилье. Повторная синхронизация может восстановить членство, но первый ответ уже некорректен; старый ранг и членство потеряны.

**Локальная проверка:** взята схема из существующего `squadron-journal-db.test.mjs`, затем последовательно применены миграции 17 и 18 ноября. Пилот вступил в OLD; при переходе в NEXT получено:

```json
{"oldMembers":0,"newMembers":0,"reason":"transferred","joined":false}
```

**Исправление:** после проверки вместимости и прав делать удаление/вставку как единый перевод; нельзя выходить из старой эскадрильи, если новая не может принять. Проверить конкуренцию с ручным управлением составом.

**Регрессия:** именно последовательность **обеих** миграций; перевод в свободную/полную эскадрилью, ошибка вставки, повтор и устаревшее событие.

### S11. GET офицерского чата не проверяет офицерские права

**Места:** `src/app/api/squadrons/[id]/chat/route.ts:13–38` (GET), проверка officer-прав присутствует в POST ниже; SQL SELECT — `20260830110258_rls_policies_v2.sql:1000–1003`.

GET проверяет только членство, затем использует клиентский `type` для фильтрации `chat_type`. Для `type=officer` проверка соответствующего ранга отсутствует; RLS также не различает officer/general. Поэтому обычный участник может читать офицерские сообщения своей эскадрильи, даже после устранения межэскадрильной ошибки S02.

**Исправление:** одинаковая политика чтения/записи officer channel на сервере и в БД, запрет неизвестных типов чата. Нельзя полагаться на скрытую UI-вкладку.

### S12. Webhook-лог сохраняет полный непроверенный JSON вместо лимитированного

**Место:** `src/app/api/billing/webhooks/[provider]/route.ts:25–45, 80`.

Сначала строка ограничивается 20 000 символами, но успешный `JSON.parse(rawBody)` заменяет её полным объектом. Даже webhook с неверной подписью сохраняется в БД. Для Т-Банка есть allowlist/redaction; для остальных включённых провайдеров аналогичной фильтрации нет.

**Последствие:** дешёвая генерация больших log rows/расход БД и возможное накопление лишних платёжных/персональных данных. Тело также целиком читается в память до проверки подписи. Это **не бесконечный body**: приложенный nginx имеет общий лимит 25 MB (`deploy/nginx.conf:50`); лимиты других ingress неизвестны. Но 25 MB значительно выше предполагаемых 20 KB лога.

**Исправление:** provider-specific body limit до полной буферизации, rate limit для rejected webhook, allowlist полей и итоговый byte cap после нормализации JSON, TTL/partitioning логов. Сохранять компактный диагностический след отказа, а не весь неподтверждённый payload.

### S13. Helper: durable offsets фиксируют чтение, а не успешную доставку

**Места:** `uploader/colonial_helper.py:424, 7014–7036, 7244–7248, 7288, 9253–9280`; shutdown — `_on_close` с `5462`.

После ошибки upload доставки остаются в `_pending_watcher_deliveries` в памяти; прочитанные offsets отдельно сохраняются на диск. При crash/закрытии между фиксацией чтения и успешной повторной отправкой restart может продолжить после недоставленных событий. Очередь также обрезается до `WATCHER_PENDING_LIMIT`. `_on_close` не выполняет явный stop/join watcher и не ждёт полного drain dispatcher.

**Класс:** риск потери данных, не доказанная атака. Наличие других persistent collectors не делает эту конкретную очередь durable. Полный автоматический replay/reconciliation может в отдельных сценариях восстановить данные; это не заменяет гарантию ACK/outbox. Crash-reproduction на Qt не выполнялся.

**Исправление:** persistent outbox с source_hash, атомарная запись события/позиции; отдельно read offset и acknowledged offset; удалять outbox-запись только после ACK. Graceful shutdown с timeout и сохранением недосланного; bounded queue должна сигнализировать о потере, а не молча вытеснять данные.

**Регрессия:** kill после чтения, после outbox commit, после серверного ACK до локального ack; offline → restart → reconnect; отсутствие дублей и потерь.

### S14. Свежий npm audit обнаруживает уязвимые версии

## 4. Дополнительные наблюдения — не смешивать с доказанной эксплуатацией

### O01. Stripe completed приравнивается к paid без проверки payment_status

`src/lib/billing/providers.ts:297–303`: подписанный fixture `checkout.session.completed` с `payment_status='unpaid'` принят как `paid`; подпись с локальным тестовым секретом корректно проверялась. Следует проверять payment_status и для отложенных методов ждать `async_payment_succeeded`. Сейчас createPayment ограничивает методы картами: доступность реального delayed-сценария в этой конфигурации **не установлена**. Это не возможность подделать Stripe-подпись.

### O02. Общие инварианты webhook реализованы только для Т-Банка

`src/app/api/billing/webhooks/[provider]/route.ts:49–71`: при наличии parsed intentId выбирается заказ без обязательной общей проверки provider/external ID/amount/currency. S05 — конкретная опасная комбинация. Для прочих драйверов одних этих строк недостаточно, чтобы объявлять произвольное бесплатное пополнение: подписи/API-проверки действительно есть. Рекомендуется единый контракт verified payment facts для всех драйверов.

### O03. «Мои проекты» не ограничены владельцем текущего аккаунта

`src/app/api/projects/active/route.ts:61–66, 105–112`: любая авторизация достаточна для запроса произвольного `cmdr`, затем выполняется `ilike('commander', cmdr)` без привязки к caller. `%`/`_` являются SQL LIKE wildcards. Комментарий обещает account binding, которого запрос не реализует. При этом те же стройки доступны публично по системе: **не считать всё содержимое секретным**, риск прежде всего в обходе заявленной привязки и удобной агрегации. Использовать проверенную связь user↔commander, точное сравнение либо явно документировать публичность.

### O04. Проверка CMDR в Helper выполняется после hooks

`uploader/colonial_helper.py:9172–9199`: `dispatcher.submit`, tracking/exobiology/collector hooks вызываются в `parse_events` до отказа при несовпадении CMDR. Доставки ниже действительно отсекаются, но уже выполненные побочные эффекты не откатываются. Доказан порядок вызовов; реальный чужой outbound report/crash не воспроизводился. Нужно валидировать identity до side effects либо сначала собирать эффекты и применять после проверки.

## 5. Что проверено и не объявляется дырой

- В административных ship image routes есть `requireAdmin`; в translate — `requireStaff`.
- Bulk-folder route ограничивает имена регулярным выражением: простого доказанного path traversal не найдено.
- EDDN ingest проверяет секрет; cron auth fail-closed и использует безопасное сравнение.
- Платёжные драйверы проверяют подпись либо запрашивают API поставщика. S05/O02 — ошибки привязки и инвариантов, **не отсутствие всякой проверки webhook**.
- Т-Банк имеет заметно более строгую сверку суммы/заказа/провайдера и redaction логов; его гарантии нельзя автоматически распространять на другие драйверы.
- MIME/extension без sniffing недостаточно, чтобы заявить XSS или выполнение загруженного файла. Для галереи подтверждены другие дефекты.
- Ранее исправленные profile-role/credentials RLS нельзя считать повторно открытыми только из-за старого названия миграции. Проверенные существующие credential-hardening тесты проходят.
