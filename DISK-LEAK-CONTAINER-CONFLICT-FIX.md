# «Переборка съедает 5–10 ГБ, а таких папок нет» + конфликт имени контейнера

Прод-инцидент: обновление через админпанель отработало сборку (536 с), выгрузило
образ — и упало на переключении:

```
02:41:32 Container src-web-1 Stopping
02:41:32 Container 548bf7698162_src-web-1 Recreate
02:42:23 Container 548bf7698162_src-web-1 Error response from daemon:
         Error when allocating new name: Conflict. The container name
         "/src-web-1" is already in use by container "548bf7698162af96…"
02:42:23 Container src-web-1 Error Error while Stopping
! ОШИБКА: переключение контейнеров — код 1
```

Параллельная жалоба: каждая переборка забирает 5–10 ГБ, при этом `du` не
показывает ни одного каталога такого размера, а по подсчётам «не хватает»
порядка 200 ГБ.

Это **одна и та же поломка** плюс две диагностические слепые зоны.

---

## 1. Почему падает переключение

`docker compose up -d` пересоздаёт контейнер в три приёма:

1. остановить старый (`docker stop`, таймаут по умолчанию **10 секунд**);
2. переименовать его в `<12 hex>_<имя>` — освободить имя;
3. создать новый контейнер под освободившимся именем.

На этом сервере диск перегружен настолько, что даже `COPY` слоёв в сборке
занимал 17–102 секунды (видно в журнале: `[runner 10/10] RUN chmod 0755 … DONE
102.4s`). Web не успевает завершиться за 10 с: демон остаётся в состоянии
«Stopping», переименование не доводится до конца, а шаг 3 упирается в занятое
имя — «Conflict … /src-web-1 is already in use». Между «Stopping» и ошибкой в
журнале ровно **51 секунда** — это и есть зависший stop.

Итог: час сборки выброшен, сайт остаётся на старом контейнере (часто уже
переименованном), обновление отчитывается кодом 1.

## 2. Почему от этого тает диск (и почему «папок таких нет»)

После срыва на хосте **остаётся старый контейнер** `548bf7698162_src-web-1`.
Он ссылается на **предыдущий образ** `src-web`. Значит:

* `docker image prune -f` не может его удалить — образ «используется»;
* `docker builder prune` к образам отношения не имеет;
* новый образ при этом уже собран и лежит на диске.

Каждая такая переборка добавляет на диск **целый образ web** (1.5–3 ГБ) плюс
свежие записи кэша BuildKit. И ни один каталог проекта не растёт: всё лежит
слоями в `/var/lib/docker/overlay2`, где `du` по проекту ничего не видит.
Отсюда «5–10 ГБ за проход при пустых папках».

Плюс ранее разобранные источники (см. `DISK-LEAK-CACHE-MOUNTS-FIX.md`):
кэш-маунты `/app/.next/cache` и `/root/.npm`, которые не подрезает
`docker builder prune`.

## 3. Откуда берутся «200 ГБ, которых нет ни в одной папке»

`du` и `df` считают разное. Две причины дают ровно этот симптом, и обе теперь
проверяются отчётом:

* **Удалённые, но ещё открытые файлы.** Файл удалён, а процесс (dockerd,
  контейнер, pg_dump) держит дескриптор: место занято, в каталогах файла нет.
  Возвращается перезапуском держащего процесса.
* **Файлы, спрятанные под точкой монтирования.** Данные записаны в каталог
  до того, как поверх него смонтировали диск. Для этого проекта — самый
  вероятный случай: `GALAXY_DATA_HOST_DIR=/mnt/sdb/ed-ring-colony/spansh`,
  дампы Spansh по ~6 ГиБ каждый. Если `/dev/sdb1` когда-то не был
  смонтирован, дампы ушли на **корневой** диск и теперь невидимы: `du` по
  пути показывает содержимое смонтированного диска, а место на корне занято
  навсегда. Несколько таких заходов — это и есть сотни гигабайт.

## Что исправлено

**`deploy/compose-lib.sh`**

* `edrc_compose_switch compose <аргументы> -- сервис…` — переключение
  контейнеров:
  1. снимает остатки прошлых срывов (`--force`);
  2. явно останавливает сервисы с таймаутом `UPDATE_STOP_TIMEOUT`
     (по умолчанию **120 с** вместо десяти) — у остановленного контейнера
     гонки переименования не существует;
  3. выполняет прежний `up -d --no-build …`;
  4. при «Conflict … already in use» / «Error while Stopping» снимает
     конфликтующий контейнер (и по имени, и по id из текста ошибки) и
     повторяет — `UPDATE_SWITCH_RETRIES` (по умолчанию 2).
     Любая другая ошибка возвращается как раньше.
* `edrc_remove_stale_containers [--force]` — снятие контейнеров-остатков
  `<id>_<имя>`. Без `--force` работающий остаток не трогается: на нём сейчас
  живёт сайт.
* `edrc_resolve_name_conflicts` — разбор текста ошибки демона.
* `edrc_prune_anonymous_volumes` — удаление **только** анонимных томов-сирот
  (имя — 64 hex). Именованные (`galaxy-dump`, `uploader-store`) не трогаются
  никогда; обычный `docker volume prune` их бы снёс.
* `edrc_cleanup_docker_disk` снимает остатки **до** `image prune` — иначе
  старый образ считается используемым и его гигабайты не возвращаются.

**`deploy/update-project.sh`**, **`deploy/rebuild-now.sh`** — переключение
идёт через `edrc_compose_switch` (с запасным прежним путём, если в дереве нет
`compose-lib.sh`).

**`deploy/docker-disk-report.sh`** — новые разделы: остатки переключений,
образы и висячие образы, именованные/анонимные тома, **удалённые, но открытые
файлы** и **файлы, спрятанные под точками монтирования**, крупнейшие каталоги
корня. `--wipe` дополнительно снимает остановленные остатки, висячие образы и
анонимные тома. Попутно исправлено: функция-заголовок называлась `head` и
перекрывала системный `head`, из-за чего `| head -n N` внутри скрипта печатал
заголовок вместо усечения вывода.

**`.env.example`** — `UPDATE_STOP_TIMEOUT`, `UPDATE_SWITCH_RETRIES`,
`UPDATE_SWITCH_RETRY_DELAY`, `UPDATE_PRESTOP`.

**`scripts/tests/compose-switch.test.mjs`** — сценарии на заглушках docker:
длинный стоп перед переключением, разбор конфликта и повтор, неустранимая
ошибка по-прежнему возвращает код 1, работающий остаток не снимается фоновой
уборкой, именованные тома переживают уборку, порядок «остатки → image prune».

## Что сделать на сервере прямо сейчас

```bash
cd /opt/ed-ring-colony/src
git pull                       # или кнопка «Обновить сейчас»

# 1. Снять зависший остаток и вернуть место (сайт поднимется заново ниже):
docker ps -a | grep -E '^[0-9a-f]+_src-'      # посмотреть остатки
sudo bash deploy/docker-disk-report.sh        # полный разбор, без изменений
sudo bash deploy/docker-disk-report.sh --wipe # вернуть место

# 2. Поднять стек штатно:
docker compose --env-file .env.production -f docker-compose.yml \
  --profile monitoring up -d --no-build web jobs monitor-agent
```

В отчёте обратите внимание на два новых раздела:

* «удалённые, но ещё открытые файлы» — если там гигабайты, перезапустите
  держащий процесс (чаще всего `systemctl restart docker`);
* «файлы, СПРЯТАННЫЕ под точками монтирования» — если там всплыли сотни
  гигабайт под `/mnt/sdb/...`, это старые дампы Spansh на корневом диске:

```bash
sudo mkdir -p /mnt/rootview && sudo mount --bind / /mnt/rootview
sudo du -shx /mnt/rootview/mnt/sdb/ed-ring-colony/spansh/*   # проверить, что это
sudo rm -rf  /mnt/rootview/mnt/sdb/ed-ring-colony/spansh/*   # только после проверки
sudo umount /mnt/rootview
```

## Если переключение всё же конфликтует

Повторы и снятие конфликтующего контейнера теперь встроены, но при совсем
медленном диске поднимите таймаут остановки в `.env.production`:

```ini
UPDATE_STOP_TIMEOUT=300
UPDATE_SWITCH_RETRIES=3
```

Корневая причина медленной остановки — перегруженный диск. Если
`deploy/docker-disk-report.sh` показывает заполнение >85 %, сначала верните
место: на забитом диске рвутся и сборка («DeadlineExceeded»), и остановка.
