# «Кэш сборки минимальный, а диск тает»: 1–2 ГБ за каждую переборку

Симптом из прод-инцидента: после каждой пересборки через админпанель свободное
место уменьшалось на 1–2 ГБ; за пару дней активных переборок «в никуда» ушло
порядка 60 ГБ. При этом `docker system df` показывал минимальный кэш сборки,
`docker builder prune`/`docker image prune` выполнялись (скрипты обновления
их и так зовут — см. MONITORING.md → «Уборка диска после обновления»), а место
не возвращалось.

## Причина: кэш-маунт `.next/cache` + Turbopack из Next 16.3

Два фактора сложились вместе.

**1. Next.js 16.3 включает персистентный кэш сборки Turbopack по умолчанию.**
В пакете `next@16.3.5` в дефолтах конфигурации
(`dist/server/config-shared.js`):

```js
turbopackFileSystemCacheForDev: true,
turbopackFileSystemCacheForBuild: true,   // ← начиная с 16.3 включено
```

Каждый `next build` теперь выгружает кэш компиляции в **`.next/cache`**
(официальный блог Next.js 16.3: «The cache lives in .next/cache»). Записи
ключуются содержимым: переборка с изменившимися исходниками дописывает новые,
а старые никто не удаляет — кэш только растёт.

**2. Dockerfile монтирует `.next/cache` как постоянный кэш-маунт BuildKit:**

```dockerfile
RUN --mount=type=cache,target=/app/.next/cache npm run build
```

Маунт живёт между сборками (это его смысл — он переживает даже `--no-cache`),
но **`docker builder prune` его надёжно не подрезает**:

- кэш-маунт — ОДНА запись кэша целиком; `--keep-storage` срезает старейшие
  записи до бюджета, а кэш-маунт, которого касалась последняя сборка, всегда
  «самый свежий» — он остаётся последним и расти может без предела;
- на части демонов кэш-маунты вообще не попадают в `docker system df`
  (классическое «место ушло в никуда, а видимый кэш минимальный»).

Итог: каждая переборка дописывает в невидимый каталог на гигабайт и больше,
`docker system df` при этом честно показывает маленький кэш слоёв, и все
существующие уборки проходили мимо проблемы. ~40 переборок за пару дней
и дали ~60 ГБ.

Второй, меньший по масштабу, но реальный источник: **дамп БД перед
обновлением** делался ПОЛНЫМ (`pg_dump -Fc` без исключений), хотя ручной бэкап
(`deploy/db-backup.sh`) каталог систем `public.galaxy_systems` исключает —
тот весит десятки гигабайт и полностью восстанавливается импортом дампа
Spansh. Каждая переборка с включённым флажком «с бэкапом БД» писала полную
копию базы (ротация держала 5 таких дампов).

## Что исправлено

- **`deploy/compose-lib.sh`** — новая `edrc_trim_cache_mounts`: измеряет и
  держит в бюджете оба кэш-маунта (`/app/.next/cache` и `/root/.npm`).
  Единственный переносимый способ добраться до кэш-маунта — синтетическая
  сборка с тем же `target` (кэш-маунты с одним id = пути общие для всех
  сборок одного BuildKit). Подключена в `edrc_trim_build_cache` (до сборки)
  и `edrc_cleanup_docker_disk` (после переключения и после КАЖДОЙ сорвавшейся
  попытки). Бюджеты: `UPDATE_NEXT_CACHE_KEEP` / `UPDATE_NPM_CACHE_KEEP`
  (по умолчанию `2g` каждый); при тесном диске кэш-маунты вычищаются целиком.
  Размеры пишутся в журнал обновления: «`кэш-маунт /app/.next/cache: N КБ
  (бюджет …)`».
- **`deploy/update-project.sh`** — дамп перед обновлением больше не включает
  `public.galaxy_systems` (та же политика, что у ручного бэкапа); полный дамп —
  осознанный `BACKUP_FULL=1`. В журнал добавлен размер каталога копий.
- **`deploy/docker-disk-report.sh`** (новый) — разбор «куда ушло место»:
  `df`, `docker system df`, `du` по `/var/lib/docker`, размеры контейнеров
  с журналами, размеры кэш-маунтов и бэкапов; `--wipe` вычищает кэш-маунты.
- **`.env.example`, `DEPLOY.md`, `MONITORING.md`** — документация бюджетов и
  диагностики.

## Как проверить на сервере (до и после обновления)

```bash
# 1. Посмотреть, где на самом деле место (нужны docker; для du — root):
bash deploy/docker-disk-report.sh

# Ожидаемая картина проблемы: строка вида
#   кэш-маунт /app/.next/cache: 60000000 КБ (бюджет 0 КБ)
# при «минимальном» кэше сборки в docker system df, плюс большой /var/lib/docker/overlay2.

# 2. Разово вернуть место (дальше это делают скрипты обновления сами):
bash deploy/docker-disk-report.sh --wipe

# 3. После обновления проекта — журналы переборки содержат строки
#    «кэш-маунт …: N КБ (бюджет …)», и место больше не уходит.
```

Альтернативный разовый способ вычистить кэш-маунты руками (то же самое, что
делает `--wipe`):

```bash
ctx=$(mktemp -d)
{ echo 'FROM node:22-alpine'
  echo 'RUN --mount=type=cache,target=/app/.next/cache find /app/.next/cache -mindepth 1 -delete'
  echo 'RUN --mount=type=cache,target=/root/.npm find /root/.npm -mindepth 1 -delete'
} > "$ctx/Dockerfile"
DOCKER_BUILDKIT=1 docker build --rm -f "$ctx/Dockerfile" "$ctx"; rm -rf "$ctx"
```

## Что не менялось

Кэш-маунты в Dockerfile сохранены: с Next 16.3 кэш Turbopack в `.next/cache`
заметно ускоряет тёплые пересборки. Меняется не механизм, а отсутствие бюджета:
теперь кэш-маунт сверх бюджета вычищается (следующая сборка становится
«холодной» по этому кэшу — плата за место). `npm ci`-кэш `/root/.npm`
контент-адресуемый и обычно стабилен, но тоже получил бюджет на случай
миграций зависимостей.

Отключить кэш Turbopack для сборки можно и на уровне Next.js:

```js
// next.config.mjs
experimental: { turbopackFileSystemCacheForBuild: false },
```

— тогда `.next/cache` при сборках не пишется вовсе (за счёт скорости тёплых
переборок). По умолчанию оставлено как у Next 16.3 (включено) + бюджет.
