# Аватар и оформление эскадры: лимиты и недоступность Storage

## Изменения приложения

- Аватар: **5 МиБ (5 × 1024 × 1024 байт)** включительно. Общий лимит UI/API,
  подсказки на всех языках, бакет `avatars` и резервная таблица согласованы.
- Логотип: 2 МиБ; фон: 6 МиБ (прежние лимиты).
- JPG, PNG, WebP, GIF. SVG и другие заявленные MIME отклоняются.
- Оба загрузчика используют общий обработчик Storage: создают отсутствующий
  бакет, повторяют загрузку при гонке создания и обрабатывают сетевые исключения.
- Если Storage отклоняет загрузку или отвечает 5xx, оформление сохраняется в
  `squadron_images` (по одной текущей картинке каждого вида на эскадру).
  Ответ содержит `storage: "database"` и предупреждение, которое показывает UI.
  При отказе обоих хранилищ ссылка на прежнее изображение не обновляется.
- Изображение отдаётся через `/api/squadrons/<id>/images/logo|banner?v=<sha256>`.
  Чтение публичное, как и оформление эскадры; таблица недоступна браузерным ролям.
  Запись разрешает сервер только создателю/участнику с `can_edit_squadron`.
  Удаление очищает соответствующую резервную строку; удаление эскадры — обе строки.
- Ответы картинок содержат MIME, `nosniff`, ETag и 304; immutable-кэш используется
  только для совпадающей версии. Старый URL не получает новые байты под старой версией.

Это **резервный путь, не ремонт Supabase Storage**. Ранее загруженные только в
Storage файлы по-прежнему зависят от его доступности; приложение не может
восстановить недоступные байты. Автоматического переноса резервных файлов обратно
в Storage нет. При следующей загрузке после восстановления используется Storage.

## Развёртывание

Сначала применить `supabase/migrations/20261024120000_profile_squadron_images.sql`
к существующей БД, затем обновить приложение. Нужны предыдущие миграции с
`squadrons` и `profile_avatars`. Миграция идемпотентна, включена в
`supabase/full_schema.sql` для новых установок; полный снимок не следует применять
вместо одной миграции к рабочей базе.

```bash
# Из каталога репозитория на сервере. Имя контейнера уточнить через docker ps.
docker exec -i supabase-db psql -U postgres -d postgres -v ON_ERROR_STOP=1 \
  < supabase/migrations/20261024120000_profile_squadron_images.sql
```

Скрипт не удаляет/перемещает объекты Storage. Если Storage ещё не установлен,
создание бакетов пропускается: приложение создаст их при первой успешной загрузке.
При работающем Storage обновляются существующие ограничения бакетов, в том числе
старый лимит аватара 1 МиБ. Глобальный `FILE_SIZE_LIMIT` сервиса Storage должен быть
**не меньше 6291456**. Лимит reverse proxy — больше 6 МиБ с запасом на multipart;
в шаблонах nginx проекта он уже 25m. Не уменьшайте больший существующий лимит.

> **Появился штатный путь починки:** Админка → Мониторинг → «Хранилище файлов» —
> проверка (состояние контейнера + ответ API `/bucket`) и перезапуск только
> сервиса `storage`, а также сторож и проверка после обновления. Устройство и
> ручные команды — в [STORAGE-RESTART.md](STORAGE-RESTART.md). Раздел ниже
> остаётся полным порядком ручного разбора: он нужен, когда перезапуск не помог.

## «Failed to retrieve buckets» в Studio / «Service Unavailable» при загрузке

Это не доказательство отсутствия бакета. Ошибка списка бакетов означает, что
Studio не смогла получить ответ Storage; 503 часто связан с неработающим upstream
Kong, но точную причину можно установить только по состоянию и логам сервера.
Создание бакета или увеличение лимита не исправляет остановленный сервис.

1. В каталоге **Supabase**, а не compose сайта (обычно `/opt/supabase`), проверить:

   ```bash
   docker compose ps -a storage kong db imgproxy
   docker compose logs --tail=100 storage
   docker compose logs --tail=100 kong
   df -h
   df -i
   ```

   Имена сервисов зависят от установки. Просматривайте логи локально; не публикуйте
   JWT, пароли БД, service-role ключи, полный `.env` или `docker inspect` с окружением.

2. В Storage искать причину остановки/рестартов: отказ соединения с БД,
   несовпадающий пароль роли `supabase_storage_admin`, незавершённые внутренние
   миграции Storage, ошибки доступа к `/var/lib/storage`, переполненный диск/inodes.
   Проверить владельца и права **существующего** тома. Не делать `chmod -R 777`,
   не удалять тома/бакеты, не использовать `docker compose down -v`.

3. Если Storage здоров, проверить доступ Kong к `storage:5000` в общей Docker-сети,
   upstream `/storage/v1/`, фактически используемые compose overrides и внутренний
   URL API в Studio. Убедиться, что JWT secret/service-role ключи согласованы между
   сервисами. **Не менять ключи наугад**: это ломает остальные сервисы и сессии.
   Если через gateway бакеты читаются, а Studio всё ещё выдаёт ошибку, проверить
   запрос в Network браузера, его HTTP-статус и настройки API URL Studio/proxy.

4. После устранения конкретной причины запустить остановленный Storage:

   ```bash
   docker compose up -d storage
   docker compose ps storage
   ```

   Если меняли окружение Storage — пересоздать только этот сервис штатным compose
   (`docker compose up -d --no-deps --force-recreate storage`). Перед операциями с
   томами/миграциями сделать резервную копию БД **и** файлов Storage.

5. Проверить Studio → Storage и загрузки аватара/логотипа/фона с обычного аккаунта.
   При живом хранилище ответ API содержит `storage: "storage"`; при резервном —
   `storage: "database"`. Проверить файл в новом окне и повторную загрузку/удаление.

Из среды разработки рабочая инфраструктура не проверялась и не изменялась.
Для дальнейшего разбора достаточно HTTP-статуса запроса списка бакетов, статуса
контейнера Storage и текста ошибки из его логов **без секретов**.

## Проверки

```bash
npm test -- avatar-squadron squadron-images migrations-sql
npm run typecheck
```

Тесты выполняют реальные route handlers с подменой Storage/БД и миграцию в PGlite:
5 МиБ и превышение лимита, 503/сетевые исключения, создание бакета, права редактора,
логотип/фон, отдача байтов/ETag, замена/удаление, отказ БД, SQL-лимиты и запрет
прямого доступа к резервной таблице. Это не заменяет проверку живого Storage.

## Точная диагностика действующей установки (без перезапуска)

Скрипт `deploy/selfhost/storage-check.py` проверяет именно **чтение списка бакетов**,
а не возможность резервной загрузки в БД. Запускать на Docker-хосте Supabase из
каталога репозитория, содержащего эту версию файлов:

```bash
sudo python3 deploy/selfhost/storage-check.py
# Если найдено несколько стеков — выбрать Compose project, не имя каталога:
sudo python3 deploy/selfhost/storage-check.py --project supabase
```

Python 3.8+, без pip-зависимостей. Рядом должен находиться `realtime-check.py`:
используются общие функции безопасного чтения Docker metadata. Не запускайте
установщик повторно ради диагностики. Скрипт не требует передавать ключи вручную:
читает окружение действующих контейнеров только в память. Проверяет GET `/bucket`
на внутреннем Storage и GET `/storage/v1/bucket` через локальный Kong, дополнительно
проверяет ключ Studio напрямую на Storage. Запросов к публичному домену нет,
редиректы не выполняются. Имена бакетов, пароли, JWT, сырые логи и тела ответов в
JSON-отчёт не попадают. Логи за последние 30 минут сводятся к признакам ошибок;
отсутствие признака **не доказывает** отсутствие ошибки при более раннем запуске.

| `diagnosis` | Где искать дальше |
|---|---|
| `STORAGE_STOPPED_CHECK_LOG_SIGNALS` | Storage остановлен; статус, рестарты, OOM и ошибки запуска |
| `STORAGE_DIRECT_FAILED_CHECK_AUTH_DB_AND_LOGS` | Не сработал сам API Storage. 401/403: ключ/роль/подпись/срок; 5xx: БД, внутренние миграции, права; ошибка соединения: порт, сеть, firewall или процесс |
| `STORAGE_WORKS_CHECK_KONG_ROUTE_NETWORK_AND_KEY` | Напрямую бакеты читаются, через Kong нет: upstream, `/storage/v1/`, общая сеть, ключ Kong |
| `CHECK_STUDIO_SERVICE_KEY_OR_MISSING_STUDIO` | Storage и Kong отвечают, но ключ Studio отсутствует/не принимается или контейнер Studio не найден |
| `LOCAL_STORAGE_AND_KONG_OK_CHECK_STUDIO_URL_AND_BROWSER_REQUEST` | Локальные API работают; проверить внутренний `SUPABASE_URL` Studio, DNS из её контейнера и HTTP-запрос с ошибкой в браузере |

`studio_api_url_is_internal_kong=false` не является автоматическим диагнозом:
нестандартная сеть может иметь другой корректный URL. Равенство ключей тоже не
обязательно при намеренной ротации; решающим является ответ API. Нестандартные
opaque/asymmetric ключи не проверяются как HS256 — соответствующие поля `null`.
Код выхода 0 означает успешные локальные проверки, 1 — обнаруженную проблему или
пропущенный необходимый запрос, 2 — невозможность диагностики/неоднозначный стек.

**Что показала проверка исходников, а не сервера:**

- `install.sh` скачивал Supabase compose отдельно, из актуального на момент
  установки `supabase/supabase`. Действующие версии и настройки нельзя установить
  по одному репозиторию сайта. Повторный запуск установщика может переписать `.env`
  из файла секретов установки — поэтому это не безопасный способ «починить Storage».
- `upgrade.py` останавливает Storage на время резервной копии и запускает его в
  `finally`. Это не доказательство исправной работы после запуска: нужно проверить
  состояние, health и запрос к `/bucket` на действующем контейнере.
- Ограничения размера тела nginx/Storage не объясняют отказ обычного GET списка
  бакетов. Увеличивать их или создавать бакеты до локализации сбоя бессмысленно.

При успешных локальных проверках пришлите из браузера **только путь** запроса Studio
с ошибкой (без query-параметров), HTTP-статус и обезличенный текст ошибки. Не
передавайте HAR, заголовки Authorization/Cookie, JWT или service-role ключи.

Тесты диагностического скрипта: `node --test scripts/tests/storage-check.test.mjs`.
Они проверяют классификацию, подписи JWT, запрет публичных адресов/редиректов,
отсутствие секретов в отчёте и отказ при неоднозначном выборе стека.
