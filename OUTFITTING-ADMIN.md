# Админ-панель верфи

## Где находится

`/admin?tab=outfitting` → **Игровые данные → Верфь**. Доступ на рабочем сайте — только пользователям с `profiles.role = admin`. Модераторы и сотрудники поддержки не могут читать административный каталог или менять его через API.

Навигация `/admin` сгруппирована: контент сайта, сообщество, игровые данные, система и сервисы. Выбранный раздел записывается в `?tab=...`; обновление страницы и кнопки браузера «назад/вперёд» его сохраняют.

## Что можно делать

- **Корабли:** добавлять (шаблон Sidewinder), копировать существующие, редактировать имя, производителя, размер, стоимость, характеристики корпуса, слоты и заводскую комплектацию. Основные слоты фиксированы (7); любой орудийный/вспомогательный или внутренний слот можно добавить и удалить кнопкой в его строке, а специальные слоты — ограничивать списком допустимых групп. После сохранения корабль сразу появляется в публичном конструкторе. Броня нового корабля копируется из шаблона, далее редактируется отдельно на вкладке «Броня».
- **Архив кораблей и слотов:** удалённый корабль больше не предлагается при создании сборки, но остаётся в публичном каталоге с меткой `archived: true`: старые ссылки и сохранённые сборки по-прежнему открываются. Его можно восстановить, а правки игрового корабля — сбросить к источнику. Нельзя архивировать последний доступный корабль. Удаление уже сохранённого орудийного или внутреннего слота **архивирует** его на прежнем индексе: в новых сборках слот исчезает, а модуль из старой ссылки остаётся видимым и учитывается в расчёте. Переключатель «Показать удалённые слоты» позволяет восстановить слот. Ещё не сохранённые слоты удаляются из массива окончательно (вместе с заводским модулем); остальные новые слоты переиндексируются. При копировании корпуса архивные слоты пропускаются: новый ID не связан со старыми сборками. Семь основных слотов удалять нельзя. **Сброс корпуса к исходному** удалит и вручную добавленные слоты — админка предупреждает, что сборки с оборудованием в этих слотах могут его потерять.
- **Модули:** добавлять, переименовывать, редактировать, копировать, удалять по одному или выбранной пачкой (до 100 записей), восстанавливать из архива.
- **Параметры:** класс, рейтинг, крепление, масса, цена, потребление, прочность, Powerplay, Merc Coin, примечания и все числовые поля группы. Можно добавить дополнительный числовой параметр.
- **Крепление** — буква, как в игровых символах модулей: **F** — фиксированное (`Hpt_PulseLaser_Fixed_Small`), **G** — наводящееся (`…_Gimbal_…`), **T** — турель (`…_Turret_…`); турельное орудие всегда дороже наводящегося. Подписи таблицы и редактора — `CATALOG_MOUNTS` в `src/lib/outfitting/catalog.ts`, публичной верфи на всех языках — `MOUNT_NAMES` в `src/lib/outfitting/i18n.ts`; тесты сверяют их между собой и с символами. До web 2.25.1 и админка, и публичная верфь подписывали G и T наоборот: если модуль добавляли или правили, выбирая крепление по подписи, проверьте у него букву.
- **Заводская инженерия:** чертежи, уровень, экспериментальные эффекты, ограничения переделки, описание, рецепт, доступность, приблизительные значения и дополнительные модификаторы.
- **JSON:** полная запись для нестандартных строковых/объектных полей. Редактор не выбрасывает неизвестные поля при изменении обычных параметров. Невалидный JSON или типы не сохраняются.
- **Группы:** создавать, переименовывать, копировать, менять короткое название; удалять пустые группы, не связанные с обязательными слотами и инженерными чертежами. Новые группы поддерживают внутренние модули, вооружение и утилиты. Новые основные группы не создаются: основные слоты жёстко определены калькулятором.
- **Броня:** каталог переборок всех кораблей с добавлением, изменением, копированием, архивированием и восстановлением. Базовую броню корабля нельзя удалить. Архивная броня не предлагается для новой установки, но её параметры и индекс остаются в старых сборках; при удалении массив не сдвигается.
- **Сброс к исходному:** для изменённой игровой записи отменяет ручные правки и берёт данные из текущего исходного справочника. Для добавленных записей доступно обычное архивирование/восстановление.
- **Поиск и списки:** категории, группа/корабль, производитель, класс/размер, рейтинг, состояние, сортировка, пагинация 25/50/100 строк. Фильтр «Удалённые» открывает архив.
- **Экспорт:** полный справочник в JSON; содержит текущие правки, архивные корабли и переборки. Это экспорт для проверки/внешнего использования, а не кнопка импорта базы. Постоянные правки резервируются вместе с таблицей БД.
- **Журнал:** последние 100 операций, администратор, время, запись и тип действия.

Технические ID существующих кораблей/модулей/групп/брони не меняются, поскольку они используются в кодах сборок. Для другого ID или группы создайте копию. Броня редактируется отдельно от параметров корпуса: сброс брони не теряется после редактирования корабля, а пересборка исходного файла не стирает правки. Переименование группы имеет приоритет над встроенным словарём названий и видно в публичной верфи.

Сопротивления и процентные бонусы в обычной форме вводятся в **процентах**. В JSON используются игровые **доли**: `0.25` = 25%. Пустое числовое поле означает отсутствие параметра, а `0` — заданный ноль.

## Хранение и развёртывание

Исходный `public/data/outfitting.json` по-прежнему собирается из EDCD/Coriolis и **не изменяется** при сохранении из админки. Ручные записи, архивные метки и журнал лежат отдельно в `public.outfitting_catalog` (одна строка, `revision`, JSONB). Пересборка исходного справочника не удаляет ручные правки и не возвращает архивные корабли или модули в выбор верфи. После замены исходника перезапустите веб-сервис, чтобы он подхватил новую базовую версию.

Перед использованием на рабочем сервере примените:

```
supabase/migrations/20261010010000_outfitting_catalog.sql
```

Миграция идемпотентна, включена в `supabase/full_schema.sql` и подхватывается штатным `deploy/update-project.sh` при включённом `UPDATE_APPLY_MIGRATIONS=1`. Сохранённые пользовательские сборки она не меняет. Нужны уже используемые `SUPABASE_SERVICE_ROLE_KEY` и `SUPABASE_INTERNAL_URL` или `NEXT_PUBLIC_SUPABASE_URL`; новых секретов нет.

Таблица защищена RLS; `anon` и `authenticated` не имеют прямых прав даже на чтение журнала. Серверный API сначала проверяет сессию и роль и только затем обращается к service-role клиенту. Публичный API не выдаёт журнал и имена администраторов.

Если в production не настроен service-role клиент, публичная верфь продолжает читать исходный справочник, а админка явно показывает режим просмотра без сохранения. Если БД настроена, но недоступна/миграция отсутствует, API сообщает об ошибке: тихого сохранения на диск или выдачи устаревшего исходника вместо удалённых записей нет.

### Локальная разработка

При `NODE_ENV=development` без service-role ключа каталог сохраняется атомарно в игнорируемый Git каталог `data/outfitting/catalog.json`. Это только локальное окружение, **не рабочий сайт**. Для тестов путь можно переопределить `OUTFITTING_DATA_FILE`. Анонимный preview-доступ разрешён только в development без service-role ключа и без переданного Bearer-токена; hostname и `BILLING_PREVIEW_ADMIN` не дают доступа в production.

## API и актуальность данных

- `GET /api/admin/outfitting` — действующий справочник, изменения, архив и журнал.
- `POST /api/admin/outfitting` — JSON `{ revision, commands: [{ action, kind, key, value? }] }`.
  Действия: `create`, `update`, `delete`, `restore`, `reset`; виды: `module`, `group`, `bulkhead`, `ship`.
  Ключи: `группа:ID` для модуля, код группы для группы, `корабль:ID` для брони, неизменяемый slug корабля для `ship`.
- `GET /api/outfitting/catalog` — публичный справочник без административных метаданных; архивные корабли присутствуют с `archived: true` только для чтения старых сборок.

Пачка валидируется целиком и записывается через compare-and-swap по `revision`. Конфликт с другим администратором возвращает **409**, не перезаписывая его работу. Редактор сохраняет введённый черновик и обновляет версию каталога; повторное сохранение — явное действие пользователя.

После сохранения общий клиентский кеш обновляется сразу. Другие вкладки получают уведомление через `storage`; открытая верфь/страница инженеров также перечитывает данные при возвращении на вкладку и каждые 30 секунд. При временной ошибке фоновой загрузки остаётся последняя успешно загруженная версия. Ответы API и browser fetch используют `no-store`.

## Проверки

```bash
node --test scripts/tests/outfitting-catalog.test.mjs scripts/tests/outfitting-ui.test.mjs
npm run typecheck
npm run build
# С запущенным Next-сервером и установленным Chromium:
npm run test:browser -- tests/browser/admin-outfitting.spec.ts
```

Тесты покрывают все 973 исходных модуля и 47 кораблей, CRUD, характеристики и специальные слоты, удаление/восстановление слотов с сохранением индексов старых сборок, архив/сброс корпуса и брони, неизменность исходника, установку новых групп, атомарность пачки, конфликты версий, ограничение прав и production без файлового fallback. Браузерные тесты используют фиктивные API/сессию, без реального входа или записи в рабочую БД.
