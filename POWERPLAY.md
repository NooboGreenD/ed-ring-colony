# PowerPlay на карте Atlas (web 2.17.0)

Вкладка **«PowerPlay»** в Atlas (`/atlas?tab=powerplay`, Alt+7) и слой 3D-карты:
**все системы под контролем держав PowerPlay 2.0** с фильтром по державам и
состояниям.

## Что видит пилот

**На карте** — облако точек поверх галактики:

| Форма | Состояние | Зона влияния |
|---|---|---|
| ★ четырёхлучевая звезда | Оплот (Stronghold) | 30 св. лет |
| ◎ кольцо с ядром | Укреплённая (Fortified) | 20 св. лет |
| • точка | Эксплуатируемая (Exploited) | нет |

Цвет точки — держава (цвета как в игре, подобраны читаемыми на тёмном фоне;
справочник — `POWERPLAY_POWERS` в `src/lib/powerplay.ts`). Клик по точке
открывает карточку системы, у оплота и укреплённой системы вокруг рисуется сфера
её зоны влияния. Переключатель «PowerPlay (N)» есть и в панели слоёв карты.

**Во вкладке:**

* «Показывать на карте» — первый визит включает слой сам и запоминает выбор;
* откуда данные: дата дампа EDSM и диапазон дат наблюдений;
* фильтр состояния — оплоты / укреплённые / эксплуатируемые со счётчиками;
* список держав: цвет, сторона (Империя, Федерация, Альянс, Независимые),
  счётчики по состояниям, флажок «показывать», кнопки «только», «все»,
  «скрыть все». Новая держава, которой нет в справочнике, видна сразу и
  получает цвет из имени;
* «На карте: N из M систем» и список систем под фильтр — сначала оплоты, затем
  укреплённые, внутри по имени; поиск по имени, «показать ещё», выгрузка в CSV.
  Клик по строке ведёт камеру к системе и открывает карточку;
* **«Чья зона? Проверить любую систему»** — любая система галактики (подсказки
  из каталога Spansh/EDSM): под чьим она контролем и чьи оплоты и укреплённые
  системы до неё дотягиваются, с расстоянием до ближайшей и числом зон. Для
  колонизации это ответ на вопрос «какая держава может забрать мою систему».

Фильтр и показ слоя хранятся в `localStorage` (`atlas-powerplay-v1`).

**Карточка системы:** держава и сторона, состояние и его зона, дата наблюдения
EDSM («вчера», «5 дн. назад»), координаты, «Зоны влияния в этой точке» (своя
держава помечена), кнопка «К системе», ссылки EDSM, Inara, Spansh.

## Откуда данные

Ночной дамп EDSM **`https://www.edsm.net/dump/powerPlay.json.gz`**
(~3,6 МБ сжатый, ~25 МБ распакованный, пересобирается раз в сутки). EDSM
получает состояние систем из журналов пилотов через EDDN, в дамп попадают
системы, о которых сообщали за последние ~30 дней. Формат — JSON-массив, по
записи на строку:

```json
{"power":"Edmund Mahon","powerState":"Exploited","id":12031,"id64":58141509045160,
 "name":"Wadjabangai","coords":{"x":-24.53125,"y":-33.78125,"z":108.8125},
 "allegiance":"Independent","government":"Communism","state":"None","date":"2026-09-17 01:49:46"}
```

Разбор — `src/lib/powerplayDump.ts`:

* хранятся только **Stronghold, Fortified, Exploited**. `Unoccupied` отбрасывается:
  у такой системы нет хозяина, а EDSM хранит при ней одну державу из нескольких
  претендентов — показывать её «чьей-то» было бы неправдой;
* имена держав приводятся к написанию журнала (`Arissa Lavigny-Duval` →
  `A. Lavigny-Duval`);
* **id64 читается из текста строки**: адрес системы бывает шире 2^53 и в number
  потерял бы младшие разряды. В базе — `BIGINT`, в API — строка;
* повтор системы — остаётся самое свежее наблюдение; записи без имени,
  координат или id64 и неизвестные состояния считаются по причинам.

Почему не другие источники:

* **Spansh** `galaxy_populated.json.gz` — 4+ ГиБ, `galaxy_1day` — 1,1 ГиБ; на
  канале сервера это часы (полный `systems.json.gz` качался неделю);
* **EDDN** в реальном времени — слушатель на сервере не развёрнут
  (см. `docker-compose.yml`, сервис `eddn-worker` закомментирован);
* **журналы пилотов сайта** — видны только посещённые системы, а нужны все.

## Обновление

`src/lib/powerplaySync.ts`:

1. **Условный запрос**: `If-None-Match` / `If-Modified-Since` по прошлому ответу.
   Неизменный дамп — 304 и одна строка состояния (`checked_at`).
2. Тело читается с пределом 64 МБ; gzip определяется по сигнатуре, а не по имени
   файла (прокси может выставить `Content-Encoding: gzip`, и тело придёт уже
   распакованным), распаковка ограничена 512 МБ.
3. **Защита данных** — таблица не трогается, если:
   * HTTP-ошибка, сеть, таймаут (3 минуты);
   * архив обрезан, тело не JSON-массив (HTML-страница прокси, объект ошибки);
   * систем под контролем меньше 100;
   * новый дамп меньше половины прошлого (сбой источника, а не итог недели).
     Ручной запуск с `force=1` такой дамп принимает.
4. Запись пачками по 2000 строк (`powerplay_apply_batch`) с меткой импорта
   `sync_run`; затем `powerplay_finish_sync` **одной транзакцией** удаляет всё,
   чего в новом дампе нет, и записывает состояние (ETag, Last-Modified, счётчики).
5. Один импорт за раз на процесс: общий «уже идёт» лежит в `globalThis` — у
   маршрутов Next свои копии модуля.

Кто запускает:

* задача **`powerplay-sync`** планировщика — каждые 12 часов (05:20 и 17:20 UTC),
  включена по умолчанию (`scripts/job-schedule.mjs`, `docker-compose.yml`);
* **ленивое обновление** из `GET /api/powerplay/systems`: если таблица пуста или
  источник не проверяли 26 часов, импорт стартует фоном (не чаще раза в 30 минут
  после неудачи, не поверх идущего). Слой работает, даже если задачу не добавили
  в `JOBS_ENABLED`;
* вручную: `node scripts/server-jobs.mjs --once powerplay-sync` или
  `curl -X POST -H "Authorization: Bearer $CRON_SECRET" "https://<site>/api/cron/powerplay-sync?force=1"`.

Ответ задачи: `status` (`ok` / `not_modified` / `error`), записано, удалено,
итого, статистика отбора (`stats.skipped`, `stats.states`, `stats.powers`),
время. Сбой — HTTP 502 и `ok: false`, данные прошлого импорта остаются.

Адрес дампа можно заменить зеркалом: `POWERPLAY_DUMP_URL` (только http/https).

## База

Миграция `supabase/migrations/20261018120000_powerplay_systems.sql` (идемпотентна,
продублирована в `supabase/full_schema.sql`):

* `powerplay_systems` — `id64 BIGINT PK`, имя, `name_lc`, координаты, `power`,
  `power_state` (CHECK: три состояния), сторона, правительство, `observed_at`
  (дата EDSM), `source`, `sync_run`, `updated_at` (двигается только при смене
  державы, состояния, имени или координат). Чтение открыто (публичные игровые
  данные, как каталог систем), запись — только service_role;
* `powerplay_sync_state` — одна строка: статус, ETag/Last-Modified, дата дампа,
  `run_id` (версия набора), счётчики, ошибка, времена попытки, проверки и записи.
  Только service_role;
* `powerplay_apply_batch(uuid, jsonb)`, `powerplay_finish_sync(uuid, jsonb)` —
  импорт; finish отказывается завершать импорт, не записавший ни одной строки;
* `powerplay_layer_rows()` — весь слой одним JSON, по имени: обычная выборка
  PostgREST обрезалась бы `max_rows`.

## API

`GET /api/powerplay/systems` — открыт всем:

```json
{
  "status": "ready",
  "version": "<run_id>",
  "meta": { "source": "edsm", "sourceUrl": "...", "dumpGeneratedAt": "...", "syncedAt": "...",
            "checkedAt": "...", "oldestObservation": "...", "newestObservation": "...",
            "refreshing": false, "lastError": null },
  "powers": ["Nakato Kaine", "Edmund Mahon", "..."],
  "states": ["Stronghold", "Fortified", "Exploited"],
  "systems": [["2557888041682", "Prajan", 56.59375, 139.59375, 10.78125, 1, 0, 1792127099]]
}
```

Кортеж: `[id64, имя, x, y, z, индекс державы, индекс состояния, наблюдение в
unix-секундах | null]` — втрое короче объектов на ~50 тысячах систем. Державы — по
числу систем. Собранный набор держится в памяти процесса до следующего импорта.
`ETag` = импорт + метаданные, повторный визит — 304; готовый набор кэшируется на
5 минут, пустой или обновляющийся — `no-store`. Ошибка источника отдаётся
коротким текстом без адресов («Источник недоступен (HTTP 503)», «Нет связи с
источником данных»).

## Развёртывание

1. Обновить сайт (`deploy/update-project.sh` сам накатит миграцию).
2. Если в `.env.production` задан свой `JOBS_ENABLED`, дописать `powerplay-sync`
   (без этого слой всё равно заполнится ленивым обновлением при первом открытии
   вкладки, но ночное обновление надёжнее).
3. Первый импорт — первое открытие вкладки или `--once powerplay-sync`; занимает
   секунды (3,6 МБ, ~50 тысяч строк).

## Ограничения

* Данные — срез EDSM: система, о которой месяц никто не сообщал в EDDN, из дампа
  выпадает и пропадает со слоя до следующего визита пилота с EDMC/EDDiscovery.
* Нет прогресса контроля (`PowerplayStateControlProgress`, подкрепление,
  подрыв) и захватов свободных систем: в дампе EDSM этих полей нет.
* Зоны влияния считаются по системам слоя; если оплот выпал из дампа, его зона
  в карточке и в «Чья зона?» не учитывается.

Что можно добавить дальше: приём `FSDJump`/`Location` с полями PowerPlay из EDDN
(слушатель уже есть в `scripts/eddn-worker.ts`) — живое состояние, прогресс и
захваты; те же поля из журналов пилотов сайта.
