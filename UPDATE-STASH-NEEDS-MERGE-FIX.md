# «git stash не удался: needs merge»: кнопка «Обновить сейчас» встала намертво

Инцидент на проде 18.11.2026, 23:29 по серверному времени:

```
update requested; project=NooboGreenD/ed-ring-colony branch=main mode=auto
tests=0 backup=0 migrations=1 only=0
compare → 21b2019
! ОШИБКА: git stash не удался (код 1): локальные изменения не тронуты;
  причина: .env.example: needs merge error: could not write index ;
  статус: UD .env.example M supabase/migrations/20260904000000_capi_journal_base.sql
```

Кнопка отказывалась работать снова и снова: каждое нажатие упиралось в тот же
`needs merge`, а сообщение выглядело как «в дереве просто есть правки» — хотя
правки тут ни при чём. Обновление не начиналось ни разу, миграции не
применялись, сайт оставался на прежней ревизии.

## Что на самом деле означал статус

Две буквы в `git status --short` — это ДВА столбца, и читаются они по-разному:

| Запись | Индекс | Рабочее дерево | Смысл |
|---|---|---|---|
| `M ` | изменён | совпадает с индексом | правка **подготовлена** (`git add`) |
| ` M` | без изменений | изменён | обычная непринятая правка |
| `??` | нет | новый файл | файл вне git |
| `U*`, `*U`, `AA`, `DD` | — | — | **записи незавершённого слияния** |

`UD .env.example` — не «файл изменён», а «в индексе лежат стадии конфликта
(`unmerged`), а в рабочем дереве файла нет» (`D`). Пока такая запись есть, git
считает, что в репозитории идёт слияние, и **отказывается писать индекс**:

```
$ git stash push --include-untracked -m update
.env.example: needs merge
error: could not write index
```

Именно поэтому «просто уберите правки» не помогало: `git stash` не начинает
работу. Проверить одной командой:

```bash
git ls-files -u          # пусто = конфликтных записей нет
git status --short | grep -E '^(U|.U|AA|DD)'
```

## Откуда взялись эти записи

Причина — в релизе 2.28.4 (PR #285, коммит `21b2019`). Он **добавил в git**
файл `.env.example` (и миграцию `20260904000000_capi_journal_base.sql`). На
сервере же лежала своя копия `.env.example` — она не отслеживалась
(`.gitignore`: `*.env.*` с исключением `!.env.example`) и в git не попадала.

Дальше сработала цепочка, которую прежний скрипт не предусматривал:

1. обновление прячет локальные правки: `git stash push --include-untracked`
   забирает и `?? .env.example`;
2. `git merge --ff-only` перематывает ветку — теперь `.env.example` приходит
   **из репозитория**;
3. скрипт возвращает правки: `git stash pop --index`. Вернуть «новый файл» на
   путь, который уже занят версией из ветки, git не умеет:

   ```
   error: .env.example: already exists in index
   error: conflicts in index. Try without --index.
   ```

   Запись stash при этом **сохраняется** (git никогда не теряет правки при
   неудачном `pop`) — но в индексе остаётся хвост конфликта;
4. следующий запуск видит `unmerged`-запись и падает на `git stash` с тем самым
   `needs merge`. Круг замкнулся: обновление больше не проходит, пока кто-то не
   сделает `git reset` руками.

Два условия нужны вместе: локальный файл, который релиз забирает в git, **и**
незавершённый `stash pop --index` после него. Обычные правки (` M`, `??`) ни
`stash`, ни `merge --ff-only` не ломают — это проверено на стенде.

## Что исправлено

`deploy/update-project.sh`:

1. **Записи конфликта от прошлого сбоя снимаются сами.** Если в индексе есть
   `unmerged`-пути, а незавершённой операции нет (`MERGE_HEAD`,
   `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `rebase-*` отсутствуют), скрипт делает
   точечный `git reset -- <путь>`: меняется только индекс, файлы на диске
   остаются как были. Кнопка снова работает без ручного вмешательства.
2. **Настоящее незавершённое слияние не разбирается за оператора.** Если
   операция идёт, обновление останавливается **до** stash и называет команду:
   `на сервере незавершённое слияние (MERGE_HEAD): … git merge --abort либо
   допишите конфликт и git commit`. Проверка стоит до ветки с перемоткой,
   поэтому срабатывает и при нулевом отставании (когда stash вообще не
   вызывается) — иначе конфликт дожил бы до миграций и сборки.
3. **Локальный файл, который релиз забирает в git, больше не ломает
   обновление.** До stash скрипт сравнивает неотслеживаемые файлы с целевой
   ревизией. Совпавший путь уносится в каталог состояния
   (`UPDATE_STATE_DIR/local-changes/<время>/`), а не в рабочее дерево: там он не
   попадёт в контекст сборки Docker (`COPY . .`), а `stash pop --index` больше
   не воюет за занятый путь. После перемотки копия возвращается: если ветка
   принесла ровно то же содержимое — отдельная копия удаляется (она не нужна),
   если содержимое отличается — оператор видит путь к своей версии и команду
   сравнения.
4. **Правки, брошенные прошлым сбоем в stash, возвращаются сами.** Git не
   удаляет запись stash, если `pop` не завершился, — правки админа целы, но так
   и лежат в `git stash list`, а следующее нажатие кнопки их уже не поднимет
   (своей грязи у него нет). Скрипт находит запись с меткой `edrc-update-…` и
   раскладывает её частями: отслеживаемые файлы — из содержимого stash,
   неотслеживаемые — на свободные пути, а занятые веткой уносит в каталог
   состояния. Сам `stash pop` для этого не годится: ровно он и даёт
   `already exists, no checkout`. Делается это **вне** ветки перемотки, потому
   что после сбоя ветка уже перемотана и следующее нажатие видит «обновлять
   нечего»; чужие stash (без метки обновления) не трогаются.
5. **Неудачный `stash pop` больше не оставляет мину.** После конфликта
   восстановления скрипт снимает `unmerged`-записи и приводит эти пути к
   версии из ветки, а сам stash сохраняет (правки целы). Следующее нажатие
   кнопки поэтому проходит, а не упирается в `needs merge` навсегда.

## Что делать оператору, если ошибка всё же видна

Сообщение в панели теперь называет причину и действие. Разбор по шагам:

```bash
cd /opt/ed-ring-colony/src
git status --short            # что именно в дереве
git ls-files -u               # есть ли записи незавершённого слияния
git stash list                # сохранились ли правки прошлого прогона
```

- **Идёт слияние** (`git status` пишет «You have unmerged paths», есть
  `MERGE_HEAD`): решите конфликт (`git add <файл>` … `git commit`) либо
  отмените слияние (`git merge --abort`) и запустите обновление снова.
- **Слияния нет, но `git ls-files -u` непуст** (хвост прошлого `stash pop`):
  новый скрипт снимет такие записи сам; вручную это
  `git reset - <путь>` (файлы на диске не трогаются).
- **Правки остались в stash** (`git stash list` непуст): после успешного
  запуска они вернутся сами. Если разбираете вручную — `git stash pop`, а при
  конфликте смотрите `git stash show -p stash@{0}`.
- **Локальная копия файла, который теперь есть в git**: ищите её в
  `UPDATE_STATE_DIR/local-changes/` (по умолчанию `/opt/ed-ring-colony/update-state/local-changes/`),
  сравнить: `diff -u <копия> <файл>`.

## Проверки

`scripts/tests/update-script.test.mjs` — три новых сценария на настоящем git:

| Тест | Что воспроизводит |
|---|---|
| «локальный `.env.example`, который релиз забирает в git» | ровно прод-случай: свой `?? .env.example` + релиз, добавивший этот путь; обновление доходит до сборки, копия сохранена в каталоге состояния |
| «записи незавершённого слияния от прошлого сбоя не блокируют кнопку» | индекс с `unmerged`-записями без `MERGE_HEAD` (`UD .env.example`); первый и повторный прогоны успешны, правка админа на месте |
| «правки, брошенные прошлым прогоном в stash, возвращаются сами» | запись `edrc-update-…` в `git stash list` + хвост `needs merge` в индексе: правки возвращаются, stash и записи сняты |
| «перемотка уже сделана: … при нулевом отставании» | прод после сбоя: ветка уже перемотана (`BEHIND=0`), правки в stash, хвост в индексе — правки всё равно возвращаются |
| «настоящее незавершённое слияние не разбирается за оператора» | идёт конфликтующий `merge`: остановка до stash, записи индекса не тронуты, сборка не начинается |

Плюс прежние проверки (`ошибка git stash возвращает причину`,
`конфликт восстановления stash останавливает обновление`) продолжают
проходить: `npm ci && node scripts/run-tests.mjs update-script` — 35 из 35.
