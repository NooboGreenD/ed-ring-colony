# Проверка безопасности проекта (2026-10-21)

## Итог

В репозитории есть два пути доступа к Supabase/Postgres:

1. Публичный Supabase API (PostgREST/Auth/Realtime/Storage) доступен браузеру через same-origin `/api/supabase/*`. Ключ `anon` публичный по назначению и сам по себе не должен давать доступ к приватным данным: границы доступа обеспечивают GRANT/RLS и серверная авторизация.
2. Прямой PostgreSQL URL и `service_role` используются только на сервере. Установщик self-hosted стека привязывает опубликованный PostgreSQL-порт к `127.0.0.1:5432`; приложение публикует собственный порт также только на loopback.

По исходникам не обнаружено включения `SUPABASE_SERVICE_ROLE_KEY` в `NEXT_PUBLIC_*` или его использования в обычных клиентских компонентах. Но репозиторий не может подтвердить реальные настройки уже работающего сервера, межсетевого экрана, Docker-сетей и то, какие миграции на нём выполнены.

## Найдено и исправлено

### Высокий риск: устаревшие runtime-зависимости

На исходном lock-файле `npm audit` выявил Next.js 16.3.5 (включая критический advisory для `next/og` и высокий advisory для image optimizer/SSRF), Sharp 0.35.4 (высокий advisory) и `source-map-js` 1.2.1 (DoS). Обновлены Next.js до 16.4.2 и Sharp до 0.35.5; для вложенной зависимости закреплён `source-map-js` 1.2.2. После обновления `npm audit` и `npm audit --omit=dev` сообщают **0 уязвимостей**.

### Средний риск: анонимный preview-admin при частично настроенном Supabase

Режим разработки мог выдавать локальному запросу административную роль при отсутствии service-role ключа, даже если задан публичный URL/anon key и процесс мог обращаться к настоящему Supabase. Такой ключ не является секретом, поэтому его наличие означает, что доступ уже требует полноценной проверки RLS. Теперь preview-admin отключён при наличии любых параметров подключения к Supabase/Postgres — как в billing API, так и в API каталога верфи. Сценарий без базы для локального макета оставлен.

### Уже имеющиеся ограничения доступа к данным

В проекте уже есть и тестами покрыты миграции:

- `20261015000000_profiles_rls_hardening.sql`: закрывает email/role и настройки приватности в `profiles`, запрещает самоназначение admin, ограничивает чтение `deliveries`, для публичных имён оставляет отдельное безопасное представление `public_profiles`;
- `20261016000000_credentials_and_views_hardening.sql`: закрывает `capi_tokens` и `inara_profiles` для `anon`/`authenticated`, ограничивает выдаваемые колонки `api_tokens`, исправляет безопасность представлений.

`src/proxy.ts` пропускает через публичный туннель только версии API Supabase (`auth`, `rest`, `realtime`, `storage`, `functions`, `graphql`) и не проксирует Studio/pg-meta. Административные API проверяют пользователя и роль на сервере; service-role применяется из server-only кода.

## Что проверить на реальном сервере

Статический аудит не может исключить неверные production-переменные или уже открытый порт. На сервере проверьте:

1. `ss -lntp | grep -E ':(5432|6543)\\b'` — PostgreSQL и pooler не должны слушать `0.0.0.0`, `[::]` или публичный IP. Для установки по умолчанию ожидается loopback (`127.0.0.1`). Проверьте и правила cloud firewall/security group, UFW и Docker `DOCKER-USER`.
2. `docker inspect supabase-db --format '{{json .HostConfig.PortBindings}}'` — публикация порта БД должна отсутствовать либо быть только на loopback. Не публикуйте `5432`/`6543` для всего Интернета.
3. Убедитесь, что миграции `20261015000000_profiles_rls_hardening.sql` и `20261016000000_credentials_and_views_hardening.sql` применены к рабочей БД. Для обновлений проекта используйте штатный механизм миграций (`UPDATE_APPLY_MIGRATIONS=1`); статус схемы можно сверить с журналом deployment/update-agent.
4. Через PostgREST с публичным anon-ключом проверьте, что запросы к `profiles` (включая `email`, `role`) и `deliveries` отклоняются, а `public_profiles` не содержит приватных колонок. Проверку выполнять на staging/тестовом пользователе, не выгружая реальные данные.
5. Если `SUPABASE_SERVICE_ROLE_KEY`, `POSTGRES_PASSWORD` или `JWT_SECRET` когда-либо попадали в клиентский bundle, логи, публичные артефакты или Git — считать их скомпрометированными и немедленно ротировать. При смене `JWT_SECRET` необходимо согласованно перевыпустить связанные Supabase JWT-ключи и учитывать завершение существующих сессий.

`NEXT_PUBLIC_SUPABASE_ANON_KEY` не является паролем к PostgreSQL. Не помещайте туда service-role ключ. Публичные данные могут оставаться доступными анонимно только по явно разрешённым политикам; для частных данных нужны и GRANT, и RLS, а не только скрытие интерфейса сайта.
