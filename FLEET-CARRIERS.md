# Учёт авианосцев на сайте проекта

Личные (Drake-Class) и эскадренные (Javelin-Class) авианосцы: статус, система и
прыжок, службы, груз поимённо и рынок. Учёт ведёт сайт проекта по журналам —
оверлей Colonial Helper берёт данные отсюда и не зависит от доступности
Raven Colonial, а в Raven уходит только проверенная информация.

## Жалоба

«Colonial Helper неправильно считывает данные с рынка авианосца — скорее всего
некорректно отправляет и читает их в Raven Colonial. Нужен учёт товаров на
авианосце через сайт проекта и БД: в профиле пилота — привязка авианосца со
службами, статусом, системой и трюмом; в эскадрилье — эскадренный авианосец с
теми же параметрами; рынки авианосцев обновлять вслед за авианосцем; оверлей
должен брать эту информацию, а в Raven — уходить корректные данные».

## Почему цифры были неверными

| Причина | Последствие |
|---|---|
| В Raven уходили только аддитивные дельты `PATCH /api/fc/{id}/cargo`, в том числе из истории (галочка «отправлять историю во внешние сервисы», сброс кэша импорта) | старые продажи прибавлялись к трюму повторно |
| Груз в Raven никогда не исправлялся по рынку носителя (SrvSurvey, эталонный клиент Raven, делает это по Market.json через `POST /api/fc/{id}/cargo`) | ошибки копились навсегда, оверлей читал их обратно |
| Дельты уходили по любому авианосцу, даже не зарегистрированному в Raven | в Raven заводились «обрывки» трюма из одной продажи |
| Эскадренный носитель не распознавался: `StationType` у него тоже `FleetCarrier`, отличает его служба `squadronBank` и поле `CarrierType: SquadronCarrier` | его `CarrierStats` у офицеров делал носитель «своим» и затирал учёт личного |
| Взнос в банк эскадры и изъятие из него не пишутся в журнал (меняется только трюм корабля) | груз эскадренного носителя не учитывался вовсе |
| Без Raven (нет ключа, сервис лежит) блок CARRIER знал только дельты текущей сессии | пустой или неверный блок |

## Модель данных (`supabase/migrations/20261017000000_fleet_carriers.sql`)

* `fleet_carriers` — один носитель = одна строка (ключ — `CarrierID` = `MarketID`).
  Тип, позывной, имя; привязка к пилоту (`owner_id`, один личный на профиль) и к
  эскадрилье (`squadron_id`); система, тело, координаты; запланированный прыжок;
  статус (доступ к стыковке, тритий, дальность, списание); службы экипажа;
  службы станции; ордера рынка; финансы (видит только владелец/офицеры).
  Каждое поле обновляется **только более свежим** наблюдением (`*_at`), поэтому
  повторная загрузка старых журналов ничего не откатывает.
* `fleet_carrier_cargo` — груз поимённо:
  `quantity = max(0, baseline_qty + Σ delta(event_at > baseline_at))`.
* `fleet_carrier_events` — грузовые дельты с `event_hash UNIQUE` (идемпотентность).

Базовые снимки груза:

| Снимок | Источник | Охват |
|---|---|---|
| Трюм пуст | `CarrierStats.SpaceUsage.Cargo = 0` | полный |
| Новый носитель | `CarrierBuy` | полный |
| Рынок носителя | Market.json (отчёт о станции из Helper'а) | частичный: товар на продажу — его `Stock`; распроданная позиция — 0; закупка ничего не говорит о трюме (правило SrvSurvey) |

Дельты: `MarketSell` на носитель (+), `MarketBuy` с носителя (−),
`CargoTransfer` (`tocarrier` +, `toship` −; носитель — стоянка пилота),
`SquadronBankTransfer` — синтетическое событие Helper'а для банка эскадры.

Все изменения идут одной функцией `apply_fleet_carrier_batch(user, source, ops)`
с блокировкой строк затронутых носителей: два Helper'а эскадрильи, пишущие в
один носитель, не пересчитают груз по неполному журналу дельт. Функция и
таблицы доступны только `service_role`; права решают маршруты Next.js.

### Рынок едет вместе с носителем

Каталог станций (`station_commerce`) хранит рынок FC по MarketID, но систему
менял только при следующей стыковке — после прыжка рынок «торговал» в старой
системе. Теперь любое новое местоположение носителя (`CarrierLocation`,
`CarrierJump`, стыковка, отчёт о рынке) переносит строку каталога в новую
систему (`move_fleet_carrier_station`), снимок рынка остаётся привязан к
MarketID, устаревшие `market_prices` старой системы удаляются.

## Привязка

* **Личный носитель** — автоматически: `CarrierStats` и `CarrierBuy` приходят
  только владельцу (доказательство), `CarrierLocation` — «мягкое»
  доказательство (только для ничьего носителя). Старый журнал со списанным
  носителем не отбирает привязку у текущего.
* **Эскадренный носитель** — автоматически к эскадрилье пилота на сайте, если
  он ещё ничей: член эскадрильи видит его `CarrierStats`/`CarrierLocation`
  (`CarrierType: SquadronCarrier`) или стыкуется к нему (Javelin пускает только
  членов эскадры). Чужую привязку не перехватывает.
* **Вручную** (журналы сброшены) — по Carrier ID или позывному: в профиле
  (вкладка «Авианосец») и на странице эскадрильи (создатель или звание с правом
  редактирования). Носитель, подтверждённый журналом другого пилота, вручную не
  привязывается.

## API

| Маршрут | Кто | Что |
|---|---|---|
| `POST /api/carriers/sync` | Helper (API-токен) и загрузчик журналов на сайте (сессия) | журнальные события → учёт (до 3000 за запрос) |
| `GET /api/carriers/mine` | профиль, оверлей Helper'а (`Authorization: Bearer rc_…`) | личный носитель + носители эскадрильи |
| `GET /api/carriers/{id\|позывной}` | все | карточка; посторонним — без груза и финансов |
| `POST/DELETE /api/carriers/bind` | пилот / офицер эскадрильи | ручная привязка и отвязка |
| `GET /api/carriers?squadron_id=` | страница эскадрильи | носители эскадрильи |
| `POST /api/stations/report` | Helper | снимок рынка FC дополнительно уточняет груз и местоположение носителя |

Авторизация «сессия сайта или API-токен Helper'а» — `src/lib/helperAuth.ts`
(раньше копировалась по маршрутам; `authFromRequest` токен Helper'а не понимает).

Хеш грузовой дельты считается **на сервере** из полей журнального события и id
пилота (`src/lib/fleetCarriers.ts → carrierDeltaHash`). Один и тот же журнал,
загруженный через сайт и через Helper, даёт одинаковые хеши — груз не
задваивается (ровно та ошибка, из-за которой раньше дублировались поставки).
Отбор событий и контекст стоянки у сайта (`src/lib/fleetCarrierCollector.ts`) и
Helper'а (`uploader/carrier_sync.py`) одинаковые — это проверяют тесты с обеих
сторон.

## Colonial Helper 2.14.0

* `carrier_sync.CarrierEventCollector` отбирает события авианосцев (живые и
  историю), хранит outbox на диске (`.carrier_events_outbox.json`) и шлёт их
  пачками по 500 из цикла watcher'а; неудачная пачка остаётся до следующей
  попытки.
* Банк эскадры: у носителя со службой `squadronBank` считается дифф трюма между
  событиями `Cargo` (Cargo.json). Покупка/продажа и `CargoTransfer` вычитаются
  из ожидаемого трюма заранее; после событий с неизвестным изменением трюма
  (миссия, сбор груза…) дифф не засчитывается; дроны не учитываются.
* Оверлей берёт груз, тоннаж, службы и прыжок с сайта (каждые 90 с, сразу после
  отправки событий, при стыковке и `CarrierStats`). Пока по носителю есть
  неотправленные события, груз с сайта не подставляется — свежая погрузка не
  «откатывается». Raven Colonial опрашивается, только если сайт молчит больше
  10 минут или не знает носитель.
* Raven Colonial получает корректную информацию:
  * дельты (`PATCH`) — только живые события и только по носителям,
    зарегистрированным в Raven (`GET /api/fc/{id}`, кэш 10 мин);
  * по снимку рынка FC и по пустому трюму (`CarrierStats`) груз
    **устанавливается** (`POST /api/fc/{id}/cargo`), отправляются только
    изменившиеся позиции, один снимок — один раз.
* `CarrierStats` эскадренного носителя больше не делает его «своим»;
  эскадренный носитель распознаётся по `squadronBank`/`CarrierType`;
  `CarrierLocation`, `CarrierJumpRequest`, `CarrierJumpCancelled` учитываются.

## Интерфейс

* Профиль → вкладка **«Авианосец»** (`/account?tab=carrier`): мой носитель и
  носители эскадрильи — система (с оценкой прибытия после прыжка), прыжок,
  статус, службы, трюм с полосой заполнения и разбивкой по товарам (и основой
  каждой цифры), рынок (продаёт/покупает), ручная привязка.
* Эскадрилья → вкладка **«Авианосец»**: те же карточки; участникам — груз,
  офицерам — финансы и управление привязкой.
* Загрузка журналов в профиле отправляет события авианосцев тем же проходом и
  показывает итог.
