# Т-Банк: разовые платежи через банковскую страницу

Интеграция доступна в `/admin?tab=billing` → «Платёжные системы» → **Т-Банк**.
По умолчанию провайдер выключен, ключей в репозитории нет.

## Что реализовано

- Создание одностадийного платежа (`Init`, `PayType=O`) в рублях и переход на `PaymentURL` банка.
- Пополнение кредитов, покупка косметики и оплата периода подписки через существующий магазин.
- Продление того же действующего тарифа от текущей даты окончания. `auto_renew=false`.
- Проверка SHA-256 Token уведомлений, терминала, OrderId, PaymentId, суммы в копейках и валюты заявки.
- Выдача только по подписанному `CONFIRMED`. `AUTHORIZED` ещё не означает списание.
- Ответ на обработанное уведомление — HTTP 200, тело ровно `OK`.
- Защита от одновременной/повторной выдачи по одной заявке через атомарный захват `processing`.
- Журнал уведомлений без Token, данных карты и RebillId.

**Нет автосписаний, привязки карты, вызовов Charge, API-возвратов, автоматической сверки GetState и формирования чеков.**
Данные карт вводятся только на стороне банка. Возврат покупателя на сайт сам по себе ничего не выдаёт.

## Подготовка

1. Подключите интернет-эквайринг Т-Банка и получите тестовый терминал.
2. Примените миграции биллинга по порядку, если они ещё не применены:
   - `supabase/migrations/20260921000000_billing_and_premium_shop.sql`
   - `supabase/migrations/20260922000000_billing_real_data_payments.sql`
   - `supabase/migrations/20260922010000_tbank_provider.sql`
3. Для боевой среды настройте `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` и `BILLING_STORAGE=supabase`.
   Проверяйте, что в админке выбран фактический backend **supabase**. Боевые платежи Т-Банка блокируются на файловом хранилище, в том числе при fallback после ошибки подключения.
4. Установите `NEXT_PUBLIC_SITE_URL` в публичный HTTPS-origin без пути и нестандартного порта, например `https://edringcolony.ru`.
   Изменения окружения требуют перезапуска приложения.
5. Обеспечьте доступ банка к POST `/api/billing/webhooks/tbank` через HTTPS/443, без авторизации пользователя, CAPTCHA и перенаправлений.
   Валидацию отправителя выполняет подпись Token. Защитите административные API обычной авторизацией проекта.

## Тестовый запуск

Используйте отдельную тестовую среду/базу и тестовый аккаунт: тестовые подтверждения действительно выдают
кредиты, подписки и товары в этой среде. Не включайте тестовый терминал в публичном боевом магазине.

1. Оставьте «Тестовый режим» включённым.
2. Введите **TerminalKey с суффиксом DEMO** и соответствующий **пароль терминала** из кабинета эквайринга.
   Это не пароль входа в Т-Бизнес. Секрет вводите только в админке, не в чат и не в Git.
3. Нажмите «Сохранить ключи» → «Проверить настройки».
   **Для Т-Банка эта кнопка проверяет только заполненность и согласованность настроек.**
   Она не обращается в банк, не проверяет правильность пароля и не создаёт пробный платёж.
4. В кабинете банка настройте HTTP(S)-уведомления на:

   ```text
   https://<ваш-домен>/api/billing/webhooks/tbank
   ```

   Этот же URL передаётся в каждом Init как `NotificationURL`.
5. Включите провайдера. В магазине выберите покупку и Т-Банк, пройдите оплату тестовой картой из документации банка.
6. Дождитесь `CONFIRMED` и статуса «Оплачено» на странице `/premium-shop/pay/<intentId>`.
   Проверьте покупку, журнал уведомлений и транзакции в админке.
7. Проверьте отказ, повторную доставку одного уведомления и ручное продление подписки.
   На `AUTHORIZED`, ошибке подписи или возврате браузера без подтверждения банка выдачи быть не должно.

Тестовый режим не подменяет URL API: и DEMO, и боевой терминал используют
`https://securepay.tinkoff.ru/v2/Init`. Переключатель не делает боевой терминал тестовым —
интеграция отклоняет несовпадение режима с суффиксом DEMO.

## Перед реальными платежами

- **Фискализация не реализована в этом драйвере:** объект `Receipt` не отправляется.
  Организуйте чеки внешним процессом/сервисом либо подтвердите применимость законного освобождения.
  Согласуйте с банком и бухгалтером правила для кредитов, цифровых товаров и подписок, включая возвраты.
  Если ваш терминал требует Receipt в Init, до запуска нужна отдельная доработка интеграции кассы.
- Подтверждение «Выдача чеков организована отдельно / подтверждено законное освобождение» обязательно для
  включения боевого режима. Галочка сама по себе чеков не создаёт.
- Выключите провайдера для новых покупок. Дождитесь завершения старых платежей; не заменяйте терминал/пароль,
  пока банк ещё может прислать уведомления по нему. Единственная конфигурация не поддерживает одновременно два терминала.
- Сохраните боевые TerminalKey и пароль, отключите тестовый режим, подтвердите решение по чекам,
  проверьте backend и включите провайдера. Выполните контролируемую реальную оплату.
- Ключи хранятся в серверной `payment_providers.config`, клиент получает маску пароля.
  Сохраните RLS и ограничьте доступ к service-role ключу, БД и её резервным копиям.
- Отключение Т-Банка в админке запрещает новые оплаты, но **не отключает обработку уведомлений по уже созданным заявкам**.

## Сбои, сверка и ограничения

Повторный `CONFIRMED` для `paid` возвращает `OK` без повторной выдачи. Параллельное уведомление во время
`processing` получает ошибку для повторной доставки. Ошибка/отмена не перезаписывает `processing` или `paid`.
Уведомление, пришедшее раньше сохранения PaymentId из Init, получает 503 и должно быть доставлено повторно.

**Выдача в текущем биллинге состоит из нескольких записей, а не одной транзакции БД.**
Атомарный захват устраняет двойную обработку одной заявки, но не делает все операции биллинга транзакционными.
Если процесс упал после захвата или на середине выдачи, заявка остаётся в `processing`:
автоматический сброс блокировки небезопасен — часть покупки уже могла быть выдана.

Порядок разбора зависшего платежа:

1. Найдите заявку и журнал уведомлений по OrderId/PaymentId. Проверьте итоговый статус в кабинете Т-Банка.
2. Убедитесь, что старый обработчик больше не работает. Сверьте баланс, инвентарь/подписку и транзакции пользователя.
3. Если выдача завершена — восстановите связь с транзакцией и итоговый `paid` через контролируемую серверную операцию.
   Если частичная — восстановите только недостающие записи. Не запускайте полную выдачу повторно.
4. Только если доказано отсутствие любых побочных записей, допустимо вернуть заявку в `pending`
   и запросить повторную доставку уведомления. Такие изменения должен делать ответственный администратор с доступом к БД.

Не подтверждайте платёж вручную лишь потому, что покупатель вернулся на сайт. Не просите его платить второй раз при `processing`.
При таймауте Init результат может быть неопределённым: сначала сверяйте OrderId в банке, не создавайте повторный Init для той же заявки.

Возвраты/реверсы не отменяют автоматически выданные привилегии и не инициируются сайтом.
Разбирайте их в кабинете банка и сверяйте учёт/права пользователя вручную; уведомления видны в журнале.
Уведомления с отличающейся суммой (включая частичный возврат) отклоняются и помечаются `Amount/currency mismatch` для разбора.
Если требуется автоматическое восстановление после сбоев или автоматические возвраты, это следующий этап:
транзакционная выдача в БД, фоновая сверка статусов и отдельный учёт возвратов.

## Проверки разработчика

```bash
node --test scripts/tests/tbank-payments.test.mjs
npm run typecheck
npm test
```

Тесты используют подмену HTTP API банка и временное файловое хранилище. Они не отправляют деньги и не заменяют
проверку реального терминала и Supabase в вашей среде.
