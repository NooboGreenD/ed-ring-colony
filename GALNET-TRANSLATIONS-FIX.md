# Galnet: переводы не работают — колонки в БД и проверка синка

## Симптомы

- На сайте статьи Galnet видны, но **на всех языках один текст** (или блок
  «Контент и переводы» показывает растущую очередь `pending`).
- В логах `jobs`/web повторяется одна из ошибок:
  - `Could not find the 'translation_status' column of 'galnet_news' …`
  - `translation columns are missing in "galnet_news" — apply supabase/migrations/20260915000000_galnet_translations.sql`
- В мониторинге окно **«Фоновые задачи» не меняется** неделями: задачи
  `galnet-sync` и `translate` падают каждый слот, а state-файл обновляется
  только успешными запусками.

## Причина

Миграция `supabase/migrations/20260915000000_galnet_translations.sql`
добавляет в `galnet_news` и `news` колонки переводов для всех языков сайта
(`ru, en, de, it, ko, zh, ja` — `title_<lang>` / `body_<lang>`) и служебные
поля `source_lang`, `translation_status`, `translated_at`, `guid`, `slug`,
а в `galnet_sync_log` — `duration_ms`, `translated_count`, `updated_count`.
Код синхронизации и сайт используют именно их.

На базах, установленных до появления этой миграции (install.sh заливает
снимок `supabase/full_schema.sql`), колонок нет. На тот момент обновление
через панель применяло только миграции, **добавленные между ревизиями**,
поэтому старую базу оно само не починило — нужен разовый запуск миграции.
*С 25.09.2026 кнопка «Обновить сейчас» донашивает и такие «старые»
неприменённые миграции (сверка с `migrations.mark`, см. `MONITORING.md` →
«Ручное обновление проекта»); разовый запуск ниже всё ещё работает.*
Скрипт синка при отсутствии колонок не падает целиком: он переходит в
«минимальный» режим и вставляет статьи без переводов, а очередь перевода
падает — отсюда и замершие «Фоновые задачи».

## Лечение — одна команда

На сервере, из каталога клона (там, где `.env.production`):

```bash
node --env-file=.env.production scripts/apply-galnet-migration.mjs
```

Скрипт:

1. подключается напрямую к Postgres (`DATABASE_URL` / `SUPABASE_DB_URL`;
   из контейнера web работает `postgresql://postgres:ПАРОЛЬ@db:5432/postgres`,
   см. SPANSH-IMPORT.md про сеть Supabase и `EAI_AGAIN`);
2. применяет идемпотентные миграции `20260830152500_galnet_news.sql` и
   `20260915000000_galnet_translations.sql` (безопасно запускать повторно);
3. показывает итоговое состояние: какие колонки есть, сколько статей и в
   каких статусах.

Только посмотреть состояние (без записи):

```bash
node scripts/apply-galnet-migration.mjs --status
node scripts/apply-galnet-migration.mjs --status --url postgresql://postgres:ПАРОЛЬ@db:5432/postgres
```

Если прямого подключения нет, тот же SQL можно выполнить через контейнер БД:

```bash
docker exec -i supabase-db psql -U postgres -d postgres \
  < supabase/migrations/20260915000000_galnet_translations.sql
```

## После применения

1. Кнопка «Синхронизировать Galnet» в Админке → Мониторинг → «Контент и
   переводы» — новые статьи получат переводы сразу.
2. Кнопка «Догнать переводы» (или задача `translate`) разберёт накопившуюся
   очередь старых статей — статусы `pending` / `failed` / `partial`
   обрабатываются заново, дозаполняются только недостающие языки.
3. «Фоновые задачи» оживут: `galnet-sync` и `translate` снова завершаются
   успешно и обновляют `jobs-state.json`. Если какая-то задача упадёт и
   дальше, в окне появится её «Последняя ошибка» с временем сбоя — больше не
   нужно догадываться, почему окно не меняется.

## Что проверено в самом синке (scripts/lib/galnet-sync.mjs)

- Лента: cms.zaonce.net (Drupal JSON:API), `Accept: application/vnd.api+json`,
  ретраи с бэкоффом, защита от внутриигровых дат «11 SEP 3312»
  (`toIsoDate` отбрасывает их — из-за них статьи молча терялись).
- Дедупликация по `nid` + `guid`, upsert, обновление изменившихся статей,
  перевод ограничен `GALNET_TRANSLATE_LIMIT` за проход, догон очереди —
  отдельной задачей `translate` (статусы `pending,failed,partial`,
  свежие — первыми).
- Язык оригинала читается из `source_lang` строки (у Galnet — `en`, у
  внутренних новостей — `ru`): раньше русский текст отправлялся в Yandex как
  «английский» и складывался в `title_en`.
- Перевод не затирает существующие языки; статус `completed` только когда
  закрыты все языки, иначе `partial` — строка остаётся в очереди догона.
- Очередевые задачи (`galnet-sync`, `translate`) больше не считаются
  провалившимся слотом из-за частичного сбоя перевода: вставка статей и
  перевод — независимые шаги, недопереведённое подхватит следующий слот.
  Провалом остаётся только структурная ошибка (недоступна лента/БД).
