# Минорные фракции на карте Atlas (web 2.20.0, Colonial Helper 2.16.0)

Вкладка **«Фракции»** в Atlas (`/atlas?tab=factions`, Alt+8) и слой 3D-карты:
**все населённые системы, где есть минорные фракции**, поиск фракций по имени и
показ систем одной или нескольких выбранных фракций. Данные хранятся **в базе
проекта**; полный набор приходит из ночного дампа EDSM, а обновления — от
пилотов: **Colonial Helper** и загрузчик журналов в личном кабинете отправляют
состояние фракций каждой посещённой населённой системы.

## Что видит пилот

**Без выбранных фракций** на карте — все населённые системы (десятки тысяч
точек), цвет — принадлежность системы:

| Цвет | Принадлежность |
|---|---|
| синий | Федерация |
| фиолетовый | Империя |
| зелёный | Альянс |
| светло-серый | Независимые |
| бирюзовый / янтарный / оранжевый | Таргоиды / Стражи / Федерация пилотов |

Во вкладке под поиском — фильтр по принадлежности (клик — скрыть/показать,
двойной клик — «только эта»), счётчики, список систем по имени с поиском и CSV.

**Поиск фракций** — поле «Найти минорную фракцию» (от 2 букв; сначала точное
совпадение, затем начало имени, затем вхождение, внутри — по числу систем) и
галочка «только фракции игроков (PMF)». В результатах — принадлежность,
правительство, сколько систем и где фракция у власти. Клик добавляет фракцию на
карту, повторный — убирает. **Можно выбрать до 12 фракций**, у каждой свой цвет.

**С выбранными фракциями** на карте — только их системы:

| Форма | Значение |
|---|---|
| ★ звезда | выбранная фракция у власти в системе |
| ◎ кольцо | в системе несколько выбранных фракций |
| • точка | фракция присутствует |

Цвет — сильнейшая из выбранных фракций в системе. В списке выбранных у каждой
фракции: цвет (клик — скрыть с карты, не убирая из списка), «только» (оставить
одну), глаз, ×; клик по имени подводит камеру к её системам. Переключатели:
«только системы, где выбранная фракция у власти» и «остальные населённые
системы — фоном». Список систем — сначала где выбранные фракции у власти, затем
по влиянию; в строке — влияние каждой выбранной фракции и её состояние
(конфликты — красным).

**Системы кликабельны** (точка на карте или строка списка): подсказка у
курсора (имя, контролирующая фракция или влияние выбранных), клик открывает
**карточку системы**: кто у власти и в каком состоянии, принадлежность,
правительство, безопасность, экономика, население, **все фракции системы** с
полосой влияния, настроением, активными / ожидающими / затухающими
состояниями, отметкой PMF и числом систем фракции; кнопка «+» добавляет любую
фракцию на карту, «×» — убирает. Внизу — дата и источник данных (дамп EDSM,
Colonial Helper, журнал на сайте), ссылки EDSM / Inara / Spansh.

Плашка состояния сверху вкладки: загрузка набора (байты), «Сервер загружает
дамп EDSM — 37 %» (этап и процент идущего импорта), «N населённых систем ·
фракций: M · дамп EDSM от … · пилоты обновляли …», «данных пока нет» (с
подсказкой про админку) или ошибка с повтором. Переключатель «Фракции (N)» есть
и в панели слоёв карты. Настройки (показ, фильтр, выбранные фракции) хранятся
в `localStorage` (`atlas-factions-v1`).

## Откуда данные

### 1. Ночной дамп EDSM — полный набор

`https://www.edsm.net/dump/systemsPopulated.json.gz` (≈0,5 ГБ gzip,
обновляется раз в сутки около 04:50 UTC): каждая населённая система с
контролирующей фракцией и списком фракций (влияние, состояния, настроение,
флаг «фракция игроков», время последнего обновления). Почти весь объём —
станции и тела, они при разборе отрезаются до `JSON.parse`.

Почему не другие источники: Spansh `galaxy_populated` — 4+ ГБ; EliteBGS API
нестабилен (elite-kode/elitebgs#378: ошибки 500 в октябре 2026) и отдаёт данные
по одной фракции; EDDN-слушатель на сервере не развёрнут.

### 2. Журналы пилотов — обновления

В событиях **FSDJump**, **Location** и **CarrierJump** игра пишет состояние
населённой системы целиком: `SystemFaction`, принадлежность, правительство,
экономику, безопасность, население и `Factions` (влияние, состояние, списки
состояний, настроение).

* **Colonial Helper 2.16+** (`uploader/bgs_sync.py`) отбирает такие события —
  живые сразу после прыжка и историю при первичной загрузке — и шлёт их на
  `POST /api/factions/sync` (API-токен). Очередь на диске
  `.bgs_snapshots_outbox.json`: по одной, самой свежей записи на систему (до
  5000), та же система с тем же состоянием повторно не уходит час; при
  недоступном сайте — пауза 60 с, данные ждут.
* **Загрузчик журналов в личном кабинете** (`/account`, `BgsSnapshotCollector`
  в `src/lib/bgsJournal.ts`) делает то же по загруженным файлам: из нескольких
  посещений системы остаётся самое свежее, отправка пачками по 400.

Проекция одинакова у обоих (`projectBgsEvent` ↔ `project_bgs_event`): эталон —
`scripts/tests/fixtures/bgs-journal.expected.json`, с ним сверяются и тест сайта,
и тест Helper'а. Личные поля (`MyReputation`, `SquadronFaction`, `HomeSystem`,
`HappiestSystem`) и `_Localised` не отправляются, `SystemAddress` — строкой
(он шире 2^53). Хеши доставок (`source_hash`) не затронуты: фракции идут
отдельным маршрутом.

### Правило слияния

**Побеждает более свежее наблюдение** (`observed_at`): у дампа — самое позднее
`lastUpdate` фракций системы, у журнала — время события. Свежие данные пилота
не затираются дампом, дамп обновляет системы, где пилоты давно не были. Состав
фракций системы заменяется целиком (ушедшая фракция исчезает). Повтор пачки и
один журнал, загруженный и с сайта, и из Helper'а, ничего не портят.

## База

Миграция `supabase/migrations/20261019120000_minor_factions.sql` (есть в
`full_schema.sql`, идемпотентна):

| Таблица | Что |
|---|---|
| `bgs_systems` | населённые системы: координаты, принадлежность, правительство, экономика, безопасность, состояние, население, контролирующая фракция, число фракций, `observed_at`, `source` (edsm / helper / web / eddn), `sync_run` |
| `bgs_factions` | словарь фракций: имя (уникально без учёта регистра), принадлежность, правительство, `is_player`, id EDSM, счётчики систем и «у власти» |
| `bgs_faction_presence` | фракция в системе: влияние 0…1, состояние, активные / ожидающие / затухающие состояния, настроение |
| `bgs_sync_state` | импорт дампа: заголовки, счётчики, ход этапов (`progress`) и журнал (`log`) |
| `bgs_updates` | пачки от пилотов: кто, откуда, сколько пришло / применено / устарело / новых систем (30 дней) |

RPC (только `service_role`): `bgs_apply_snapshots` (пачка наблюдений:
фракции → системы «свежее побеждает» → замена состава → счётчики; известные
фракции не вставляются заново — последовательность id не сжигается),
завершение импорта короткими вызовами — `bgs_delete_missing` (пропавшие из
дампа системы, если пилоты не присылали их 30 дней, пачкой),
`bgs_recount_factions_batch` (счётчики фракций пачкой по id),
`bgs_prune_factions` (фракции без систем, пачкой), `bgs_finish_sync` (состояние
и итоги); `bgs_layer_rows` (слой одним JSON — мимо `max_rows` PostgREST),
`bgs_search_factions`, `bgs_faction_presence_rows`, `bgs_system_detail`,
`bgs_admin_summary`, `bgs_recount_factions`, `bgs_parse_rows`.

Каждый вызов укладывается в короткий `statement_timeout` PostgREST: пачка
записи, не уложившаяся в него, делится пополам; удаление и пересчёт идут всё
меньшими шагами.

## Импорт дампа: архив → куски → база (как у «Каталога систем»)

Дамп весит ≈0,5 ГБ, а канал сервера к зарубежным хостам режет скорость
**одного соединения** (у Spansh замеряли ~10 КБ/с на поток). Поэтому импорт
устроен так же, как у каталога систем — архив скачивается на сервер, там
разбивается на куски, куски загружаются в базу, — только все шаги идут
**одновременно**: запись в базу начинается с первых мегабайт, а не после
последнего байта архива.

`src/lib/bgsSync.ts` (оркестратор, один запуск за раз на процесс),
`bgsShards.ts` (куски), `bgsWriter.ts` (запись), скачивание — общий
`downloadDump` из `galaxyImport.ts`:

1. **Запрос к EDSM** — HEAD: размер, дата, ETag, поддержка Range. Тот же дамп,
   что в прошлый удачный импорт, второй раз не качается («без изменений»).
2. **Скачивание архива на сервер** —
   `data/spansh/factions/edsm-systemsPopulated.json.gz` (тот же отдельный диск,
   что у каталога; `FACTIONS_ARCHIVE_DIR`). `FACTIONS_DOWNLOAD_SEGMENTS`
   соединений (по умолчанию **8**, до 16; в админке — выбор на запуск) берут
   **куски файла по `FACTIONS_PIECE_MB` (8 МБ) по порядку**, как aria2c: скорость
   — сумма соединений, а начало файла готово почти сразу. Прогресс кусков — в
   `<архив>.parts.json`, метка дампа — в `<архив>.meta.json`: обрыв, «Остановить»
   и перезапуск сайта не теряют скачанного. Каждый ответ сверяется с дампом
   (размер, Last-Modified/ETag): если EDSM пересоберёт дамп посреди скачивания
   (≈04:50 UTC), половинки двух дампов не склеиваются — скачанное удаляется и
   загрузка сама начинается заново со свежим дампом (до двух раз за запуск).
   Сервер, не дающий столько соединений (429/503), не роняет скачивание: лишние
   соединения отключаются, остальные докачивают. Перед скачиванием проверяется
   свободное место.
3. **Разбивка на куски** — прямо во время скачивания архив читается ровно до
   границы, до которой он уже скачан без дыр, разбирается (`bgsDump.ts`: станции
   и тела отрезаются до `JSON.parse`) и раскладывается в
   `data/spansh/factions/shards/bgs-00001.ndjson.gz` по `FACTIONS_SHARD_SYSTEMS`
   (1000) систем — готовые строки для `bgs_apply_snapshots`. От 0,5 ГБ остаются
   мегабайты. `manifest.json` рядом: чей это дамп, метка импорта, сколько записей
   архива разложено, какие куски уже в базе. Разбивка — ~140 МБ/с распакованного
   JSON, узким местом не бывает.
4. **Загрузка кусков в базу** — каждый готовый кусок сразу пишется в базу:
   * **прямой Postgres**, если веб-процессу задан `DATABASE_URL` /
     `SUPABASE_DB_URL` (деплой собирает его сам, как для каталога систем) —
     кусок одним вызовом `bgs_apply_snapshots`, без `statement_timeout`;
   * иначе (или `FACTIONS_DB_DIRECT=0`, или прямое подключение не поднялось)
     **PostgREST** — пачками по `FACTIONS_BATCH_SIZE` (250) систем, пачка, не
     уложившаяся в короткий `statement_timeout`, делится пополам.

   Кусок — **единица продолжения**: после остановки или перезапуска сайта
   записываются только незаписанные куски с той же меткой импорта; архив не
   качается и не разбирается заново.
5. **Завершение** — удалить пропавшие системы, пересчитать фракции, удалить
   фракции без систем, записать состояние (прямой Postgres — по запросу на шаг,
   PostgREST — короткими вызовами в цикле); архив и куски удаляются с сервера
   (`FACTIONS_ARCHIVE_KEEP=1` оставляет).

Защита: меньше `FACTIONS_MIN_SYSTEMS` (1000) систем или дамп меньше половины
прошлого — пропавшие системы не удаляются (записанное кусками — валидные
данные, «свежее побеждает»); «Импортировать принудительно» принимает
«усохший» дамп. Битый gzip — архив и куски удаляются, следующий запуск скачает
заново. EDSM не отвечает, а на сервере лежит скачанный архив (или разбитые
куски) — «Загрузить данные» записывает в базу его.

**По частям** (как кнопки каталога систем): «Скачать архив» — только скачать
(база не трогается), «Разбить на куски» — только разбить скачанный архив,
«Загрузить куски в базу» — записать то, что уже на сервере, без обращения к
EDSM (`mode` = `download` / `split` / `import`; обычный запуск — `full`).

**Запускают:** администратор (ниже) и задача **`factions-sync`** планировщика —
раз в сутки в 07:10 UTC. Первый импорт (≈0,5 ГБ) задача **не делает** — это
решение администратора; после него она обновляет данные, когда прошлый импорт
старше `FACTIONS_REFRESH_DAYS` (7 дней), и продолжает импорт, оборванный
перезапуском сайта. Задача включена по умолчанию (`docker-compose.yml`); со
своим `JOBS_ENABLED` допишите `factions-sync`. Вручную:
`node scripts/server-jobs.mjs --once factions-sync` или
`curl -X POST -H "Authorization: Bearer $CRON_SECRET" "https://<site>/api/cron/factions-sync?force=1"`.

## Админка: Игровые данные → Фракции

`src/components/Admin/FactionsAdminTab.tsx`, `/api/admin/factions` (только
администратор):

* **Данные в базе проекта** — населённые системы, фракции (и PMF), присутствия,
  сколько обновлено за 7 дней, дата дампа и импорта, источник последнего
  наблюдения (EDSM / Helper / сайт), системы по принадлежности с полосами;
* **Загрузка из EDSM** — «Загрузить данные / сейчас» (всё сразу),
  «Импортировать принудительно», «Остановить», выбор **числа соединений к
  EDSM** (1–16); две карточки, как у каталога систем:
  * **① Архив на сервере** — сколько скачано из скольких (а не размер заранее
    выделенного файла), скачан ли целиком и дамп от какого числа, свободное
    место, путь; «Скачать архив» / «Докачать архив», «Удалить архив и куски»;
  * **② Куски → ③ база** — кусков, систем, объём, разбит ли архив до конца,
    сколько кусков уже в базе, путь записи (прямой Postgres или PostgREST);
    «Разбить на куски», «Загрузить куски в базу»;

  общий прогресс-бар и пять этапов с полосами (скачивание — объём,
  соединения, скорость, оставшееся время; разбивка — куски, системы,
  «ждёт скачивания»; запись — кусок N из ~M); итог; что решит задача
  `factions-sync` прямо сейчас. Ход, оставшийся в базе «идущим» после
  перезапуска сайта, показывается как прерванный;
* **Обновления от пилотов** — пачки и системы за 24 ч / 7 дней, сколько пилотов,
  последние 15 пачек: когда, откуда, командир, пришло / применено / устарело /
  новых, какие системы;
* **Журнал процесса** с копированием (живой прогон — из памяти, после
  перезапуска — копия из `bgs_sync_state`).

## API

| Маршрут | Что |
|---|---|
| `GET /api/factions/systems` | слой: кортежи `[id64, имя, x, y, z, принадлежность, правительство, фракция у власти, население, фракций, наблюдение, источник]` + словари; ETag/304, `X-Content-Bytes`, `meta.progress` идущего импорта |
| `GET /api/factions/search?q=&player=1&limit=` | поиск фракций |
| `GET /api/factions/presence?ids=1,2` | системы выбранных фракций (до 12) с влиянием и состояниями |
| `GET /api/factions/system?id64=` | карточка системы со всеми фракциями |
| `POST /api/factions/sync` | наблюдения от Helper (токен) и сайта (сессия), до 500 событий |
| `GET/POST /api/admin/factions` | админка: состояние (архив, куски, путь записи); `start` / `start+force` / `download` / `split` / `import` (+ `segments` 1–16) / `cancel` / `cleanup` |
| `GET/POST /api/cron/factions-sync` | задача планировщика (`CRON_SECRET`) |

## Настройки (`.env.production`)

| Переменная | По умолчанию | Что |
|---|---|---|
| `FACTIONS_DUMP_URL` | EDSM | зеркало дампа |
| `FACTIONS_ARCHIVE_DIR` | `GALAXY_ARCHIVE_DIR/factions` | куда качать архив (куски — в `shards/` рядом) |
| `FACTIONS_ARCHIVE_KEEP` | `0` | `1` — не удалять архив и куски после импорта |
| `FACTIONS_DOWNLOAD_SEGMENTS` | `8` | параллельных соединений к EDSM (1–16; в админке — на запуск) |
| `FACTIONS_PIECE_MB` | `8` | кусок файла, который соединение берёт за раз (1–64 МБ) |
| `FACTIONS_SHARD_SYSTEMS` | `1000` | систем в куске (100–10 000) |
| `FACTIONS_DB_DIRECT` | `1` | `0` — писать через PostgREST, даже если `DATABASE_URL`/`SUPABASE_DB_URL` заданы |
| `FACTIONS_REFRESH_DAYS` | `7` | раз во сколько дней задача обновляет данные |
| `FACTIONS_BATCH_SIZE` | `250` | систем в пачке записи через PostgREST |
| `FACTIONS_MIN_SYSTEMS` | `1000` | меньше — дамп считается сбоем |

## После обновления сайта

1. Миграция `20261019120000_minor_factions.sql` применяется
   `deploy/update-project.sh` сама (2.20.0 новых миграций не добавляет).
2. Админка → Игровые данные → **Фракции** → «Загрузить данные». Архив ≈0,5 ГБ
   качается на сервер фоном в 8 соединений, по мере скачивания разбивается на
   куски и пишется в базу; ход — по этапам, в карточках архива и кусков и в
   журнале. Остановка, обрыв и перезапуск сайта продолжаются с того же места:
   недокачанный архив прошлой версии докачивается (его крупные части
   перерезаются на куски по 8 МБ, скачанное не теряется).
3. Свой `JOBS_ENABLED` в `.env.production` — дописать `factions-sync`.
4. Опубликовать пакет **Colonial Helper 2.16.0** — тогда пилоты с Helper'ом
   будут обновлять фракции после каждого прыжка.
