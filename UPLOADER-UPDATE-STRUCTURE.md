# Обновление Uploader без перекачивания EXE

Разбор вариантов: как обновлять Colonial Helper «структурой программы» (кодом),
а не 22-мегабайтным экзешником на каждый релиз, с учётом того что сайт, API и
хранилище теперь живут на **собственном сервере** `edringcolony.ru`.

> **Статус: реализовано** (раунд 67, версия программы 2.13.0; автономная
> публикация — 2026-09-28). Выбран вариант **В1** — exe-лаунчер + пакет кода,
> хранение на диске сервера (`/data/uploader`), подпись Ed25519, подтверждение
> перед скачиванием. GitHub Actions и GitHub Releases из цепочки удалены.
> Что именно сделано и как это включить — раздел 8 в конце документа.

Документ начинался как проект решения; разделы 1–7 сохранены как обоснование
выбора, раздел 8 описывает готовую реализацию.

### Автономный выпуск новой версии

1. Открыть **Админка → Обновления Helper → Настроить**.
2. Импортировать приватный seed уже доверенного клиентами ключа (например,
   `k202609`) либо создать серверную пару и включить её публичный ключ в новую
   базовую сборку. Ключ хранится в `config.json` тома с правами `0600`.
3. В форме публикации указать версию/канал/заметки и выбрать каталог
   `uploader`. Сервер сам исключит тесты и сборщики, посчитает SHA-256,
   подпишет манифест, создаст ZIP и переключит канал.
4. При смене Python или зависимостей собрать `ColonialHelper.exe` на доверенной
   Windows-машине и загрузить второй формой. EXE хранится и раздаётся тем же
   сервером (`/api/uploader/launcher/win64`), без GitHub Releases.

Опубликованная версия неизменяема. Ошибка исправляется новым номером либо
мгновенным откатом указателя канала в таблице версий. Именованный том
`uploader-store` переживает пересборку сайта; entrypoint автоматически
исправляет владельца старого тома, что устраняет прежний HTTP 500 при записи.

## 1. Что происходит сейчас (факты, не ощущения)

| Что | Значение | Где в коде |
|---|---|---|
| Формат поставки | PyInstaller `--onefile --windowed` → один `ColonialHelper.exe` | `uploader/build_exe.py` |
| Размер сборки | **23 159 225 байт ≈ 22.1 МиБ** (v2.12.2; до 2.10.26 было ≈31 МиБ) | релизы GitHub |
| Канал обновлений | GitHub Releases API, `api.github.com/repos/NooboGreenD/ed-ring-colony/releases` | `uploader/updater.py:34` |
| Как ставится обновление | скачивается в «Загрузки», дальше **пользователь закрывает программу и вручную заменяет exe** | `colonial_helper.py:6565-6600` |
| Релизов за 30 дней | **78** (из них 11 стабильных, 67 prerelease из веток `arena/**`) | GitHub API |
| Трафик на одного пилота | **≈290 МБ/мес** только по стабильному каналу; на канале «Все сборки» — ≈1.7 ГБ/мес | 11 × 22.1 МиБ |
| Сборка релиза | Windows-раннер, ~10 мин на каждый push в `uploader/**` | `.github/workflows/build-exe.yml` |
| Реально меняющийся код | **27 модулей, 1.55 МиБ исходников, 397 КиБ в сжатом виде** | `uploader/*.py` |

Ключевая диспропорция: **99.8 % веса обновления — это Python-рантайм, tkinter,
ttkbootstrap, requests и прочие библиотеки, которые не менялись месяцами.**
Меняются 1–3 файла из 27, то есть от 5 до 130 КиБ.

```
ColonialHelper.exe 22.1 МиБ
├── python311.dll + stdlib + tcl/tk .......... ~19 МиБ   меняется раз в полгода
├── ttkbootstrap / requests / pyperclip ...... ~2.5 МиБ  меняется раз в месяцы
└── НАШ КОД (PYZ, 27 модулей) ................ ~0.4 МиБ  меняется каждый день  ← только это и надо возить
```

### Чем это плохо, кроме трафика

1. **Ручная замена файла.** Сегодня «обновление» = «мы скачали вам файл,
   дальше сами». Часть пилотов остаётся на старых версиях навсегда, и сервер
   вынужден поддерживать древние форматы `PARSER_VERSION`.
2. **SmartScreen и антивирусы.** Каждый новый неподписанный exe — это новый
   хеш с нулевой репутацией. Пока exe меняется по 3 раза в день, репутация
   не набирается никогда, и часть установок ловит «Windows protected your PC»
   или карантин Defender'а.
3. **10 минут Windows-раннера на любую правку.** Опечатка в подсказке = полный
   ребилд и новый 22-мегабайтный релиз, который выглядит как «обновление,
   в котором ничего не изменилось».
4. **Канал обновлений — GitHub, а не наш сервер.** Всё остальное уже переехало
   на свой сервер (`site_config.DEFAULT_SITE_URL`, POST-MIGRATION.md), а
   обновления по-прежнему зависят от доступности `api.github.com` (в РФ это
   регулярно «через раз») и от публичности репозитория.
5. **Нет отката.** Если сборка сломана — у пилота нет способа вернуться на
   предыдущую версию, кроме как вручную искать старый релиз.

## 2. Идея, общая для всех вариантов

Разделить поставку на два слоя с разной частотой изменений:

| Слой | Что внутри | Частота | Размер |
|---|---|---|---|
| **Рантайм** | Python, tkinter, ttkbootstrap, requests, pyperclip | раз в месяцы | ~22 МиБ |
| **Код программы** | `uploader/*.py` — 27 модулей | ежедневно | 0.4 МиБ (сжато) |

Обновлять по сети только второй слой. Это и есть «обновление структуры
программы»: на диске у пилота лежит не монолит, а каталог модулей, который
синхронизируется с сервером по манифесту.

## 3. Варианты

### В1 — Лаунчер + пакет кода на сервере ⭐ рекомендуемый

`ColonialHelper.exe` перестаёт быть программой и становится **загрузчиком**:
внутри Python + все зависимости + ~300 строк bootstrap-кода. Сам код программы
лежит рядом, в пользовательском каталоге, обычными модулями, и обновляется
пофайлово по манифесту с нашего сервера.

```
%LOCALAPPDATA%\ColonialHelper\
├── app\
│   ├── 2.12.2\  colonial_helper.py, overlay.py, … (27 файлов)
│   ├── 2.13.0\  ← скачано, проверено, ещё не активировано
│   └── current.json  {"version": "2.12.2", "previous": "2.12.1", "health": "ok"}
├── cache\  манифесты, кэш загрузок
└── logs\
```

Порядок работы:

1. Лаунчер читает `current.json`, проверяет sha256 всех файлов версии
   (27 файлов, 1.55 МиБ — ~15 мс), добавляет каталог в `sys.path`, импортирует
   `colonial_helper` и отдаёт ему управление. Внешне — та же программа.
2. В фоне спрашивает `GET /api/uploader/manifest?channel=stable` на **нашем**
   сервере. Сравнивает список файлов с локальным.
3. Качает **только файлы с другим хешем** — обычно 1–3 файла, 5–130 КиБ.
   Складывает в `app\<новая версия>\`, недостающие копирует из текущей
   (hard-link/копия), проверяет хеши и подпись манифеста.
4. Атомарно переключает `current.json` и перезапускает программу (~2 секунды,
   без участия пользователя, без «замените файл вручную»).
5. Если новая версия не дожила до отметки «здорова» два запуска подряд —
   лаунчер сам откатывается на `previous`.

**Трафик обновления: 5–130 КиБ вместо 22.1 МиБ (в 170–4000 раз меньше).**

| + | − |
|---|---|
| Максимальная экономия трафика и времени | Нужен новый лаунчер и один (последний) полный переход пользователей |
| exe перестаёт меняться → репутация SmartScreen наконец копится | Код исполняется из каталога с правом записи → **обязательна подпись манифеста** |
| Релиз кода = 30 секунд на ubuntu-раннере вместо 10 минут на Windows | Нужна дисциплина: новая библиотека в `requirements.txt` = новый exe |
| Честный автоапдейт с откатом и «ремонтом» установки | Появляется своя мини-система версионирования (тестируемая, ~700 строк) |
| Обновления идут с нашего сервера, GitHub — только зеркало | |

### В2 — PyInstaller `--onedir` + синхронизация папки

Собирать не один файл, а каталог (`ColonialHelper.exe` + `_internal\` с DLL).
Апдейтер синхронизирует файлы каталога по манифесту: DLL и библиотеки не
меняются, поэтому по сети едет только изменившееся.

Проблема: **наш код в onedir тоже лежит внутри exe** (архив PYZ), поэтому при
любой правке кода меняется сам `ColonialHelper.exe` — правда, в onedir он
весит не 22 МиБ, а ~3–5 МиБ. Плюс Windows не даёт перезаписать работающий exe:
нужен приём «переименовать работающий → положить новый → перезапустить»
(это рабочий, законный приём, `MoveFileEx`).

| + | − |
|---|---|
| Никакой самодельной загрузки модулей: всё штатное для PyInstaller | Трафик 3–5 МиБ на релиз — в 30 раз хуже, чем В1 |
| Программа стартует заметно быстрее (onefile каждый запуск распаковывается во временную папку) | Установка «раздувается» с 22 МиБ до ~60 МиБ на диске |
| Проще всего внедрить (2–3 дня) | exe меняется каждый релиз → проблема SmartScreen остаётся |
| | Требует установщика/каталога, а не «скачал один файл и запустил» |

### В3 — Бинарный дельта-патч самого exe (bsdiff / `zstd --patch-from`)

Сервер хранит патчи между версиями, клиент качает патч и собирает новый exe
локально.

| + | − |
|---|---|
| Ничего не меняется в архитектуре программы | Внутренности onefile-exe сжаты zlib → патч между соседними версиями получается **не 100 КиБ, а 3–10 МиБ**; чтобы патчи были мелкими, сборку надо делать несжатой (exe ~50 МиБ) |
| Работает с чужими бинарниками (нам не нужно) | Нужны цепочки патчей N→N+1 или патч на каждую пару версий (при 78 релизах в месяц — это склад патчей) |
| | Всё равно надо решать самозамену exe и откат |
| | Самый сложный в отладке вариант («не тот байт» → битый exe у пилота) |

Вывод: как основной механизм — нет. Имеет смысл **только** как оптимизация
редкого обновления самого лаунчера в В1 (и то не на первом этапе).

### В4 — Вынести данные и правила на сервер (дополнение, а не замена)

Раз всё уже на сервере, часть релизов вообще не обязана быть релизами кода.
На сервер уезжают и кэшируются локально:

* справочники (товары/материалы колонизации, шаблоны построек, типы сигналов,
  словарь экзобиологии и её ценников);
* тексты интерфейса и подсказок (i18n уже есть на сайте);
* предустановки оверлея, параметры лимитов и размеры пачек выгрузки
  (`DELIVERY_CHUNK_SIZE`, `UPLOAD_WORKERS`, таймауты) — сервер сам подскажет
  клиенту оптимальные значения;
* карта эндпоинтов и «минимальная поддерживаемая версия клиента».

| + | − |
|---|---|
| Часть изменений доезжает **мгновенно, без обновления вообще** | Не отменяет обновлений кода (UI, разбор журнала, оверлей) |
| Сервер может попросить старого клиента обновиться / отключить сломанную фичу | Нужен аккуратный офлайн-кэш: без сети программа обязана работать |
| Готовит почву для A/B и поэтапной раскатки | |

### В5 — Тонкий клиент: UI уезжает в WebView, локально остаётся агент

Долгосрочный горизонт: нативными остаются только вещи, которые иначе не
сделать — чтение журнала, оверлей поверх игры, горячие клавиши. Вкладки
(«Колонизация», «Карта», «Досье», «Экзобиология») открываются как страницы
сайта в WebView2. Тогда 80 % изменений — это деплой сайта.

| + | − |
|---|---|
| Обновление UI = обычный деплой, клиент не трогаем вообще | Большая переделка (месяцы), 10 255 строк `colonial_helper.py` переписываются |
| Единый UI на сайте и в программе | Без интернета программа превращается в тыкву |
| | WebView2 Runtime — ещё одна зависимость на машине пилота |

## 4. Рекомендация

**В1 как основа + В4 поэтапно.** В2 — запасной план, если В1 покажется
избыточным; В3 — не делать; В5 — отдельным проектом, когда/если понадобится.

Обоснование коротко: при 78 релизах в месяц любой вариант, где exe меняется на
каждую правку кода, оставляет и трафик в мегабайтах, и вечную борьбу со
SmartScreen, и 10-минутный Windows-раннер. В1 закрывает всё это разом, а
«цена» — один последний полный переход пользователей на новый exe-лаунчер.

## 5. Как это устроено в деталях (проект В1)

### 5.1 Манифест

`GET https://edringcolony.ru/api/uploader/manifest?channel=stable&platform=win64`

```jsonc
{
  "schema": 1,
  "channel": "stable",
  "version": "2.13.0",
  "released_at": "2026-09-28T12:00:00Z",
  "notes_url": "https://edringcolony.ru/download/notes/2.13.0",
  "entry": "colonial_helper.py",          // что импортирует лаунчер
  "runtime": {                            // требования к exe-лаунчеру
    "min_launcher": "1.0.0",              // ниже — код не запустится
    "python": "3.11",
    "packages": {"requests": ">=2.31", "ttkbootstrap": ">=1.10.1"},
    "exe_url": "https://edringcolony.ru/download/ColonialHelper-1.1.0.exe",
    "exe_sha256": "…"                     // на случай «нужен новый лаунчер»
  },
  "files": [
    {"path": "colonial_helper.py", "size": 555_000, "sha256": "ab12…",
     "url": "/api/uploader/blob/ab12…"},  // контент-адресуемо, кэш навсегда
    {"path": "overlay.py", "size": 211_000, "sha256": "cd34…", "url": "…"}
  ],
  "signature": {                          // Ed25519 по канонизированному JSON
    "alg": "ed25519", "key_id": "2026-09", "value": "base64…"
  }
}
```

Файлы отдаются **контент-адресуемо** (`/api/uploader/blob/<sha256>`): такой URL
неизменяем, ему можно ставить `Cache-Control: public, max-age=31536000,
immutable`, и nginx/CDN отдаёт его без участия Next.js. Одинаковые файлы между
версиями физически хранятся один раз.

### 5.2 Эндпоинты сервера

| Метод | Путь | Назначение | Доступ |
|---|---|---|---|
| GET | `/api/uploader/manifest?channel=&platform=` | текущий манифест канала | публично, `max-age=60` |
| GET | `/api/uploader/blob/<sha256>` | файл по хешу | публично, immutable |
| GET | `/api/uploader/bundle/<version>.zip` | полный пакет (первая установка, «ремонт») | публично |
| GET | `/api/uploader/launcher?platform=win64` | ссылка+хеш актуального exe | публично |
| POST | `/api/admin/uploader/publish` | CI кладёт новую сборку (zip + манифест) | токен CI |
| POST | `/api/admin/uploader/promote` | перевести версию в канал / откатить канал | админ |

Плюс страница в админке: какие версии опубликованы, сколько пилотов на какой
версии (клиент и так шлёт версию в `User-Agent`/заголовке при выгрузке),
кнопки «сделать текущей» и «откатить канал».

**Хранилище** (решается отдельным вопросом): том сервера `/data/uploader`
(просто, быстро, nginx отдаёт напрямую) или Supabase Storage bucket `uploader`
(как `support-attachments`, переживает пересоздание контейнера).

### 5.3 Безопасность — это обязательная часть, а не «потом»

Сейчас программа скачивает exe и **ничего не проверяет**, кроме HTTPS. С
переходом на подгружаемый код требования жёстче, потому что появляется два
новых способа выстрелить себе в ногу:

1. **`site_url` настраивается пользователем** (`site_config.normalize_site_url`,
   режим selfhost). Если брать обновления «с того сервера, что в настройках»,
   то любой самохост сможет прислать официальному клиенту произвольный Python-
   код = удалённое исполнение кода. → Канал обновлений берётся **с отдельного,
   зашитого в лаунчер `UPDATE_HOST`**, и только пользователь явно, галочкой
   «обновляться с моего сервера» (для selfhost-инсталляций), может это сменить.
2. **Компрометация сервера/зеркала.** → Манифест подписывается **Ed25519**,
   приватный ключ живёт в GitHub Secrets (CI), публичный зашит в лаунчер.
   Файлы проверяются по sha256 из подписанного манифеста. Подпись не сходится —
   обновление не ставится, пишется в лог, программа продолжает работать на
   старой версии.

Плюс мелочи, которые дёшевы и сильно помогают: проверка хешей при каждом
старте (защита от «кто-то подложил модуль в каталог»), запрет на путь вне
каталога версии (traversal при распаковке), запрет на исполняемые расширения в
манифесте (только `.py`/`.json`/`.png`), лимит размера файла и пакета.

### 5.4 Атомарность, откат, ремонт

* Скачивание — во временный каталог `app\.tmp-<version>`; переключение —
  запись `current.json` через `os.replace` (атомарно на NTFS).
* `current.json` хранит `previous`. Первый успешный старт новой версии (дошли
  до готового окна) ставит `health: ok`. Два падения подряд без `ok` → лаунчер
  молча возвращается на `previous` и сообщает в логе.
* Команда «Восстановить установку» в интерфейсе: качает `bundle/<version>.zip`
  целиком и перекладывает каталог с нуля (лечит и повреждённые файлы, и
  вмешательство антивируса).
* Старые версии чистятся: держим текущую + предыдущую.

### 5.5 Когда всё-таки придётся качать exe

Только когда меняется рантайм: новая версия Python, новая библиотека в
`requirements.txt`, правка самого лаунчера. Манифест объявляет `min_launcher`;
если установленный лаунчер старее — программа показывает «нужна новая базовая
сборка, 22 МБ» и качает exe (это уже существующий код `updater.download_asset`,
он остаётся). По опыту такое бывает 1–2 раза в квартал вместо 11 раз в месяц.

### 5.6 Что меняется в CI

Сейчас: один workflow, Windows, ~10 мин, на каждый push в `uploader/**`.

Станет два:

| Workflow | Когда | Раннер | Время | Что делает |
|---|---|---|---|---|
| `build-bundle.yml` | любой push в `uploader/**` | ubuntu | **~30 с** | тесты, компиляция `py_compile`, сборка zip+манифеста, подпись Ed25519, `POST /api/admin/uploader/publish`, зеркало в GitHub Release |
| `build-exe.yml` | только изменения `requirements.txt`, `build_exe.py`, `launcher.py` или ручной запуск | windows | 10 мин | как сейчас, но собирается лаунчер |

Побочный приятный эффект: в `arena/**`-ветках prerelease-канал становится
по-настоящему удобным — сборка кода 30 секунд, пилот-тестер получает обновление
за 2 секунды.

### 5.7 Переход пользователей

1. Версия `2.13.0` выходит **как обычный полный exe** (последний такой),
   внутри — лаунчер + пакет кода 2.13.0 на борту.
2. При первом запуске лаунчер раскладывает встроенный пакет в
   `%LOCALAPPDATA%\ColonialHelper\app\2.13.0` и дальше живёт по новой схеме.
   Настройки, токен и кэш (`config.json`, `credentials.json`) остаются на месте
   — путь к ним не меняется.
3. Пилотам на 2.12.x существующий механизм предлагает скачать 2.13.0 — то есть
   один последний раз «по-старому», дальше уже никогда.
4. Сервер видит долю установок по версиям и может через месяц-два выключить
   поддержку клиентов ниже 2.13.0.

### 5.8 Тесты (в стиле существующих `uploader/tests/*`)

* `test_bundle_manifest.py` — разбор/валидация манифеста, отказ на плохой
  подписи, на traversal в путях, на неизвестном `schema`.
* `test_bundle_updater.py` — расчёт дельты (что качать), докачка, порча файла →
  «ремонт», отсутствие сети → работаем на текущей версии.
* `test_bundle_apply.py` — атомарное переключение, откат после двух падений,
  очистка старых версий.
* `test_launcher.py` — выбор версии, проверка хешей на старте, `min_launcher`.
* Серверные — в `scripts/tests/`: `uploader-manifest-route.test.mjs`,
  `uploader-publish-route.test.mjs` (по образцу `logs-upload-route.test.mjs`).

### 5.9 Необязательный, но полезный спутник: разрезать монолит

`colonial_helper.py` — 10 255 строк / 542 КиБ (126 КиБ в сжатом виде). Пока он
один, почти любая правка кода тянет за собой самый большой файл пакета. Если
разложить его на пакет `app/` (вкладки, сервисы, модель, UI-хелперы), типичная
дельта падает с ~126 КиБ до 5–20 КиБ, а CI-проверки становятся точечными.
Это отдельная работа, её можно делать постепенно и уже после запуска В1.

## 7. Принятые решения

1. **Вариант В1** — лаунчер + пакет кода.
2. Пакеты и базовый exe хранятся в серверном томе `/data/uploader`.
3. Манифест подписывается Ed25519 приватным seed из закрытого `config.json`;
   публикацию запускает администратор, внешние CI/Actions не нужны.
4. Helper спрашивает разрешение, показывает progressbar, проверяет SHA-256 и
   подпись, атомарно переключает версию и умеет применить серверный откат.
5. Selfhost настраивает собственную пару и базовую сборку тем же интерфейсом.

### Как включить канал (по шагам)

1. Пересобрать `web`, чтобы новый entrypoint исправил владельца именованного
   тома `uploader-store`. Отдельный publish-token больше не обязателен.
2. В **Админка → Обновления Helper → Настроить** импортировать приватный seed
   ключа, уже зашитого в `uploader/bundle.py`, с тем же ID. Если создаётся новая
   пара, сначала собрать базовый exe с её публичной частью и загрузить его.
3. В форме «Опубликовать новую версию» выбрать каталог `uploader`, указать тот
   же номер, что в `colonial_helper.py`, канал и заметки. Нажать публикацию.
4. Новую базовую сборку (только при смене runtime/ключа) собрать локально на
   доверенной Windows-машине и загрузить формой `.exe`; сервер проверит PE,
   посчитает хеш и будет раздавать файл со своего домена.
5. **Проверка**: `curl https://edringcolony.ru/api/uploader/manifest` должен
   отдать `{"ok":true,...}` с подписью, а админка → «Обновления Helper» —
   показать версию в канале.

### Что видит пилот

* Первый раз скачивает `ColonialHelper.exe` (ссылка на сайте ведёт на
  `/api/uploader/download`, адрес постоянный).
* Дальше «Обновить программу» → «Доступна версия X: изменилось файлов N,
  скачать K КБ» → видимый progressbar скачивания/проверки → установка за
  секунду → «Перезапустить сейчас?».
* Если обновление окажется битым — лаунчер вернёт прошлую версию сам,
  а кнопка «Восстановить» скачает пакет целиком.

### Что осталось на потом

* **Телеметрия версий** (сколько пилотов на какой версии) — сервер сейчас не
  считает обращения к манифесту; при желании добавляется одним счётчиком в
  роуте `manifest`.
* **Постепенная раскатка** (10 % → 50 % → 100 %) — в манифесте есть канал, но
  доли пока нет: откат канала закрывает ту же задачу проще.
* **Зеркало пакетов на GitHub** — сейчас там только exe. Нужно, если свой
  сервер окажется недоступен: клиент умеет фолбэк на GitHub только для exe.
* **Selfhost** (`SELFHOST.md`): свой сервер обновлений уже можно задать через
  `COLONIAL_HELPER_UPDATE_BASE` + `COLONIAL_HELPER_UPDATE_KEYS`, но в
  интерфейсе это не выведено — только переменные окружения.
