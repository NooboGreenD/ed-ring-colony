# Frontier CAPI: привязка принадлежит сайту

Обновлено: **24 октября 2026**.

## Решение по архитектуре

Frontier OAuth/CAPI подключается только в личном кабинете сайта: `/account/capi`.
Сайт хранит Frontier access/refresh-токены, обновляет их, запрашивает Companion API,
нормализует ответ и записывает профиль, статистику, положение и события в свои
таблицы. Colonial Helper больше не проходит собственный OAuth, не обращается к
`companion.orerve.net` и не получает Frontier-токены.

Helper использует только **отзываемый API-токен проекта**:

- `GET /api/capi/helper` возвращает признак привязки, диагностический статус и
  уже разобранный сайтом профиль;
- `POST /api/capi/helper` просит сайт обновить только профиль CAPI и вернуть
  результат для интерфейса Helper. Сайт не опрашивает `/journal` повторно:
  Helper загружает локальные Journal-файлы отдельным существующим потоком;
- при отсутствии/отключённой привязки `POST` отклоняется; подключить Frontier
  можно по ссылке `/account/capi`;
- оба метода не принимают и не выдают Frontier-токены; все данные CAPI
  разбираются и сохраняются сервером теми же функциями, что используют ручная
  синхронизация и расписание.

Старый `/api/capi/token` — мост, который копировал одну вращающуюся пару
Frontier refresh-токенов между сайтом и Helper. Он отключён ответом `410`:
старые версии Helper прекращают token handoff явно, а не создают параллельную
привязку. Используйте актуальную версию Helper с сайто-ориентированным CAPI.

## Почему это уменьшает число сбоев

1. **Один владелец refresh-токена.** Frontier выдаёт новую пару токенов при
   refresh; две копии, обновляющие одну пару, могли инвалидировать друг друга.
   Передача секретов между Helper и сайтом порождала stale writes и гонки.
   Теперь refresh выполняется только сайтом через `capiSession()`.
2. **Привязка не создаётся из Helper.** API-токен проекта даёт Helper право
   работать с данными своего пользователя на сайте, но не является заменой
   Frontier OAuth. CAPI-задачи выполняются только при активной записи
   `capi_tokens`, созданной OAuth-колбэком сайта.
3. **Один разбор профиля и один набор побочных эффектов.** `syncCapiPilot()`
   сохраняет `capi_profiles`, `pilot_stats`, положение пилота, журнал и
   события колонизации. Helper показывает сводку сервера, но не присылает
   нормализованные поля, не пишет их напрямую и не выбирает таблицу.
4. **Чёткое разделение полномочий.** API-токен Helper проверяется по хэшу в
   `api_tokens`, учитывается `is_revoked`; Frontier credentials никогда не
   возвращаются в ответе. Отвязка и повторная авторизация выполняются на сайте.

## Какие данные CAPI нужны Helper

Для локальной работы Helper — никаких Frontier-данных: данные игры он уже
получает из Journal-файлов. CAPI используется как серверный источник профиля,
рангов, кредитов, положения и, при необходимости, событий/Community Goals.
Helper нужен только ответ для статуса интерфейса: командир, дата обновления,
итог синхронизации и список предупреждений. Endpoint возвращает профиль,
уже нормализованный сайтом, если пользователь явно запрашивает синхронизацию;
секретные OAuth-поля в схему ответа не входят.

Синхронизация Helper ограничена одной попыткой в минуту на пользователя и
делает один запрос `/profile`; не тянет `/journal` и каталог Community Goals.
Это не отменяет расписание сайта. Запросы к CAPI не являются реальным временем;
пустой журнал и часть ошибок — штатные состояния, а не повод пересоздавать
OAuth-привязку. Сбой CAPI не следует автоматически трактовать как потерю
привязки, кроме подтверждённого отказа refresh/access credentials.

## OAuth и совместимость с практикой сообщества

Официальная публичная документация Frontier по Companion API неполна. Ниже
используются community-maintained материалы EDCD/FDevIDs и действующий клиент
EDMarketConnector (EDMC) как практический пример; эти материалы полезны, но не
являются официальной гарантией API:

- [EDCD/FDevIDs: обзор Frontier API и User-Agent](https://github.com/EDCD/FDevIDs/blob/master/Frontier%20API/README.md)
- [EDCD/FDevIDs: OAuth2/PKCE notes](https://github.com/EDCD/FDevIDs/blob/master/Frontier%20API/FrontierDevelopments-oAuth2-notes.md)
- [EDCD/FDevIDs: CAPI endpoints](https://github.com/EDCD/FDevIDs/blob/master/Frontier%20API/FrontierDevelopments-CAPI-endpoints.md)
- [EDMarketConnector](https://github.com/EDCD/EDMarketConnector)
- [EDMC troubleshooting: Frontier auth / 25-day reauthorization](https://github.com/EDCD/EDMarketConnector/wiki/Troubleshooting#problems-with-frontier-authentication)

Проверенные требования и следствия:

- OAuth запрашивает `scope=auth capi`; только `capi` без `auth` может вернуть
  неполную identity. Веб-поток использует PKCE S256, проверку `state`, точное
  совпадение `redirect_uri`; эти проверки остаются в `/api/capi/auth` и callback.
- Учитывайте платформу аккаунта (`audience`): Frontier / Steam / Epic и
  консольные платформы могут выдавать разные identities. Автоматический выбор
  `frontier,steam,epic` и платформенный выбор на странице сайта сохраняются.
  После OAuth фактическую identity следует диагностировать, а не угадывать по
  тексту произвольного HTTP 400.
- Frontier просит User-Agent вида `EDCD-[A-Za-z]+-[.0-9]+`. Сайт выставляет
  его в запросах OAuth/CAPI.
- CAPI `/profile` — структура с `commander`, `ship`, `lastSystem` и `ships`;
  нельзя считать, что поля плоские. `/journal` — NDJSON/строки журнала, не
  JSON-профиль; HTTP 204 означает пустой ответ, 206 может быть частичным.
- Live и Legacy используют отдельные hosts. Пустой профиль, временная ошибка,
  418 обслуживание или 429 limit не равны отзыву OAuth.
- EDCD рекомендует избегать частых запросов и не использовать CAPI как
  real-time feed. Сайт выполняет штатный синк по расписанию и ручному запросу;
  Helper не запускает собственный цикл polling.
- Повторная авторизация примерно через 25 дней — ограничение Frontier, а не
  дефект синхронизации: после истечения этого окна пользователь проходит
  OAuth заново на `/account/capi`.

## Регрессии

Проверяются:

- CAPI helper route: валидный API-токен, отсутствие binding, запрет sync без
  website binding, доступ к уже нормализованному профилю, отсутствие
  access/refresh-токенов в ответе;
- token bridge: GET/POST возвращают `410`, Frontier credentials не выдаются;
- Colonial Helper: его CAPI-кнопка вызывает только `ApiClient.sync_capi()`,
  статус читается только через API-токен проекта, ссылка ведёт на сайт;
- сайт продолжает использовать существующий OAuth callback, `capiSession()` и
  `syncCapiPilot()` — новый второй парсер профиля не добавлен.
